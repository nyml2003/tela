# 组件私有状态与声明式生命周期框架改动意图

> 状态：核心 owner 运行时、统一帧事务和代表性应用迁移已经落地；本文保留设计意图，
> 后续开发细则以 [036-事件系统与组件生命周期机制](036-事件系统与组件生命周期机制梳理.md) 为准。
> portable 测试和交叉构建不替代真实 Target 的 surface、present 与交互验收。
>
> 范围：`tela-ui` 状态所有权、`ui!` 组合语义、帧事务与 Host 能力
>
> 关联产品：变速齿轮、Transfer 等需要跨帧私有状态的组件

## 1. 背景

框架已经能够把组件写成声明式视图，并通过 owner runtime 让组件私有状态跨帧持续。本文保留这一能力的设计意图和所有权边界，防止后续开发又把搜索词、临时勾选、展开状态或交互中间态推回应用全局管理。

这不只是使用不便，还会模糊所有权：应用开始知道组件的内部操作细节，组件也不再是可以独立复用的交互单元。复杂组件会因此退化成一层外观包装，而不是真正拥有行为的组件。

本次改动的核心意图，是让组件可以持有自己的私有状态，并且在声明式重算、候选帧失败和旧事件到达时，仍然保持正确的生命周期与事务语义。

## 2. 状态所有权意图

框架应当让状态归属其最小必要所有者，而不是默认全部上收。

| 状态类别 | 应归属的所有者 | 典型内容 |
|---|---|---|
| 业务事实 | 应用或业务会话 | 当前目标进程、连接状态、已生效的速率 |
| 可控组件值 | 使用组件的上层 | Transfer 最终选中的目标键、表单已提交值 |
| 组件交互中间态 | 组件实例 | 搜索词、临时勾选、展开项、拖动中状态 |
| 通用视图状态 | Host 视图状态存储 | 滚动位置、视口约束、原生焦点协调 |
| 跨组件共享依赖 | 最近的共享作用域 | 主题、窗口能力、表单协调器、局部服务 |

组件的私有状态不应为了跨帧持续而泄漏给应用。反过来，一项会影响多个业务区域、需要持久化或代表外部事实的状态，也不应被隐藏在某个视觉组件内。

## 3. 组件生命周期意图

有状态组件应当表现为两个概念阶段：

1. 实例建立时确立私有状态与局部依赖。
2. 每次需要新视图时，根据当前输入与持久状态生成候选视图。

第一阶段只属于该组件的稳定实例，不因每一帧视图重算而反复执行。第二阶段可以反复执行，但它的职责是描述视图，而不是偷偷改变已提交的组件状态。

这个模型的目标不是强迫所有组件拥有生命周期。纯展示组件仍应当只是简单的视图转换，不因框架支持私有状态而被迫承担运行时实例、动态分发或额外存储成本。

## 4. 稳定身份与跨帧持续

私有状态能否持续，必须由声明式树中的稳定身份决定，而不是由某次构建出来的临时对象地址决定。

默认情况下，组件在树中的位置、类型与显式业务键共同界定身份：

- 身份稳定时，私有状态应在多帧之间保留。
- 组件被移除时，其私有状态应随该实例失效。
- 组件类型或显式键发生变化时，应视为旧实例移除、新实例建立。
- 动态列表的排序变化不应让状态误投到另一个业务项，因此列表中的有状态项需要稳定的业务键。

框架应当让这些规则可预期、可观察、可验证。不能依赖隐式的全局名称寻址，也不能让开发者在普通组件中手工管理一套另外的生命周期注册表。

## 5. 候选帧与提交语义

组件私有状态必须纳入现有的帧有效性模型，不能成为绕过帧事务的旁路。

框架采用的意图是 Host 候选事务与帧令牌共同守住活跃状态：

- 一次视图构建生成的树、组件实例、局部处理关系与 Host 视图状态只是候选结果。
- 只有完整候选帧被成功接受时，这些结果才一起成为新的活跃状态。
- 候选帧建树、计划解析、布局或 renderer preflight 失败时，已活跃的组件实例与状态不得被部分覆盖；Target present 失败时不得接受未实际呈现 token 的输入。
- 事件只能作用于产生它的当前活跃帧。来自过期帧的输入不得修改新树上恰好占据同一位置的组件。
- 局部状态更新应是一次完整的事件处理，不向外暴露半更新的中间状态。

应用不得在 `FrameCoordinator` 外再长期持有一份 active `UiTree`、`UiFrame` 或
`IdentityAllocator`。绘制、命中、Action 路由、组件路由与 Host 视图状态必须来自同一次
候选构建，并在同一提交边界成为 active；临时投影树只能用于候选内部收敛，不能接收输入。

这个约束同时保护应用状态与组件状态。两者不应拥有两套彼此独立的提交规则，否则会出现视图已回退而私有状态已前进，或视图已前进而局部处理关系仍属于旧帧的分裂。

## 6. 局部事件与可控输出

组件需要能处理只对自身有意义的事件，但这不意味着框架应引入一个无边界的全局事件还原器。

局部事件的意图是：

- 事件的类型与处理关系在组件边界内明确。
- 处理过程修改该组件的普通私有状态，不强迫每一个局部字段都升级为可观察信号。
- 只有对上层有业务意义的最终值或命令向外发送。
- 组件不应保留可捕获任意外部环境的不透明回调，以免寿命、重放和候选帧回滚变得无法判断。

一个组件可以同时拥有可控的最终值与非可控的中间态。Transfer 就是这种边界的代表：最终位于目标栏的业务键属于上层，左右搜索词和尚未移动的临时勾选属于组件。

## 7. `provide` / `inject` 与 Signal 的边界

`provide` / `inject` 继续承担有边界的局部依赖传递。它表达的是声明式树上的词法作用域：子树可以看到最近祖先提供的值，离开该子树后不应泄漏。

为了让这个作用域真正成立，子树的构建必须发生在父组件的局部环境已建立之后。`ui!` 的组合语义不应在父组件获得控制权之前就提前构建全部子节点，否则声明式嵌套只有外观，没有作用域语义。

Signal 用于真正需要被多个所有者观察、跨层共享或由异步源驱动的状态。它不应成为组件能够跨帧保存一个普通字段的前置条件。

因此，三者的分工是：

- 组件私有状态解决“这个实例自己记住什么”。
- `provide` / `inject` 解决“这棵子树共享什么”。
- Signal 解决“谁需要被一个持续变化源主动通知”。

## 8. `ui!` 的开发边界

新的应用和新组件应尽量通过 `ui!` 表达，因为这能够检验框架的声明式组合能力是否足够完整。

这里的“尽量”不代表用应用层技巧遮盖缺口。当应用无法自然地表达组件私有状态、子树作用域、双向值、输入事件或通用容器行为时，应当把缺口明确暴露为框架问题，先确认语义，再继续实施。

完成某个应用不是唯一目标。通过真实应用发现框架无法稳定表达的概念，同样是本次工作的产出。

## 9. 由真实组件触发的通用能力

Transfer 和变速齿轮会对框架提出一组可复用的通用要求，这些要求不应被实现为单一应用的特例：

- Transfer 应当是通用数据选择组件，支持两侧列表、搜索、临时勾选、定向移动、空态、禁用态与可控的最终键集合。
- 滑块应当是通用数值输入组件，能表达范围、离散节点、实时变更与键盘操作，而不是变速齿轮专用控件。
- 滚动动作应当真正作用于 Host 管理的视图状态，并保持解析与布局过程的纯净。
- 指针、键盘、焦点和手势需要能以统一的活跃帧语义到达组件。
- Host 需要通用的定时与唤醒能力，但滚动条的自动隐藏、淡出时机等平台体验仍归 Host SDK 所有，应用和 `ui!` 不跟踪这些可见性时序。
- Windows 应用共有的标题栏、窗口按钮、拖动区、DPI 与窗口状态协调应归入可复用的 Windows 公共能力，而不在每个产品中复制。

## 10. 明确不做的事

本次框架改动不以下列方向为目标：

- 不把所有状态都改造为 Signal。
- 不引入管理所有应用与组件的通用全局还原器。
- 不让 Host 知道 Transfer 搜索词等具体组件私有字段。
- 不开放可在 render 或候选阶段执行任意副作用的生命周期回调。现有挂载、卸载通知只用于发布后的 Effect 代际管理。
- 不允许组件通过任意捕获的回调隐式持有应用、Host 或过期帧。
- 不因一个新 APP 而提前冻结宽泛的跨平台终端接口。
- 不用产品层全局状态或手工节点构建来掩盖 `ui!` 的语义缺口。

## 11. 验收意图

框架改动只有在以下行为都能稳定成立时，才算达到设计目标：

- 同一组件身份经历多次视图重算后，私有状态仍然保留。
- 组件移除、类型变更或键变更后，旧状态不会泄漏到新实例。
- 动态列表重排后，有稳定键的项仍保留自己的状态。
- 候选帧失败时，活跃树、Host 视图状态、组件实例与局部处理关系都保持原状。
- 来自旧帧的事件不能修改当前组件状态。
- 父组件提供的局部依赖能在其子树构建期间被注入，且不泄漏到作用域之外。
- 纯展示组件不为未使用的状态机制支付显著运行时成本。
- Transfer 能在不向应用泄漏搜索词与临时勾选的前提下，保持可控的最终键集合。
- 滚动、键盘、焦点、定时唤醒与 Windows 标题栏在真实 Host 中表现为通用能力，而不是变速齿轮的私有补丁。

单元级语义、本地构建、跨平台交叉构建与真实 Windows 交互验收属于不同证据层。前一层通过不代表后一层已经完成。
