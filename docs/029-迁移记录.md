# 029-迁移记录：026 产品闭包落地

> 状态：已完成代码与目录迁移。本记录只说明迁移中作出的边界判断；它不把未在本机执行的
> Android、iOS、Win32、macOS 图形验收表述为已完成。

## 1. 物理投影与职责名

工作区按 026 的运行时责任迁移到 `crates/kernel`、`crates/ui`、
`crates/presentation`、`crates/delivery`、`crates/targets` 和 `crates/support`，业务应用
位于 `apps/desktop-demo`、`apps/mobile-demo`。原生 Android、iOS、WebView 和 macOS bundle
输入位于各自 `products/<target>` 根。

Cargo package 名也收敛为职责名，例如 `tela-ui-foundation`、`tela-desktop-ui-kit`、
`tela-mobile-ui-kit`、`tela-target-*`、`tela-*-resources` 与 `tela-desktop-runtime`。这不是仅
目录改名：`ops` 的产品模型和架构门禁使用同一套名称及依赖闭包。

`tela-log` 放入 `crates/support/log`。它是跨域的零依赖支撑库，不属于 Kernel 的 contract/core
内部责任，也不应被伪装成 Presentation 或 Delivery 模块。

## 2. UI、资源与文本边界

`ui-foundation` 只保留两端一致的基础控件和 `Icon` 原子；`IconKey`、`IconName`、`IconProvider`、
`UiResources` 与 `UiResourceSet` 是 Contract 中的纯值/窄协议。desktop/mobile kit 分别保留键鼠高密度
与安全区/触控模式。desktop 和 mobile application 的领域、控制器和业务视图仍是两份实现，没有为了
macOS/iOS 或 Android 复用而合并页面。

具体字体、字形度量和 Material 映射移到 Presentation resources。应用和 kit 不再在生产闭包中选择
`ControlledTextMeasurer` 或 Material provider；产品根用 Contract 的 `UiResourceSet` 注入二者。图标
provider 直接用 Contract 值对象构造 `UiNode`，既不反向依赖 Kernel Core，也不反向依赖 UI Foundation。

`TextStyleRef` 取代 `FontRef` 作为 Kernel 所见的排版样式 token，其内部存储私有，只允许通过
`new`/`as_str` 传递稳定语义名。为保持未版本化 frame ABI 的字段形状，wire/`TextContent` 字段仍叫
`font`，但其值是 token 而不是字体文件、字体族或 glyph provider。Canvas 只原样转发该 token；实际
字体解析仍在 Presentation。

图标与文字的行内对齐使用 provider 给出的 `IconOpticalMetrics` 和逻辑行盒，不让 UI kit 解析字体
glyph。这样 SVG、图集和平台图标可以替换 Material 字体，而不会把资源实现泄漏进 Application。

## 3. Product 与 Target 的装配方式

动态交付新增两个 Rust 产品根：

- `products/desktop-guest` 选择 desktop application、资源和 App ABI，供 WebView、Win32、macOS
  的不同 Target 分别加载。
- `products/mobile-guest` 选择 mobile application、资源和 App ABI，仅供 Android 的动态路线使用。

这两个根不是新的 Target，也不是共享业务 view；它们只解决“同一产品 guest 被多个动态 Target
交付”这一装配问题，避免任何 Target 静态链接应用。

两个动态 product crate 不继承 workspace 的 `unsafe_code = "forbid"`，而是对手写代码保持
`deny(unsafe_code)`。ABI 导出宏生成的 `extern "C"` 入口是经过 `tela-app-abi` 审核的唯一局部例外，
宏内显式降级 lint；不能使用 workspace 的命令行 `forbid`，否则会连这个受控 FFI 边界一并拒绝。

iOS 选择独立的 `products/ios` 静态产品根。`targets/ios` 只暴露 iPhone 的窄
`IosMobileSession` 交换面并保留 UIKit、Metal、safe area、IME、touch 与生命周期；iOS product 负责
实例化 mobile application 并注入资源。没有创建 Android/iOS 共用 runtime 或万能 Host trait。

`products/core`、`products/win32` 没有创建空目录或空 Cargo package：前者是纯 Rust 闭包，后者当前
没有需跟踪的原生工程输入。二者仍作为 `ops` 中的显式 `ProductSpec` 和构建入口存在。这样产品选择
可审计，又不会制造只为目录完整性而存在的伪执行文件或无内容目录。

## 4. 工具链与门禁

根 flake 保持一份 lock，并声明 `core`、`webview`、`android`、`ios`、`win32`、`macos` 六个产品
shell；`default` 收缩为 `core`。WGPU 测试环境和资产生成移到 `render-wgpu`、`assets` capability shell。
不支持的宿主也有同名 shell，但会明确拒绝而不是回落到 default。Android/iOS 私有 rustup bootstrap
改为使用锁定 nixpkgs 导出的 Rust release，不再请求浮动 `stable`。

`ops build` 不再猜测默认产品。`core`、WebView、Android、iOS、Win32、macOS 分别有显式入口；动态
路线先构建相应 guest，iOS 只构建静态 product。架构门禁读取 `cargo metadata` 的 normal/dev/build
依赖，并同时约束 Kernel、UI、Presentation、Delivery、Target 与 Product 的方向；Presentation 对 UI
的反向依赖会被门禁拒绝。

本次按迁移约束未启用或评估 Nix shell，也未执行不在当前 WSL 主机可完成的原生图形验收。它们仍应在
对应产品宿主上按各自 Target 的运行流程验证。
