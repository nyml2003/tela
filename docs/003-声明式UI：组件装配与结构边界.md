# 声明式 UI：组件装配与结构边界

> `ui!` 提供可读的声明式 UI 表面；组件类型和 `UiSpec::assemble` 提供真正的语义边界。
> 宏负责组装，组件负责解释自己的能力，运行时不猜测。

本文记录 033 之后形成的 UI DSL 设计共识，并标明截至 2026-08-31 的实现状态。响应式图与身份原则见 [001](./001-响应式核心抽象：边、坐标与身份.md)，候选帧、脏传导和提交回滚见 [002](./002-渲染管线：脏的传导与身份缓存.md)。

> **阅读约定**：本文的“已实现”必须能在当前代码中找到对应链路和测试；“下一阶段”是已经确定方向、但尚未接入完整运行时的能力，不能被当作本次已经完成。001/002 仍包含更大范围的 retained / binding 性能目标，003 不用新的 DSL 语义掩盖那些缺口。

## 1. 先说结论

Tela 的 UI 只有一个概念：**组件**。普通组件、结构组件、容器组件和自定义组件都经过同一套身份、状态、绑定、候选帧和提交事务。

组件之间的差异不由标签名或“是不是叶子节点”决定，而由组件自己声明的 `UiSpec` 决定。`UiSpec` 的公开装配操作统一叫 `assemble`。`UiSpec` 是完整的组件生命周期契约；目标态不保留由 `UiSpec` 再调用旧 `DslComponent::render` 的过渡层。

```text
组件类型 ──声明──> UiSpec
ui! ──生成类型调用──> UiSpec::assemble
assemble ──创建/注册──> 组件拥有的视图、绑定和结构边界
```

因此：

- `ui!` 是可读的结构和属性表达式，不是第二套业务语言；
- 只读 Signal 只有在显式传入并被组件契约接收时，框架才处理它；
- `Show`/`Switch`/`For` 可以控制子树的创建时机和次数，但不窥探子树内部；
- 组件只能更新自己创建并拥有的目标；
- 所有更新都先进入候选帧，`presented(token)` 后才成为活动状态，失败则回滚。

本文的“已定”表示实现者不得自行改变语义；“下一阶段”表示语义已定但仍缺少实现；只有“待决定”才需要新的产品或架构选择。

## 2. `ui!` 的边界

### 2.1 宏做什么

`ui!` 只做以下工作：

1. 解析 XML/JSX 风格的标签、属性和嵌套结构；
2. 把属性中的 `{expr}` 原样作为 Rust 表达式传递；
3. 把标签解析为一个真实的 Rust 组件类型；
4. 生成对该组件 `UiSpec::assemble` 的类型化调用；
5. 把普通 Rust 表达式作为属性值、渲染函数或其他组件输入。

属性表达式的含义由目标组件的 Props 和 `UiSpec` 决定。宏不理解业务类型，也不把某个表达式偷偷改写成 Signal 订阅。它也不刻意区分普通值和只读 `Signal`：某个 Props 是否同时接受 `T` 与 `Signal<T>`，是该组件自己的 Rust 类型设计，而不是 DSL 的全局规则。

### 2.2 宏不做什么

以下行为不属于 `ui!`：

- 扫描 `.get()`、方法调用或闭包体来推断依赖；
- 根据标签名判断组件能力；
- 根据 `Text`、`Icon`、`Image` 等名字选择“叶子优化”；
- 根据节点数量决定是否可以 retained；
- 查询运行时全局注册表或通过字符串选择装配逻辑；
- 为 `For`、`Show`、`Switch` 或任何单个组件开专用解析后门；
- 检查已经生成的子节点内部结构。

如果一个组件需要响应某个 Signal，它必须在自己的类型契约或 `UiSpec` 中声明；如果没有传入这样的值，框架就不处理这条边。组件可以在自己的实现中处理普通值，框架对此保持无感。

### 2.3 显式核心不等于把实现细节摊给调用者

本设计有意把复杂性放在组件契约和运行时，而不是为了少写几行调用代码而让运行时猜测依赖、所有者或业务接收者。Rust 的静态类型和可控执行开销使这条分层可行：组件库可以把绑定、对账、比较和 fast path 集中实现并充分优化，而不需要把这些隐式规则藏进宏或全局运行时。

“显式”的责任按层次分配：

| 层次 | 必须显式的事实 | 不要求每次手写的实现细节 |
|---|---|---|
| 调用点 | 传入的是普通值还是组件契约接受的**只读** `Signal`；Output 交给哪个逻辑接收者 | 建立订阅、选择组件已声明的重装配或静态呈现绑定路径、计算 damage、维护候选注册表 |
| 组件 / `UiSpec` | Signal 的源、自己拥有的目标、更新方式和 damage；公开 Output 的类型 | 调用者的父组件业务 State 和孩子的私有实现 |
| 运行时 | 候选、提交、回滚、订阅替换和生命周期回收 | 任意业务类型之间的隐式映射或跨组件写入 |

因此，调用点可以保持短小：

```rust
ui!(build {
    <Text value={title} />
})
```

内建 `Text` 与 `Icon` 明确接受普通值或只读 `Signal`：`value` 可为 `String`/`&str`/`Signal<String>`，`color` 可为 `Color`/`Signal<Color>`。普通值只参与本次装配；Signal 值选择该组件声明的静态呈现边。调用点只传入值，不写订阅、轮询、`NodeId` 或路由。

传入 `Signal<String>` 后，`Text` 在候选副本中只更新自己的文本内容并标 `Layout`；传入 `Signal<Color>` 后只更新自己的文本颜色并标 `Paint`。dirty 集完全由这些绑定拥有、没有普通 watch 或未提交 Output 事务时走 binding-only 快路径。若同一 retained 根还有普通 `#[watch]`，它先按普通规则候选重入，binding 随后同步到新的候选输出根，不能借“文本是叶子”绕过 `view`；多个静态 binding target 嵌套时按最深到最浅路径投影，父壳保留已更新的 child。没有独立 retained 根、目标消失、结构，或无法选择 binding/retained 窄候选的图脏边才保守回退根级候选装配。调用点不需要也不能在“绑定”与“重装配”之间手工选择。

常用模式和 fast path 可以提供类型化语法糖、Props 适配器或库级辅助函数，前提是它们只有一个可检查的展开结果：仍然是某个组件 `UiSpec` 声明的 Signal 边、OutputConnection 和候选事务操作。语法糖不能退化为扫描任意表达式、标签名/叶子节点白名单、全局隐式订阅、未类型化事件冒泡或跨组件直接写入。

## 3. 编译期组件注册

### 3.1 注册跟着组件类型走

不建立一个用字符串索引的全局特殊组件表。每个 `DslComponent` 实现都明确声明自己的 `UiSpec`：

```rust
struct Text;
struct OrdinarySpec;

impl DslComponent for Text {
    type UiSpec<A: 'static> = OrdinarySpec;
}
```

结构组件显式使用自己的 Spec：

```rust
struct For;
struct ForSpec;

impl DslComponent for For {
    type UiSpec<A: 'static> = ForSpec;
}
```

这里的代码表示接口形状，具体 Props、生命周期和泛型参数按实现展开。重要的是：**每个组件都明确写出 Spec；普通组件也不依赖运行时猜测。**

`DslComponent` 只负责把标签类型关联到 `UiSpec`；Props、业务 State、事件、Output、初始化、装配和事件处理都属于 `UiSpec`。静态呈现绑定也由 Spec 显式附加到自己构造的 `ViewOutput` 根或内部 `ViewNode`：它只能绑定该组件创建的节点的 `NodePresentation`，不能引用另一个组件或活动树。这样“普通组件”和 `For`、`Show`、`Switch` 的区别只存在于 Spec 的输入和装配策略，不存在于宏的分支表。

### 3.2 `assemble` 是统一入口

公开 API 使用 `assemble`，不把 `lower` 或 `lowering` 暴露为用户概念。编译器术语可以在实现文档中说明这是“从 DSL 结构装配为运行时视图”的阶段，但组件作者面对的是 `assemble`。

`ui!` 的目标不是调用某个名字匹配分支，而是生成类似下面的类型调用：

```text
<For as DslComponent>::UiSpec::assemble(...)
```

Rust 编译器负责解析类型、Props、插槽/渲染器类型和返回值类型。注册失败、参数形状错误或渲染器类型不匹配，都应该在编译期暴露。

`assemble` 返回 `ViewOutput`：其中承载候选结构、显式 watch、静态呈现绑定、HostInput 路由和调用点的 OutputConnection。Spec 不直接改 active 状态。静态绑定可通过 `ViewOutput::attach_static_presentation_binding(component_snapshot, table, site)` 附加在输出根，也可在构造内部模板节点时通过 `ViewNode::attach_static_presentation_binding(component_snapshot, table, site)` 附加；其中 `table` 是由无捕获函数指针组成的 `StaticBindingTable`，组件快照只保留只读 Signal 句柄。常见的“字段绑定自己输出根”可写成 derive 字段 `#[bind(paint = function_path)]` 或 `#[bind(layout = function_path)]`；它只生成同一张静态表，仍要求 `Signal<T>` 字段和显式 `fn(&T, &mut NodePresentation)` 写入函数。

### 3.3 `UiSpec` 是唯一扩展入口

本文的目标不是围绕某个复杂控件设计一套协议，而是让绝大多数 UI 都自然落在同一条组件链路里；少数难以拆成普通节点的控件，也能以受限扩展有机接入：

```text
HostInput / scoped external input
  → Component::Event
  → candidate State
  → candidate Presentation + Component::Output
  → explicit OutputConnection
       Parent::Event：同一候选事务
       AppAction：presented 后才释放

外部模型的新事实
  → Signal / ReadSource
  → binding 或下一次 assemble
```

`UiSpec` 不只是旧 `render` 的别名。它是组件完整语义的唯一扩展入口，概念上需要容纳以下四件彼此解耦的事：

1. **呈现装配**：组件怎样创建自己的结构、以及可选地声明自己创建的输出根或内部模板节点的静态呈现记录和绑定计划；
2. **输入适配**：组件怎样把它拥有的 HostInput 事实翻译成私有 `Event`；
3. **状态机**：组件怎样在候选 State 上处理 `Event`，得到新的呈现和公开 `Output`；
4. **输出接线**：调用点怎样把 `Output` 显式交给逻辑父组件或最外层应用边界。

前两项和状态机语义由组件的 Spec 界定，其中状态机实现仍是组件私有；第四项由调用点提供接收者，不能让子组件反向依赖父组件或 `AppAction`。当前 Rust 形状已经是 `DslComponent -> UiSpec`、`UiSpec::{setup, assemble, handle, wire_output}`；实现不能把这四件事重新绑回“某个节点 key 直接映射为应用动作”的旧模型。

这使组件可以有不同形状，而不需要增加宏打洞或新的全局事件通道：

| 形状 | 可以自定义什么 | 仍继承什么 |
|---|---|---|
| 普通组件 | 普通节点的呈现与默认输入适配 | 身份、State、绑定、Output、候选事务 |
| 结构组件 | children 的调用时机、结构边界和身份对账 | 同上 |
| 专用表面组件 | 一个自己拥有的根表面，以及对坐标、手势、文本等 HostInput 的局部解释 | 同上 |

`Table`、`Canvas`、图表、地图、代码编辑器都只是第三类的可能例子，不是协议中心。它们可以声明专用呈现或内核 primitive；但这只在普通节点无法表达其布局、绘制或命中模型时发生。即使使用专用 primitive，它也不能绕过组件身份、候选提交、显式 Output、生命周期回收或所有权边界。

因此，扩展组件改变的是“怎样装配呈现”和“怎样解释自己拥有的宿主事实”，而不是“怎样越过系统直接改外部状态”。`ui!` 仍只生成已注册组件类型的 `UiSpec::assemble` 调用，不认识这些组件的特殊名称或局部业务语义。

## 4. 组件统一，插槽形状不同

“组件统一”不表示所有组件必须拥有相同的 Props 形状。统一的是生命周期和所有权；不同的是组件需要什么输入。

| 组件形状 | 输入 | 典型职责 |
|---|---|---|
| 普通子树组件 | 普通 `children` 渲染入口 | `ScrollView`、`Row`、`Column` 等包住或布局一段子树 |
| 条件结构组件 | 条件源 + 分支渲染入口 | `Show` 在候选帧中选择一个分支 |
| 多分支结构组件 | 选择源 + 分支身份函数 + 分支渲染入口 | `Switch` 在候选帧中选择并维护一个具名分支 |
| 列表结构组件 | 集合源 + `key` 函数 + 行渲染入口 | `For` 按身份创建、复用、移动和注销行 |
| 虚拟窗口组件 | 窗口信息 + 行/内容渲染入口 | 只装配当前窗口需要的内容 |
| 专用表面组件 | 自己拥有的根表面 + HostInput 输入适配 | 在局部坐标系中解释复杂绘制和交互，例如画布或代码编辑器 |

这不是“普通组件”和“特殊组件”的安全等级划分。所有组件都必须经过同一套身份、绑定、候选帧和提交事务；差异只体现在 `UiSpec` 的输入和装配策略。

普通 derive 组件的 children 表面是一个显式单次槽位，而不是预先构造的 `Body`：

```rust
impl Panel {
    fn view<A: 'static>(
        &self,
        build: &mut ViewBuild<A>,
        children: &Children<'_, A>,
    ) -> ViewResult<ViewOutput<A>> {
        let body = children.build(build)?; // 唯一的实际装配/挂载点
        build.finish(body, ViewSite::new(file!(), line!(), column!()))
    }
}
```

`Children::build` 最多成功一次。未调用时，调用点 child 的 DSL 闭包从不执行，因而没有孩子实例、订阅、Output route 或生命周期事件；已物化的 retained 槽位在独立重入时也只在再次调用 `build` 时恢复。若组件依据自己的显式输入从“消费”切换为“不消费”，这是结构删除：候选 memo 条目撤销并由根级候选对账注销旧孩子，不把旧 children 当作父组件的隐式状态保活。这个接口是刻意的 breaking change：它让“谁消费 children，谁决定其生命周期”成为代码中可见的边界。

默认槽位之外，调用点可以用**直接子级**的字面量 `Fragment slot` 声明独立命名槽位：

```rust
ui!(build {
    <Panel>
        <Fragment slot={"header"}>
            <Text value={"Title"} />
        </Fragment>
        <Text value={"Body"} />
        <Fragment slot={"footer"}>
            <Text value={"Save"} />
        </Fragment>
    </Panel>
})

impl Panel {
    fn view<A: 'static>(
        &self,
        build: &mut ViewBuild<A>,
        children: &Children<'_, A>,
    ) -> ViewResult<ViewOutput<A>> {
        let header = children.build_named(SlotName::new("header"), build)?;
        let body = children.build(build)?;
        let footer = children.build_named(SlotName::new("footer"), build)?;
        // Panel explicitly decides how to place the three Bodies.
        todo!("assemble the Panel-owned container")
    }
}
```

这里 `Fragment` 仍不创建组件身份、State 或 OutputScope；`ui!` 只把它转为当前调用点的一个 `NamedSlot` builder。名字必须是非空字符串字面量，重复名字在展开期报错。只有接收组件自己调用 `build_named`，该槽位才装配、登记 Output/route/watch 并取得 retained 快照；未消费的命名槽位不会隐式保活。每个槽位可独立消费一次、独立保留和注销，且孩子 Output 在实际消费点仍使用原有最近词法 `OutputScope`，不会因槽位名称改写接收者。此机制不要求宏认识 `Panel`、`Show`、`Switch`、`For` 或业务组件名称。

## 5. `For` 的共识接口

### 5.1 `For` 不接收并检查子节点

`For` 不应该先得到一组已经生成的 `ViewChild`，再判断这些节点是什么。它接收一个普通的 `row` 渲染函数，由自己决定什么时候、用什么参数调用它。

概念上的 DSL 形状是：

```rust
ui!(build {
    <For
        each={items}
        key={key_renderer}
        row={row_renderer}
    />
})
```

`each`、`key`、`row` 都是普通属性表达式。`ui!` 不需要判断标签是不是 `For`，也不需要为 `For` 解析一套嵌套闭包语法。

`each={items}` 有两种**显式**输入形状：普通 `Vec<T>` / slice 只提供本次装配快照；`Signal<Vec<T>>` 或 `Computed<Vec<T>>` 则让 `ForSpec` 自己拥有集合 source 的结构边。后者不是宏从 `items` 的读取中猜出的订阅，也不是把 source 交给某一行代管；它的生命周期由 `For` 本身负责，具体锚点规则见 §8.2。

### 5.2 `key` 和 `row` 使用同一种上下文

每一行都有一个可扩展的 `ForContext`。它至少包含：

```text
item
index
```

`key` 和 `row` 都接收这个上下文：

```text
key: ForContext -> String
row: (&mut ViewBuild<A>, ForContext) -> ViewResult<ViewOutput<A>>
```

这样以后增加 `is_first`、`is_last`、`total`、`visible_index` 等字段时，不需要把函数从两个参数改成三个或四个参数。字段是有类型的，不使用 `HashMap<String, Any>` 或字符串查找。

`key` 是根据上下文计算出来的结果，不是上下文的输入字段。装配顺序是：

```text
创建 ForContext(item, index)
    → 调用 key(context)
    → 将 key 编码为内部行身份
    → 按身份复用/创建行
    → 调用 row(context) 生成候选行视图
```

表面返回 `String` 是为了保持 DSL 简单；运行时在 `ForSpec` 内部马上将其编码为内部 `ScopeId`，不把字符串作为热路径上的内部句柄。

`index` 表示当前集合位置，`key` 表示稳定身份。列表重排时，相同 key 的行应保留组件状态，同时得到新的 index。是否使用 index 参与 key 是调用方的明确选择，不由框架偷偷改写或猜测。

### 5.3 `row` 的实际输出

`row` 是命名 Rust 渲染函数，不是内联捕获闭包；它直接接收同一个 `ViewBuild`。`ForSpec` 先为当前业务 key 压入行身份范围，再调用 `row`，因此行内的子组件、State、呈现记录和绑定都自然落在这个稳定范围下。它不能强制返回裸 `UiNode`。一行可能包含：

- 自定义组件及其生命周期；
- Fragment 或框架视图输出；
- 类型化 action；
- 需要由 `ViewBuild` 建立身份和绑定的子树。

因此内部返回值保留框架视图结果和构建错误信息，概念上接近：

```text
(&mut ViewBuild<A>, ForContext) -> ViewResult<ViewOutput<A>>
```

如果某个列表要求每行恰好一个真实根节点，由 `ForSpec` 在装配边界验证，而不是把所有行渲染器都降成内核裸节点。

### 5.4 行的身份、重排和失败

- 同一个 key 的行在重排后保留业务 State 和 lease，但会以新的 `ForContext` 再调用 `row`，所以新的 `index` 和 item 内容会生效；
- key 改变、行被移除或 `Show` / `Switch` 卸载时，行及其子树在当前 Output 批末统一注销 State、watch、route 和 lease；之后即使出现相同 key，也是一次新创建；通用 binding/presentation 接入后也必须同时注销；
- 重复 key、`key` 函数出错或 `row` 出错都会使整个候选帧失败，不能跳过坏行或局部提交；
- item 只在 `key` 与 `row` 调用期间借用。要让子组件跨帧使用数据，行渲染器必须传入拥有的值、复制值或显式 Signal 句柄。

## 6. `Show` 与 `Switch` 的共识边界

`Show`、`Switch` 与 `For` 遵循同一原则：它们需要的是**分支或行的渲染入口**，不是已经生成好的子节点。

已定的表面接口是：

```rust
<Show
    value={account}
    test={is_logged_in}
    then={render_account}
    fallback={render_login}
/>
```

`value` 可以是任意业务类型，`test` 是明确的谓词；不引入隐式 truthiness。普通 `value={account}` 只是一帧候选快照。若条件本身需要驱动分支重装配，调用点必须明确写成 `source={account_signal}` 或 `source={account_computed}`；`value` 与 `source` 互斥。`then` 和 `fallback` 都是命名 Rust 渲染函数，签名形状与 `For::row` 一致，差别是它们得到 `ShowContext`。两个分支都可读取当前值，但只在被选择时调用，也不得以捕获闭包暗中保存跨帧数据。

`ShowSpec::assemble` 负责：

- 观察显式传入的条件源；
- 在候选帧中选择当前分支；
- 条件切换时注销旧分支并注册新分支；
- 保持分支身份和组件状态规则；
- 在提交事务成功后才让结构变化成为活动状态。

分支切换时旧分支立即从候选注册表中删除；若它以后再次出现，按新实例建立 State、绑定和呈现记录，不复用已卸载分支的旧数据。

`Show` 不检查分支内部是 `Text`、`Row` 还是自定义组件，也不通过节点名称选择路径。分支内部创建出来的组件仍然拥有自己的状态、绑定和目标。

`Then`、`Else` 之类必须由宏认识的专门标签不属于本方案。

### 6.1 显式多分支：`Switch`

多分支不是让 `ui!` 扫描 Rust `match`、识别 `<Case>`，或观察孩子来猜结构。它是另一个注册到同一 `DslComponent -> UiSpec` 路径的结构组件：

```rust
<Switch
    source={screen}
    branch={screen_branch}
    render={render_screen}
/>
```

其函数合同是：

```text
branch: (&T) -> String
render: (&mut ViewBuild<A>, SwitchContext<T>) -> ViewResult<ViewOutput<A>>
```

`branch` 是无捕获命名函数，只返回稳定的**分支身份**，不是事件名、全局 key 或路由能力。相同 key 表示调用者明确要求复用同一分支实例；不同 key 则在成功候选提交时注销旧分支并建立新分支。`render` 同样是无捕获命名函数，它拿到当前值的不可变快照后可在普通 Rust 中写 `match`，也可继续装配 `For` 或子组件；但它不能把该值变成可写的共享上下文。

`Switch` 的 `value={T}` 与 `source={Signal<T> | Computed<T>}` 和 `Show` 一样互斥。只有后者建立结构 watch；该 watch 归 `Switch` 自己的完整内部 lease 所有，选中分支及其嵌套 `For` 的 source 则仍由各自组件拥有。分支切换候选若被拒绝，active 分支和其订阅保持不变；只有候选成功提交后，旧分支及其子树的 State、watch、route、binding 和 lease 才注销。

因此 `Switch` 补的是一个清楚的结构合同，而不是新的宏洞：宏仍只把 `value/source/branch/render` 四个普通属性交给 Props 槽位，组件自己完成类型一致性检查、身份范围、候选 watch 和事务式拆建。

## 7. 所有权与隔离性

采用“谁创建，谁负责”的规则：

- `ForSpec` 创建并管理列表边界、行身份和行的注册/注销；
- `ShowSpec` 创建并管理当前分支边界；
- `SwitchSpec` 创建并管理当前选中分支的身份边界；
- 普通容器 Spec 管理自己创建的容器节点；
- `Row` 或其他子组件管理自己创建的目标节点和绑定；
- 父组件不能直接写入兄弟或子组件内部的呈现状态；
- 需要跨组件传递动态值时，父组件把只读 Signal 或普通值作为显式输入传给子组件。

结构组件调用渲染入口，不等于它拥有渲染入口内部的所有权。它只拥有自己创建的结构边界和由此产生的生命周期；子组件的内部实现仍然封装在子组件自己的身份范围内。

HostInput 路由还要满足同一条规则，不能只因为“知道某个 `SemanticKey`”就取得处理权。候选 `ViewOutput` 私有携带一份 `SemanticKey -> 创建组件 scope` 的来源账本；组件声明自己的 HostInput 路由时，候选计划解析必须验证该 key 的来源 scope 与路由组件身份相同。子组件、已物化 `Children` 和 retained 快照会原样携带自己的来源记录；外层 wrapper 不能重新认领它们。`ViewOutput::opaque` 中的 key 刻意没有可认领的组件来源，因此它可承载视觉内容，却不能被任何 wrapper 事后变成组件路由目标。这样，删除 `ActionTarget` 不只是删标签名，而是删除“父/包装组件把处理器附着到孩子节点”的能力本身。

## 8. Signal、绑定与 damage

### 8.1 只有显式输入才形成边

组件或其 Spec 必须明确声明：

- 哪个 Props 是 Signal/Computed；
- 它观察哪个源；
- 它更新自己拥有的哪个目标；
- 更新属于视觉、布局还是结构 damage；
- 结构切换时如何注册和注销这组绑定。

宏不从任意 Rust 表达式中推断这些信息。特别是以下做法禁止：

```text
扫描 signal.get()
按标签名决定是否 watch
按叶子节点决定是否走直写路径
让一个组件直接拿到另一个组件的节点句柄
```

### 8.2 已实现：显式 watch 驱动候选重装配

当前接通的是第二条路径：组件在自己的 Props/derive 契约中显式声明 `#[watch]`，运行时只为这条已声明的边建立失效关系。`Show`、`Switch`、`For` 或普通组件需要因输入变化改结构、Props 或节点属性时，都走这条候选重装配路径。

透明结构也已支持直接 source，但仍保持显式：`For each={Signal<Vec<T>> | Computed<Vec<T>>}`、`Show source={Signal<T> | Computed<T>}` 与 `Switch source={Signal<T> | Computed<T>}` 分别由其 `UiSpec` 注册一条**结构 watch**；普通 `For each={Vec<T>}`、`Show value={T}` 与 `Switch value={T}` 不注册。结构 watch 的 target 是当前结构组件的完整内部 lease（`ComponentIdentity + InstanceGeneration`），不是 `NodeId`、`SemanticKey`、业务 key、第一行、父布局节点或隐形 wrapper。`InstanceGeneration` 由框架内部全局单调分配，业务组件、Props、Output 和应用代码都不能读取或构造它。

这类 target 只表达“这个透明结构必须重新装配”，不谎称拥有一个物理树坐标。因此它不参与 retained 定点重入或呈现字段直写快路径；运行时发现结构 target 后保守回到根级候选投影，再从新的候选树计算真实的结构、布局和绘制影响。这样空 `For` 也能持续观察 source，列表重排仍由 `key` 复用行身份，而没有把生命周期借给第一行或父节点。

候选帧解析每一条显式 watch 后保存 `(SignalId, version)`。提交前有两道复核：构建完成、进入待呈现阶段前检查一次；`FrameCoordinator::commit` 再检查一次。版本不匹配时不提交旧候选，恢复该 watch 坐标的脏标记并以新快照重建。这个检查只覆盖显式声明的 watch，不扫描任意 `Signal::get()` 以建立隐藏依赖。

结构 watch 的订阅同样属于候选计划：候选失败或 source 版本过期时，旧 active 订阅保持，结构 target 归还 dirty 集等待重试；只有成功提交才以新计划替换订阅。`Show` / `Switch` 切换分支或 `For` 删除行时，离开候选树的结构 source 也只在成功提交后注销。因此被隐藏或未选中分支里的 source 不会在失败候选中提前失效，也不会在已提交卸载后继续唤醒 runtime。

因此同一个组件作者只在定义组件时声明一次“这个 Signal 需要重装配”；页面调用者不需要写订阅、轮询或跨组件路由。组件仍只能重装配自己拥有的结构，不能借此修改孩子或兄弟的私有 State。

#### 输入能力与候选隔离（已定）

候选事务要能整体回滚，首先不能把“可写的共享对象”伪装成 Props 传过组件边界。目标态把向下输入明确分成两类：

| 输入 | 孩子拿到什么 | 运行时是否跟踪 |
|---|---|---|
| 普通 `T` | 父组件在候选投影时计算出的 Props 快照 | 不跟踪；以后是否重算由父组件的显式投影边决定 |
| `Signal<T>` | 只读的值、稳定来源身份、版本和订阅能力 | 仅当孩子的 `UiSpec` 声明该边时跟踪；组件可明确选择普通 watch 重装配或静态呈现绑定，宏不猜测 |

这里的 `Signal<T>` 已经是**只读 capability**：只有 `SignalWriter<T>` 持有 `set`/`update`，读取方无法从 `Signal<T>` 反推出 writer。写能力不随 Props 传递，因而子组件既不能回写父组件 source，也不能把共享 source 当作跨组件事件总线。

当前应用/宿主 source（viewport、hover、pressed、focus、动画时钟、窗口最大化、模态栈顶和按 scroll key 的 `ScrollState`）由 runtime 私有的 `SignalWriter` 写入；组件接收到的是只读 `Signal`，`FrameContext` 不暴露这些值的普通快照。组件私有 State 尚未以通用 `State Signal` 的形式对孩子公开：父组件在 Output 批末以最终 candidate State 重新装配，并把普通 Props 快照向下传递。这保持了候选 State 的隔离，避免把可回滚的内部 State 错误地暴露成可写共享对象。

`#[provide]` / `#[inject]` 是第三种、仍然显式的**词法只读 capability**：普通 `T` 表示本次父候选装配给出的快照，既不自动订阅，也不允许消费者写回；父级下一次候选重装配时它会重新解析，因此携带它的 derive 组件不能仅凭 SignalId 命中 retained cache。表格的行、列、格式策略等上下文适合走这条路径。若它必须在不重装配父级的情况下独立唤醒消费者，capability 的类型必须是只读 `Signal<T>` 或 `Computed<T>`，并由消费者显式 `#[watch]` / `#[bind]` 声明边。

版本复核的语义是“已声明的来源没有在候选期间变化”，而不是“运行时自动截获了每一次读取”。这条限制是有意的：只有显式 Signal 边才参与版本比较和候选重试。

### 8.3 已实现：组件声明的静态呈现绑定

`BindingSlot`、`StaticBindingTable`、`SlotGroup`、`SlotSelector` 和候选入口 `StaticBindingSelector` 提供静态布线的底座：槽位用无捕获函数指针从只读 Signal 取值，按 source version 比较，只写调用者提供的呈现值，并报告 `Paint` 或 `Layout` damage。`StaticBindingSelector` 额外接收一个条件 Signal 和两张静态表，只订阅当前分支及条件本身；候选失败时旧分支订阅保持 active，只有 `presented(token)` 后才切换。它只选择同一组件自己输出根或内部模板节点的呈现字段，不承担 `Show` 一类结构切换。`ui!` 不分析插值、标签名或叶子性；一个组件是否使用此能力，只由它的 Props 类型和 `UiSpec::assemble` 中的显式静态表决定。derive 的 `#[bind(paint = function_path)]` / `#[bind(layout = function_path)]` 只是输出根表的样板生成：它拒绝非 `Signal<T>` 字段和闭包，不能自行发现任意 `Signal::get()`，也不能绑定内部子节点或其他组件。

当前候选帧已经把这条链路接通：

1. 组件可在装配输出根时调用 `ViewOutput::attach_static_presentation_binding(component_snapshot, table, site)` 或 `ViewOutput::attach_static_presentation_selector(component_snapshot, selector, site)`，也可在构造内部模板节点时调用对应的 `ViewNode` 入口。公开入口只接受 cloneable 的组件快照与 `&'static StaticBindingTable` / `&'static StaticBindingSelector`，不接受捕获闭包、可写 capability、`NodeId` 或任意目标地址；
2. `ViewOutput` 和 `ViewNode` 都把待解析锚点、绑定表和源码位置随普通容器、`Show`、`Switch`、`For`、retained 快照一起传播并 rebase；`UiTree` 形成后才解析为真实 `SemanticKey`；
3. 初次候选装配从新树建立 `PresentationState`，只记录 source version，不二次修改刚装配的节点；成功 `presented(token)` 后，`PresentationRuntime` 才安装 source 订阅并替换 active 绑定表；
4. 绑定 source 写入时，若 dirty 集完全由 active binding 拥有、没有同坐标的普通 `#[watch]`，且没有未提交 Output，运行时克隆 active `PresentationState`，在候选 `NodePresentation` 副本上应用变更，再通过 `UiTree::splice_many_shared` path-copy 目标节点壳；active `Rc<UiNode>` 从不被突变。若另一个显式 watch 选择 retained 根独立重入，运行时保留根外的 sidecar、用重入输出的新绑定替换根内 sidecar，并以该组件既有 lease 恢复 child OutputScope；
5. 候选保存所有 binding source 的 version 和 `SignalId -> SemanticKey` 反向表。layout、renderer preflight 或 present 前任一 source 再变化时，整个候选被拒绝，候选中的**全部**显式 watch/binding 目标回到 dirty 集；旧 active 节点、旧绑定版本和旧订阅继续有效；
6. `Show` / `Switch` 分支切换、`For` 行删除、普通根重装配都只在成功提交时替换订阅。离开树的 source 此后不再唤醒 runtime；候选失败不会留下新分支或新行的幽灵订阅。

`Text`/`Icon` 是第一个已接入的组件契约，而不是特殊叶子路径：`value: Signal<String>` 的槽是 `Layout`，写自己 `TextContent::text`；`color: Signal<Color>` 的槽是 `Paint`，写自己 `TextContent::color`。自定义 `UiSpec` 可用同一个公开静态表入口绑定自己构造的输出根或内部模板 `ViewNode` 的 `NodePresentation`。测试覆盖了文字/颜色的 damage 分类、提交前 active 隔离、source 版本失效回滚、`Show`/`Switch`/`For` 注销和自定义组件内部节点，无一项依赖标签名猜测。

Host 不需要接收“直接改旧 UiNode”的命令：它 resolve 候选 `UiTree` 得到树形 `RenderPlan`，并沿既有 publication/presented token 通道提交。扁平 `UiFrame` 只在 ABI/wire 或显式诊断/导出转换时物化；当前没有新建字段级跨进程 ABI 补丁协议，那是传输级优化，必须在 002 的 shared-tree 基础上另行设计。

### 8.4 damage 的已定分类

- 文本内容变化通常同时影响文字布局和绘制，因此至少产生布局脏与视觉 damage；
- 颜色、填充、透明度、视觉偏移等几何不变的变化，可以只产生视觉 damage；
- 尺寸、边距、内边距、换行相关变化需要重新布局，并将受影响矩形交给绘制级；
- `Show`/`Switch` 的分支和 `For` 的行变化属于结构变化，通常会连带布局和绘制影响。

该分类已由 `BindingSlotKind::{Paint, Layout}` 表达，并已接入 binding-only 候选帧：`Text` 值变化产生 `GEOMETRY`，颜色变化产生 `VISUAL`。几何未变只能阻止不必要的重新测量，不能吞掉纯视觉变化的 damage。

## 9. 事件、输出与可插拔性

本节区分已经实现的三条 UI 事件路径和一个应用边界。`Signal` 是状态传播，不计入事件机制。

```text
已呈现 HostInput ──┐
                    ├──> Component::Event ──> Component::handle
非 HostInput sender ┘                                  |
                                                       v
                                             Component::Output
                                               |              |
                                               v              v
                                      Parent::Event      最外层 AppAction
                                      （同候选事务）    （presented 后释放）
```

这张图是所有组件共享的稳定协议，不是一张“只有普通控件能使用”的白名单。扩展组件可以改变自己的呈现装配，或声明如何把自己拥有的 HostInput 解释为 `Component::Event`；它不能因此增加一条绕过候选事务、Output 接线或生命周期检查的事件旁路。

`ActionTarget` 已从当前代码删除。`Output -> Parent::Event` 及其候选队列已经实现；不存在把孩子根 `NodeId` 直接映射为应用 Action 的替代入口。

### 9.1 HostInput：按已呈现节点投递宿主事实

鼠标、触摸、键盘、IME、辅助功能激活和窗口系统输入首先是宿主事实。它们使用当前已呈现帧的 `FrameToken + NodeId` 定位，不是通用业务事件地址：

```text
宿主输入
  → FrameToken + NodeId
  → 当前 active/presented 树中的组件路由
  → 该组件把 HostInput 显式翻译为自己的 Component::Event
  → Component::handle
```

- `Activate`、模态开关等少数语义输入可以从命中组件沿**逻辑组件父链**寻找处理者；子组件返回 `Ignored` 才继续，`Consumed` 或 `Output` 立即停止；
- `ShortcutActivated` 也属于语义输入，但不是旧式“全局 AppAction 回调”：Kernel 在已呈现树中以**栈顶模态根优先、当前焦点其次、树根兜底**选出 `origin_node_id`，它只定义这一次候选路由的冒泡起点。路由仍只能登记在组件自己创建的节点上，因此快捷键不能让页面或透明 wrapper 借用孩子节点、越过模态，或绕开 `Component::Event -> Output`；
- `TextInput`、pointer、keyboard、hover 等原始或编辑输入只交给命中目标，不向父级传播；
- `NodeId` 只在对应帧仍为 active 时有效。节点消失、路由不存在或 token 过期时，事件直接丢弃；不得按位置、语义 key 或“相似的新节点”重定向；
- HostInput 路由在候选计划解析时还必须证明目标 `SemanticKey` 由该路由组件自己创建；“key 存在于树中”不是跨组件接管输入的权限；
- 候选帧尚未 presented 时，旧 active 帧及其节点仍是唯一合法目标。候选失败则旧帧继续有效；候选成功后旧 token 的晚到输入一律失效。

这里的“冒泡”只指同一个**宿主语义事实**沿逻辑组件父链寻找处理者。它不表示 `Child::Event` 会自动作为 Rust 类型向父组件传播。

#### 专用表面组件也只接收 HostInput

普通组件通常把一个普通节点的 `NodeId` 映射为自己的 `Event`。专用表面组件可以拥有一个根表面节点，并将该节点命中的位置、手势、键盘、文本或辅助功能事实，按**当前已 presented 的本地几何**解释为自己的私有 Event。例如画布可以把位置解释为图元命中，代码编辑器可以解释为光标位置；这些局部语义不进入全局 `NodeId` 路由，也不要求宿主认识业务对象。

这不是第四条事件机制：宿主仍只交付带 `FrameToken` 的事实，根表面仍只属于一个组件，组件仍在自己的候选 State 上处理 Event。若某类表面需要虚拟语义目标或额外内核 primitive，也必须以显式、类型化的扩展契约登记，并与该根表面和已 presented 帧一起失效；不能把内部子目标暴露为可被其他组件或应用任意寻址的 NodeId。

### 9.2 组件直投（非宿主输入，已实现）

定时器 Tick、future/task 完成、stream 新值、网络回包、后台回调和显式观察到的 Signal 边沿都没有 `NodeId`。它们通过组件在 `setup` 阶段取得的、仅指向自身的类型化能力回到 UI 线程，而不是伪造点击或查询 UI 节点：

```text
UiSpec::setup(context)
  → context.event_sender()
  → ComponentEventSender<Component::Event>::send(event)
  → 有界的外部 ComponentEventMailbox
  → Host UI 调度器唤醒
  → UI 线程固定 ingress 快照
  → 当前 active lease 校验
  → Component::handle(Component::Event)
  → 新候选事务 → present(token)
```

组件可在 `ComponentSetupContext<E>::event_sender()` 中保存自己的 sender；真正开始外部工作时，Host/服务应在成功挂载后使用 `Mounted::effect_scope()` 向 `FrameCoordinator::component_event_sender_for::<E>` 或 `Application::component_event_sender_for::<E>` 请求同一个实例的 sender。后者同时验证 scope 仍是当前 active 实例、lease 仍匹配且请求的 `E` 正是该组件的 Event 类型；任何一项不满足都返回 `None`。`ComponentEffectScope` 为取消和诊断保留 identity/effect generation，但 sender 自身不暴露目标，且没有任何 API 接受裸 `ComponentIdentity` 来构造或投递 Event；请求 sender 必须交出一次成功 `Mounted` 签发的完整 scope capability。因此调用方无法把它改造成按裸 identity 给任意组件发送任意 Event 的全局总线。`send` 只接受同一个组件的 `E`，并要求 `E: Send + 'static`；它成功时只表示消息进入邮箱，不表示 handler 已运行或 UI 已提交。协调器销毁时返回 `Closed(event)`，邮箱达到固定 `4096` 条背压时返回 `Full(event)`，两种错误都返还 payload 所有权。

实现遵循以下边界：

- 同一个 `Component::Event` 既可以由 HostInput 产生，也可以由 timer/task/network 产生；来源不同，不改变组件自己的状态机；
- 直投恰好命中 sender 创建时绑定的一个组件实例，不做命中测试，也不做冒泡；
- sender 在内部只带不可对业务读取的 `(scope, generation)` lease token。UI 线程从当前 active lease 表回查完整实例；卸载、类型替换、key 改变或同槽位重建后，旧 token 不匹配并静默丢弃，绝不重定向给新实例；
- 后台线程不能直接修改组件 State、候选树或呈现。它只能入队并通过 `ComponentEventInvalidator` 请求 Host 开始一帧；`FrameCoordinator::dispatch_queued_component_events` / `Application::ensure_frame` 才会在 UI 线程创建候选事务；
- 外部 ingress 与 `CandidateOutputQueue` 分离。前者是“组件自己的 Event”的下一事务入口；后者始终只保存孩子向最近逻辑拥有者上报的 `Parent::Event`。若已有尚待 `presented` 的组件候选事务，外部邮箱保持原样，等该事务提交或回滚后才消费，不能把两条因果链混合。

`setup` 只可以取得和保存 sender，不能因为取得 sender 就启动不可回滚的后台工作：setup 所在候选帧可能被拒绝。真正的 timer/task/stream 启动与取消仍属于 Host/服务的生命周期桥接：成功 `presented` 后从 `FrameCoordinator::take_component_lifecycle_events` 或 `Application::take_component_lifecycle_events` 消费 `Mounted`，用其 `effect_scope()` 取得匹配的 sender 并启动工作；在 `Unmounted` 时按同一 `(identity, effect generation)` 取消自己创建的工作。旧回调即使在取消竞态中晚到，lease 校验仍是最后一道静默丢弃防线。Tela 没有也不应偷偷接管任意 Rust thread、future 或网络客户端的取消语义；通用执行器/任务注册表是基于这条桥接可继续扩展的独立能力，不是 sender 的越权后门。

Signal 值变化默认仍走第 8 节的显式 watch / 绑定路径，因为它表示“当前事实变成什么”，不是一次性的消息。只有组件显式需要某次边沿语义时，才可以把该观察结果转换为自己的 `Component::Event`。

### 9.3 Component Output：类型化、显式接线的向外结果

`Component::Event` 是组件处理输入时使用的私有类型；`Component::Output` 是组件对使用者公开的业务结果。它相当于类型化、事务化的 Vue `emit`，但不用字符串事件名，也不自动向祖先广播。

```rust
enum ConfirmDeleteEvent {
    ConfirmPressed,
    EnterPressed,
    ValidationFinished,
}

enum ConfirmDeleteOutput {
    Confirmed { user_id: UserId },
    Cancelled,
}
```

父组件不应依赖孩子究竟是点击、键盘、timer 还是网络完成导致了确认；它只消费孩子声明的 `Confirmed` 或 `Cancelled` 结果。调用点必须显式建立类型映射：

```text
ConfirmDeleteDialog::Output::Confirmed { user_id }
  → 预先声明的类型化映射
  → SettingsPage::Event::DeleteConfirmed { user_id }
```

这不是自动冒泡：Output 只有一个明确接收者。这个接收者是调用点建立的**最近显式逻辑 Output 作用域**：它可以是物理父组件，也可以隔着 `Row`、`Column`、`Show`、`Switch`、`For` 等透明结构/布局层的 Form 或页面拥有者；但它不能是兄弟、后代、任意 `ComponentIdentity`，也不能越过中间已经建立的语义 Output 作用域。接收者若要继续上报，必须先处理孩子的 Output，再显式产生**自己的** Output 交给自己的逻辑接收者。最外层也可以把 Output 映射为 `AppAction`。

若 `Output -> Parent::Event` 会修改父组件的 UI State，父组件的 `handle` 必须在发出 Output 的同一个候选事务中执行，二者一起提交或回滚。若 Output 的最终接收者是应用 Action，则它只能在候选帧 `presented(token)` 后释放，不能让被 rejected 的候选 UI 提前触发不可逆业务副作用。

组件本地 Event 路由由其 `UiSpec` 自己声明；Output 的接收者由调用点/父组件装配时决定。两者不依赖 `ui!` 对某个组件名或 `output={...}` 属性的专用分支。

Output 接线必须是独立于输入适配的通用调用点能力。`ui!` 的唯一公开写法是标签上的通用 `@output` 属性：

```rust
ui!(build {
    <ConfirmDialog
        visible={show_dialog}
        @output={map_confirm_dialog}
    />
})
```

`@output` 不是普通 Props，也不是某个组件的宏特例；它对所有注册组件有同一含义。右侧只能是无捕获的函数路径或函数项，不能是闭包。当前 mapper 的精确形状是 `fn(Child::Output) -> Parent::Event`，或最外层的 `fn(Child::Output) -> AppAction`。需要额外业务数据时，调用点写一个普通命名函数并把数据编码进孩子 Output 或父组件随后处理的 State；框架不偷偷提供 route context，也不允许闭包捕获父组件局部变量。

`@output` 是 `OutputConnection` 的简洁表面；展开后的连接持有 source lease、当前词法 OutputScope 导出的 destination、函数指针 mapper 和 `ViewSite` 诊断来源。这样结构组件、浮层或专用表面都不需要为“把孩子的结果带回拥有者”另开组件专用宏语法、闭包捕获或全局事件通道。

作用域规则已经实现：

- Output 的接收者是**显式逻辑接收者**，不是物理视图父节点；
- 嵌套的 Output 作用域只使用最近的显式作用域；
- `For`、`Show`、`Switch` 等结构组件只建立自己的结构身份、行/分支上下文和子树生命周期，不会自动成为孩子 Output 的接收者；它们保留 `ViewBuild` 携带的词法 OutputScope，行和分支里的 `@output` 因而默认连接到外围最近的逻辑接收者；
- `For` 需要提供行信息时，只通过已声明的 `ForContext` 传递，不把行身份、索引或项目数据塞进全局 OutputScope。

这条作用域规则避免把**物理嵌套深度**变成胶水代码：一个字段即使嵌在 `Row`、`Column`、`Show`、`Switch`、`For` 或其他纯结构/布局组件之下，也可以直接连接到表单或页面建立的最近逻辑 Output 作用域；这些中间组件不需要逐层接收、改名和再发送 Output。只有跨越真正的业务语义边界时，才需要显式把孩子的公开结果映射为拥有者的 Event；框架不能从同名 variant、字段名或节点位置猜出这种业务对应关系。

直接转发、字段更新和其他高频模式可以由类型化辅助函数、派生代码或语法糖表达，但它们必须展开成普通的、可检查的 `OutputConnection`，并保留一个明确逻辑接收者。`@output={ignore_output}` 是允许的显式忽略连接；非空 Output 缺少 `@output` 则必须失败。过程宏在展开时不能反射 `Child::Output` 的 Rust 类型，因此它生成“未接线”占位和相应的类型约束：只有 `()` 或 `Never` 可以保持未接线，其他 Output 由 Rust 后续的类型检查报错。它们不能恢复全局冒泡、字符串事件名匹配或孩子绕过拥有者直接改父组件 State。

Output 是**向上汇报**，不是任意组件间的消息总线。父组件处理孩子 Output 后，只能修改自己拥有的候选 State，并在候选对账中通过孩子声明接受的 Props、候选派生输入或显式 Signal 边向下提供新事实；它不能向孩子或兄弟组件的私有 `Event` 入队。若父组件需要上报，则由它产生自己的 Output，继续沿逻辑拥有关系向上。

`@output={函数路径}`、无捕获约束、显式忽略和非空 Output 的受检语义已经实现。`OutputConnection` 是内部类型，不向业务组件暴露 lease 或 route 信息；当前诊断包含 source/receiver lease 和 `ViewSite`，更丰富的因果链是后续诊断增强，不是协议缺口。

### 9.4 `AppAction` 是应用边界，不是第四条组件冒泡链

`AppAction` 处理 UI 树外的应用业务，例如会话过期、保存文档、深链导航和网络结果改变领域模型。它可以是最外层 Output 的接收者，也可以直接由应用基础设施产生；它不通过 `NodeId` 命中组件，也不沿组件树传播。

应用处理 Action 后改变领域 State 或 Signal，UI 根据新的事实进入下一次候选装配。应用级事件不应借由全局匿名 UI 事件总线回灌到任意组件；当前需要局部响应时，把状态作为显式 Props/Signal 向下传递。第 9.2 节的受作用域 sender 只用于明确的非宿主输入，不能改变这条所有权方向。

### 9.5 可插拔性的边界

一个可复用组件的公开合同只有它的 Props、children/插槽形状、显式能力依赖和 Output。它的 NodeId、私有 Event、State、timer、task、订阅和内部节点结构都不属于调用者。

```text
Props / Signal / children：父组件 → 子组件
私有 Event / State：组件内部
公开 Output：子组件 → 显式接收者
AppAction：UI 树 ↔ 应用边界
```

因此同一个 `DatePicker` 可以在订单页把 `DatePickerOutput::Changed(date)` 映射为 `OrderFormEvent::DeliveryDateChanged(date)`，也可以在旅行页映射为 `TripEvent::StartDateChanged(date)`；组件本身不得知道父组件 Event 或应用 Action 类型。

下列做法会破坏可插拔性，目标态禁止：

- 组件内部直接依赖全局 Controller 或应用 `AppAction`；
- 父组件把事件挂到或写入子组件内部 `NodeId`；
- 父组件依赖孩子的私有 `Child::Event`，而不是孩子公开的 `Child::Output`；
- 通过全局事件总线让任意组件订阅或发送未声明的业务消息。

### 9.6 `ActionTarget` 已删除

`ActionTarget` 违反“谁创建，谁负责”：父组件借一个透明包装器，把应用 Action 附着到孩子创建的根 `NodeId`，并且可以在孩子自己的候选状态机之前直接触发应用行为。

目标态不保留这种能力的任何形式。不能通过改名、自动转发、透明 wrapper 或“通用子树激活器”恢复它。若将来确实需要一个可复用的激活行为，它必须是一个注册组件，拥有自己创建的交互节点，先把 HostInput 解释为自己的 `Event`，再通过自己的 `Output` 显式上报；它不能修改、借用或代理孩子的内部节点。

## 10. 候选帧、提交与回滚

### 10.1 总事务规则（已定）

一次 UI 更新的可变部分只存在于候选 UI 事务中。当前已实现的候选内容包括组件 State、结构/lease/事件路由注册表、静态呈现记录与 binding 注册表，以及焦点、hover、滚动等宿主投影状态。当前 active/presented UI、应用领域状态和外部世界都不能被 HostInput 直接改写。

```text
HostInput
  → Component::Event
  ─┐
非 HostInput ComponentEventSender
  → 外部 ingress mailbox
  → UI 线程 Component::Event
  ─┤
只读 Signal source 的版本变化
  → 显式 watch 重装配边
  ─┼→ 候选 UI 事务
  → 候选 State 和结构
  → 已映射 Parent::Event 的 CandidateOutputQueue
  → 候选视图、布局、damage 和注册表
  → present(token)：只发布 frame / status / damage；不携带 Effect
       presented(token)：原子提交，并释放最终 AppAction 产生的 Effect 批
       take_presented_effects()：宿主立即、一次性取走该批
       rejected(token)：丢弃全部候选内容，旧 active UI 继续有效
```

其中有四条不可绕过的规则：

1. **HostInput 只改变候选 UI 事务。** 它可以导致候选组件 State、焦点、hover、滚动、呈现或结构变化，但不能直接写当前 active UI、应用领域状态、网络、文件或平台状态。
2. **孩子的 Output 到父组件 Event 必须走候选事务私有的专用 `CandidateOutputQueue`。** 父组件处理该 Event 所得到的 State、呈现、后续 Output 都属于同一候选事务；它们不能提前提交到 active UI。
3. **最终 `AppAction` 和所有 Effect 只能在 `presented(token)` 后释放。** `AppPublication` 本身不含 Effect；这里的 Effect 包括网络请求、文件写入、平台调用和其他不可逆外部行为。
4. **候选本地结果被拒绝时全部作废。** 候选组件 State、宿主投影状态、结构、候选呈现记录、待安装 binding 订阅、待处理父级 Event，以及尚未提交的 Output 派生 `AppAction` / Effect 一并丢弃；先前 active/presented 帧保持有效。这里不包括已经从候选外接受的程序化 `AppAction`（菜单、快捷键或服务入口）：它已经改变应用领域状态，其 Effect 只是在等待下一张成功呈现的候选；若该候选被拒绝或被更新候选取代，Effect 必须按原顺序重新暂存，不能凭空丢失或提前释放。

这条规则把 `ActionTarget` 一类“按子节点直接执行 AppAction”的路径排除在外。`CandidateOutputQueue` 的成员范围、批次推进、批末候选投影、结构对账、实例 lease 和失效投递规则已经实现。默认预算为最多 `16` 个非空批次、最多 `4096` 个已接纳 Envelope；正好达到上限且队列清空是合法的，尝试第 `N + 1` 个批或 Envelope 才失败。即使 Envelope 后来因 receiver 失效被静默丢弃，它也计入预算，避免用卸载绕过扇出限制。

#### Effect 的提交交接

`presented(token)` 是 Effect 的唯一发布闸门，但闸门后的交接也必须精确，不能把“已提交”又变成“宿主何时碰巧读到”。当前协议固定为：

1. `AppPublication` 只描述候选 `RenderPlan`、damage、status 与 token，绝不携带可执行 Effect；因此 host 在真正呈现前没有可误执行的对象。
2. 进程内 `ApplicationSession::presented(token)` 成功后，运行时把该 token 释放的 Effect 放入会话私有批；host 紧接着调用一次 `take_presented_effects()` 取得所有权。第二次调用为空，不能把这一批带入后续 frame。
3. `Output -> AppAction` 的 controller handler 在产生它的候选已经提交后运行；它的 Effect 直接进入刚刚确认的批。候选若未提交，这个 handler 根本不运行。
4. guest ABI 使用独立的 post-present packet：`tela_app_presented(token)` 成功后才生成 `tela_app_presented_effects_ptr/len`，候选 publication wire packet 中没有 Effect。guest 内部 drain 是一次性的；裸指针 packet 是供本次 host 回执立即复制的只读快照，不能把“只读指针被读了几次”误当成协议层的一次性保证。
5. `GuestRuntime::presented(token)` 先验证本地 pending token，再调用 ABI 并返回 token 绑定的 `GuestPresentationAck { outcome, effects }`。直接使用 guest runtime 的 target 必须在处理 follow-up candidate 前执行它支持的 Effect，或报告明确的“不支持此已提交 capability”错误；不能静默丢弃。

这把两种容易混淆的失败分开：候选内部 Output 导出的未提交结果会随候选一起作废；已被候选外入口接受的程序化 Action 不是候选局部事实，其 Effect 只延后到一次成功 `presented`，不因 surface 一次失败而消失。

### 10.2 `CandidateOutputQueue`：专车专用、分批推进

`CandidateOutputQueue` 不是通用事件循环。它只容纳已经完成 `OutputConnection` 映射的、从孩子发往最近显式逻辑拥有者的 `Parent::Event`。概念上，队列项是一个 `OutputEnvelope`：它保留发起者和接收者的实例 lease、所用路由的诊断信息，以及已经映射且完全拥有的父级 Event。它不保存原始 `Child::Output`，也不能借用发送者的 State、ViewBuild 或其他生命周期短于 Envelope 的数据。

以下内容不进入 `CandidateOutputQueue`：

- HostInput：先按 active/presented 帧的 `FrameToken + NodeId` 路由，再启动候选事务；
- 非宿主组件直投：进入独立的、生命周期绑定的外部 ingress mailbox；它在 UI 线程 lease 校验后才启动新的候选事务，绝不混入 Output 批次；
- 只读 Signal source 的版本变化：通过组件明确声明的 watch 重装配边或静态呈现绑定边标脏候选；
- `AppAction` 与 Effect：不进入 Output 队列。候选 Output 派生的 Action 只在该候选 `presented(token)` 后才交给 controller；Effect 通过提交后的专用一次性批离开 UI 运行时。候选外已接受的程序化 Action 的 Effect 与下一张候选绑定，reject / supersede 时重试而不提前外泄。

队列按 FIFO 的**批次**推进：

1. 每个非空批次开始时，固定本批要处理的 `OutputEnvelope` 集合；
2. 本批按 FIFO 顺序逐个派发。这里固定的是消息成员，不是候选 State 快照：后一个 Event 能观察到前一个 Event 已写入的候选 State；
3. 本批处理期间新产生的 OutputEnvelope 一律进入下一批，不插入或追加到当前批；
4. 本批结束后，运行时依据最终 candidate State 重建并统一对账候选树，执行 `Show` / `Switch` 分支切换、`For` 行增删/移动和实例注销；
5. 下一批才使用这个更新后的候选结构和路由注册表。指向本批末已撤销实例的队列项在出队时静默丢弃，不使候选失败。

因此，若同一批先处理的 Event 令 `Show` 或 `Switch` 卸载子树，后面已经属于该批快照的孩子 Event 仍会完成处理；批末才统一撤销该子树。下一批才会丢弃仍指向旧实例的事件。用户永远不会看到这个候选过程中的中间结构。

#### 批内 State 可见性与批末候选投影

一个 `OutputEnvelope` 出队后，只会调用其 receiver 的私有 `handle`。该 handle 对**自己拥有的** candidate State 的修改，立刻对同一批中随后派发到同一 receiver 的 handle 可见；其他组件既不能直接读取这份 State，也不会因为它变化而在批中收到新的 Props。

每个孩子在批开始时持有上一轮候选装配得到的 Props 快照。本批所有 Output handler 完成前，Props 快照保持不变；后一个 handler 可以看见同一 receiver 前一个 handler 写入的 candidate State，但子组件不会在批中突然收到新 Props。

批末运行时以最终 candidate State 调用应用的渲染入口并对账组件树，因此孩子在下一批才看到新的 Props，`Show`/`Switch`/`For` 也在此时完成结构拆建。binding-only dirty 直接对候选树做 path-copy；相互嵌套的 retained 根按最深 child 到父处理，最终只 splice 最外层根。静态 binding 无论彼此是否嵌套，都在同一候选树上从最深 target 向最浅 target 投影；父壳写入保留已经更新的 child `Rc`。若同一 retained 根同时有普通 watch，先重入得到新根，再同步该 binding；若它位于父重入后恢复的 child 快照内，会以未 prime 的候选值同步当前 source，不能把新版本误记到旧呈现值上。没有独立 retained 根、重入后目标不存在的 binding 和其他不满足条件的情况才走根级候选投影。独立重入会在候选中替换该根自己的 HostInput / Parent Event 路由和按组件 scope 归属的动画调度；一个非空 `Children` 槽位若在重入时不再被消费，则作为结构删除退回根级对账。纯 Host projection（scroll/focus/window）会复用 active 共享树创建候选 resolve/present，不重跑 controller 根 render；Host 投影与 binding/retained 图脏边同帧时，后者提供候选 tree，HostState 与 damage 在同一次 resolve 合入。focus 额外把旧/新 key 作为只读 damage 坐标，并把焦点环描边外沿纳入该坐标，故可局部重绘。候选被拒绝或 source 在 `presented` 前过期时，运行时按已记录的候选来源重试：只有根装配候选重跑 controller，Host/retained/binding 候选恢复其已有窄路径。结构变化、全局 viewport 变化，或没有 binding/retained 可选的图脏边仍走根级路径。这不改变本节的事务和可见性语义。

`assemble` 是候选装配和计算阶段：它可以创建候选结构、watch 和输入路由，但不能调用组件 `handle`、修改既有组件的 candidate State、产生 Output 或释放 Effect。Props 到达本身不会自动产生下一批 Output；下一批只接收前一批 handler 已经合法产生的上行 Output。若一个 State 变化需要外部工作，相关 AppAction / Effect 仍须等到 `presented(token)` 后释放。

因此候选事务以固定节奏交替：**上行 Output 批次处理 -> 候选投影与结构对账（必要时根级） -> 下一批上行 Output**。binding-only 与 retained 快路径只是这一投影阶段的受限实现，不是把 Props 变化伪装成向上的事件反馈环。

#### 实例 lease 与失效 Output

`ComponentIdentity` 表示可跨普通重装配复用的**逻辑组件槽位**，不是“每次创建都全局唯一的实例号”。`For` 的语义 key 是形成、复用该逻辑槽位的一个输入，但既不是 HostInput 地址，也不能单独区分一次卸载前后的两个实例。

候选运行时用下列概念标识一个具体存续期实例：

```text
ComponentLease {
    identity: ComponentIdentity,
    generation: InstanceGeneration,
}
```

`InstanceGeneration` 由框架内部按**全局单调序列**分配，对业务组件、Props、Output 和 AppAction 都不可读取、不可写入、也不可依赖其数值。候选被拒绝后允许留下编号空洞；编号只用于避免实例混淆，不承载业务顺序语义。普通 State 更新、Props 更新和普通重装配复用原 lease；一个逻辑槽位真正卸载、随后重建为新实例时，才获得新的 generation。

`CandidateLeaseRegistry` 是候选事务私有的：候选开始时以 active lease 为基础，批末结构对账撤销已卸载实例的 lease，并为新实例分配新 lease；`presented(token)` 才把结果提升为 active 生命周期。成功提交后供 Effect 使用的 generation 可以由这份已提交 lease 派生，但不能直接把 active Effect scope 当作候选队列中的 lease。

`OutputEnvelope` 的准入和投递遵循以下规则：

1. **入队时验证 source、receiver 和向上路由。** source 必须是当前正在合法处理的 live candidate lease；receiver 必须是该孩子最近显式逻辑拥有者的 live candidate lease。任何 sibling、descendant、任意身份直投或越过中间显式 Output scope 的路由都使候选事务失败。
2. **禁止自目标。** 完全相同的 source/receiver lease 是实例向自己发送 Output。更强地说，合法的向上 Output 路由根本不应出现 `source.identity == receiver.identity`，即使 generation 不同；出现即是路由或生命周期错误，入队时失败并回滚整个候选事务，而不是等待预算耗尽。
3. **出队时只以 receiver 的完整 lease 判断可达性。** `CandidateLeaseRegistry` 中不存在完全相同的 `(identity, generation)` 时，Envelope 静默丢弃。若同一 `ComponentIdentity` 已被新 generation 重建，旧 Envelope 不能投递给新实例。
4. **source 后续失效不撤回已接纳的 Output。** source 必须在发射并入队时存活；但一旦已通过准入检查并拥有独立 payload，之后 source 被批末结构对账卸载不影响投递。只要 receiver 的完整 lease 仍存活，父组件仍应消费这个已经发生的业务结果。

因此，当前批内的 source 不会因稍后的结构变化半途消失；批末撤销 lease 后，下一批才可能因 receiver lease 已失效而静默丢弃旧 Envelope。

候选必须同时拥有“最大非空批次数”和“最大已接纳 OutputEnvelope 数”两项预算。当前默认值是 **16 批** 与 **4096 条**：恰好达到上限允许，尝试处理第 17 个非空批或接纳第 4097 个 Envelope 时失败；已接纳但随后因 receiver 失效被丢弃的 Envelope 仍占用总数预算，避免借卸载绕过扇出保护。超出任一预算时，整个候选事务失败并回滚，旧 active UI 保持；候选 Output 派生、尚未提交的 AppAction 与 Effect 一并丢弃。候选外已经接受的程序化 Action 不属于这份候选本地队列，其 Effect 保留为下一次成功呈现的待交接项；错误包含触发的预算、上限与本次尝试值。

只有在队列清空、最后一次候选投影和结构对账完成后，候选才能进入最终的布局、damage 计算和 `present(token)`。

### 10.3 候选装配、提交与回滚

所有已实现的 `assemble`、显式 watch 重装配和结构变化都工作在候选状态上；通用呈现绑定接入后也必须沿用同一提交边界：

```text
只读 Signal source 的版本变化
  → 显式 watch 标脏
  → 候选装配和结构对账，删除失效的 lease / route
  → 候选视图、布局、damage 和注册表
  → present(token)
       成功：原子提交
       失败：丢弃候选并恢复脏集/绑定状态
```

候选帧失败时必须保证：

- 当前已提交的树和宿主投影状态不被半写入污染；
- 新分支、新行和新 watch / route 注册全部随候选一起丢弃；
- 候选组件 State、焦点、hover、滚动等宿主投影状态不进入 active UI；
- 仍在候选本地队列中的父级 Event、候选 Output 派生但尚未提交的最终 AppAction 和 Effect 不会泄漏到下一帧或外部世界；候选外已经接受的程序化 Action 的 Effect 则保留，等待下一次成功提交；
- 被检测到但尚未完成装配的显式 Signal source 版本变化不会从脏集中消失；若它使候选失效，同候选中已经处理的其他显式 watch/binding 目标也会一并归还，避免半帧更新丢失；
- 下一次唤醒仍能重新尝试同一变化。

当前静态 `BindingSlot::apply` 是无返回值的函数指针写入，候选路径没有可恢复的局部失败分支；将来若允许可失败 binding apply，必须和结构装配失败等价：丢弃整帧候选结构、呈现记录与绑定变更，活动帧不变，相关脏边保留以供重试。

当前规则已经适用于直接属性更新、`Show` 分支切换、`For` 行对账和虚拟窗口变化。

## 11. 明确排除的方案

以下方案不属于本设计：

1. `ui!` 内部写 `match tag_name { "For" => ..., "Show" => ..., "Switch" => ... }`；
2. 通过 `can_leaf_memo`、内建标签白名单或叶子判断决定隔离和优化；
3. 为 `For` 增加 `{|item| ...}` 这类专用子节点语法；
4. 为 `For` 增加 `let={row}` 等专用模板变量语法；
5. 为 `Show` 增加必须由宏认识的 `<Then>`、`<Else>` 标签；
6. 让结构组件先接收完整子节点，再反射或遍历节点内部；
7. 用运行时字符串注册表替代组件类型的编译期 Spec；
8. 把所有 Signal 读取自动提升成隐藏 watch；
9. 让父组件绕过子组件边界，直接修改子组件节点。
10. 让同一身份的重装配先清空呈现记录，再靠 Signal 重新填充。
11. 把非宿主事件伪造为 `NodeId` 输入，或把失效节点的事件重定向到新节点；
12. 让 `Child::Event` 自动向父组件或祖先组件广播；
13. 使用全局匿名业务事件总线替代显式 ComponentIdentity 投递或 Output 连接；
14. 保留、改名或以透明 wrapper 变体保留 `ActionTarget` 一类旁路，把应用动作附着到孩子创建的节点。

这些排除项的共同原因是：它们把组件能力重新放回宏猜测、运行时反射或跨组件越权，破坏了声明边界和候选事务的隔离性。
