# 036-事件系统与组件生命周期机制

> 状态：当前开发基准；旧事件 crate、字段双发、应用读值回调、物理键组件旁路和独立
> 局部状态运行时均已删除。应用会话统一使用 ABI v6 的
> `initialize -> dispatch -> publish -> presented/rejected` 协议。真实 Target 的 surface、present
> 与交互验收仍须按平台单独完成。
>
> 本文是 Tela 后续事件系统、组件状态和生命周期实现的权威约束。它替代此前以
> 全局事件表、字段绑定和字符串路由为中心的讨论稿。Headless 事件栈、字段双发和字符串路由兼容入口已经删除；
> 后续开发直接遵守本文，不再设置迁移适配层。

## 1. 设计结论

Tela 采用**基于已呈现帧的、类型化的、分层事件系统**。

事件系统不使用一个万能事件枚举，也不使用全局字符串事件总线。运行时必须明确区分：

1. 平台输入事实：宿主观察到的指针、键盘和文本输入；
2. Kernel 交互事实：命中、捕获、手势竞争、焦点、滚动和模态规约的结果；
3. 组件局部事件：组件根据交互事实处理自己的私有状态；
4. 组件 Output：组件向父级暴露的有限语义结果；
5. 应用 Command：按钮、菜单、快捷键和组件 Output 汇聚后的业务入口；
6. 应用状态与 Effect：业务模型变更和宿主/网络/桥接副作用。

核心关系是：

```text
AppFrameInput
  -> 校验来源 AppFrameToken 已实际呈现
  -> Kernel 交互规约
  -> KernelInteraction
  -> 组件局部 handler
  -> ComponentOutput
  -> AppCommand
  -> ControllerOutcome（状态变化 + 待提交 Effect）
  -> 候选帧
  -> AppPublication（frame + status + effects + token）原子发布
  -> Target present
  -> presented(token) 提交，或 rejected(token) 回滚
```

每一层只拥有自己的状态和副作用。下层可以是函数式状态转换，上层可以持有长期状态，
但不得跨层直接访问对方的所有者。

## 2. Tela 的不可变核心约束

事件系统必须服从 Tela 已经确立的运行时边界，而不是反过来改变这些边界：

- `AppFrameInput` 必须携带输入所针对的已呈现 `AppFrameToken`；旧帧输入不得进入新帧命中
  或组件状态处理；
- `UiTree -> resolve -> UiFrame` 是纯投影，`resolve` 不读时钟、随机数、宿主对象或
  业务 Signal；
- `ViewStateStore` 由 Core 持有焦点、滚动、指针会话等视图交互状态；它不是业务 Store；
- 组件 owner 持有组件实例的私有跨帧状态；候选帧状态只能在成功发布后替换 active 状态；
- 应用 Signal/Store 持有业务状态；业务状态不写入 `UiNode` 或 Core 的全局运行时；
- 建树、计划解析、布局或 renderer preflight 失败时，不得部分提交状态、Output、mount 或
  unmount；Target present 失败时不得把未呈现 token 用作后续输入来源；
- 宿主只负责平台生命周期、输入标准化、Effect 执行和帧呈现，不解释组件内部事件。

这意味着事件处理不是“收到动作后随便修改全局状态”，而是一次有帧来源、有所有者、有
提交边界的状态转换。

## 3. 运行时分层

### 3.1 平台输入层

平台 Target 将平台事件转换为 ABI 可传输的输入事实：

- 指针的 id、设备类型、阶段、位置、按钮和时间戳；
- 物理键、修饰键和重复标记；
- 受控文本值、输入焦点、提交、取消和 IME composition 阶段。

Target 不提前合成 `Click`、`Scroll` 或业务命令。多指、指针捕获、手势识别、嵌套滚动
和焦点路由由 guest Kernel 处理，保证 WebView、Win32、macOS、Android 和 iOS 共享同一
交互语义。

### 3.2 Kernel 交互层

Kernel 对一次输入执行显式状态转换：

```text
(UiTree, UiFrame, ViewStateStore, Input)
  -> (ViewStateStore', KernelInteraction[])
```

Kernel 负责：

- 命中测试和当前帧的 `NodeId` 解析；
- pointer capture 和 pointer session；
- gesture recognizer 竞争与胜者选择；
- nested scroll 的增量消费；
- 焦点迁移和焦点作用域；
- Modal/Teleport 的输入边界；
- 键盘导航、激活和文本输入目标；
- 由这些机制产生的视图状态变化。

Kernel 不负责：

- 解释 `command.*`、`folder.open.2` 等业务字符串；
- 更新应用模型；
- 调用 bridge、HTTP、线程、窗口或定时器；
- 直接读取或写入 Signal；
- 为组件构造闭包回调。

唯一的 Kernel 出站类型是 `KernelInteraction`。它只描述机制事实，不允许增加业务命令
变体；业务语义必须在 Composition 的 typed 路由中产生。

### 3.3 当前帧交互索引

组件树构建时同时生成三类帧计划：

- `InteractionIndex`：`NodeId`、交互能力、组件实例和事件槽的映射；
- `LogicalPathIndex`：逻辑父级、组件边界和传播路径；
- `LifecyclePlan`：本帧出现的组件实例、状态类型和 Effect 作用域。

这些计划只属于候选帧。`LifecyclePlan` 当前由 owner frame 的候选状态和提交通知共同实现；
后续若需要独立的静态计划对象，必须保持同一提交边界。输入只能查找已呈现帧的计划，候选帧
未提交前不能成为输入来源。

Kernel 的树拍平、focus graph 和 hit region 快照由 `KernelInputPlan` 在 `ResolvedFrame`
生成时一次构造，并随该帧保存。pointer move、key 和文本事件只复用这个不可变计划，不得为
每个样本重新调用 `UiTree::node_table()`、重建 focus context 或克隆完整 `UiFrame`。

### 3.4 组件运行时层

组件运行时根据 `KernelInteraction` 找到最近的组件实例，执行局部 handler：

```text
(active owner, local event)
  -> (candidate owner, Ignored | Consumed | ComponentOutput)
```

组件 handler 可以：

- 修改组件私有状态；
- 消费事件，阻止继续传播；
- 发出有限的、声明过的 `ComponentOutput`；
- 为后续发布后的 Effect 声明需求；当前 handler 结果不直接携带宿主 Effect。

组件 handler 不可以：

- 修改应用模型的其他字段；
- 直接操作宿主窗口或渲染器；
- 直接调用 bridge 或 HTTP；
- 把组件内部搜索词、临时选择、拖动中间值广播到全局；
- 捕获一个会跨帧失效的 `NodeId` 或宿主对象。

### 3.5 应用命令层

应用只处理 typed command。组件 Output、快捷键、菜单和宿主命令可以映射到同一个应用
Action/Command，应用只维护一套 reducer 分支。

Command 的查找采用有限的 owner/responder scope：

```text
当前组件 owner
  -> 祖先组件 owner
  -> 当前窗口 scope
  -> 应用 root
```

这是命令路由，不是 UI 事件冒泡。未处理的命令可以继续向上，最终被丢弃并记录诊断；
不得回退为字符串解析。

## 4. 事件交付策略

事件按交付策略分类，而不是按“所有动作都能绑定”处理。

### 4.1 连续流：捕获、竞争和消费

适用事件：

- 原始 pointer move；
- 拖动和 splitter；
- 长按、缩放、旋转等手势；
- 文本 composition；
- 滚轮和触控板滚动增量。

规则：

- pointer down 确定候选目标和可捕获组件；
- pointer capture 后，后续流直接送到捕获 owner，不逐次沿祖先冒泡；
- 同一指针上的多个 recognizer 通过 gesture arena 竞争；
- nested scroll 传递未消费的剩余增量，而不是向所有祖先广播；
- 文本编辑流留在当前输入组件，提交/取消时才折叠为语义事件；
- 连续流可以有只读观察者，但观察者不能隐式获得业务修改权。

### 4.2 语义事件：逻辑树传播

适用事件：

- Activate；
- Submit；
- Select；
- Dismiss；
- Cancel；
- 一次完成的拖放或手势结果。

这些事件沿逻辑树执行：

```text
capture -> target/component -> bubble
```

事件上下文至少包含来源帧、目标 `NodeId`、当前逻辑节点、传播阶段和消费状态。

组件边界优先于应用边界：组件可以在 target 阶段消费内部事件并产出 Output；未消费的
事件才允许继续向逻辑父级传播。组件 Output 不自动重新作为内部事件广播。

### 4.3 状态通知：状态投影而非命令

适用状态：

- focus gained/lost；
- hover entered/left；
- pressed/selected；
- scroll position；
- IME composition 状态。

这些状态由 `ViewStateStore` 或组件 owner 保存，并通过下一帧投影外观。应用只有在明确
声明观察关系时才收到通知，不得在应用入口无条件 match 所有机制状态。

### 4.4 Command：独立的业务路由

按钮、菜单、快捷键、窗口标题栏和组件 Output 可以产生同一个 typed command：

```text
Button Activate ─┐
Menu Selection  ─┼─> AppCommand
Shortcut        ─┘
```

Command 不携带 UI `SemanticKey`，也不通过 `NodeId` 解析业务对象。动态业务对象必须
携带明确的领域 id 或类型化 payload。

## 5. 身份和地址模型

以下概念禁止混用：

| 概念 | 生命周期 | 唯一职责 | 禁止用途 |
|---|---|---|---|
| `NodeId` | 当前帧 | 命中和帧内索引 | 跨帧状态、业务命令 |
| `SemanticKey` | 跨帧 | 身份保持；构建期解析 ActionTarget 锚点 | 运行期事件总线、命令名 |
| `ComponentIdentity` | 组件实例 | owner 状态、生命周期、Effect 代际 | 节点命中、业务字段名 |
| component action route | 当前帧 | 类型化事件绑定索引 | 全局字符串路由 |
| `CommandId`/应用 Action | 业务生命周期 | 应用命令语义 | UI 结构身份 |

`SemanticKey` 首先服务跨帧身份保持。`ui!` 中的 `ActionTarget` 以结构锚点生成计划；对尚未
改写为 `ui!` 的 opaque kit 子树，Composition 可以在候选帧构建期用 `SemanticKey` 把 typed
Action 解析为 `NodeId`。发布后只能查帧内整数索引，不能再次解析字符串。静态节点优先用
自动路径；动态集合使用领域实体 id。禁止把 action 枚举编码进 key 后再反向解析。

组件实例身份由 DSL 根据调用点、组件类型和动态集合 key 生成。应用不再手工创建或持有
`ComponentIdentity`。

Teleport 必须同时记录：

- 视觉父链：用于布局、绘制和命中；
- 逻辑父链：用于事件传播、组件 owner 和 provide/inject。

树拍平只能改变这些父链和索引的存储形态，不能改变它们的语义。

## 6. 受控值和状态所有权

新的权威边界如下：

```text
Core:       TextInput { node_id, TextInputEvent }
Component:  InputChanged / SearchChanged / SelectionChanged
Application: Signal / Store / Reducer
```

Core 不产生字段变更或业务值。文本编辑只能通过已提交帧的 typed `on_input`、`on_submit`、
`on_cancel` 路由进入组件 Event 或应用 Action。组件若需要草稿、IME 组合态、冲突标记或
提交边界，应把它们放在 owner State 中，只把确认后的 Output 暴露给父级。

输入节点必须在 `TextInputSpec.value` 中声明本帧完整受控文本快照。Target 可以持有一个只服务
原生编辑器连续输入的短期 channel，但不得通过 Application 回调或组件 owner 查询读取值；新帧
发布后必须用 active tree 的 `TextInputSpec` 协调该 channel。

当前没有通用双向字段绑定 API。后续若真实表单需求证明需要该能力，必须先讨论独立的
类型化字段契约；不得用 `SemanticKey`、字符串字段名或 Kernel 事件临时模拟。

Signal 适合应用级、跨组件或异步源驱动的状态；组件普通私有字段由 owner 持有，不要求
所有状态都升级为 Signal。`provide/inject` 表达逻辑树上的有限作用域，不是全局状态总线。

## 7. 组件生命周期和 Effect

生命周期采用以下阶段：

| 阶段 | 时机 | 允许做的事 | 不允许做的事 |
|---|---|---|---|
| setup | 实例首次出现 | 创建/恢复 owner、声明依赖和 Effect 需求 | 依赖候选帧一定会提交的外部副作用 |
| render | 每次候选帧 | 读取 Props/State/Context，生成节点和事件计划 | 写状态、调用宿主、发请求 |
| handler | 交互到达时 | 更新候选状态、忽略/消费事件、产生 Output | 直接提交应用或宿主副作用 |
| mount | 实例首次成功发布后 | 启动已声明的 Effect、申请需要已就位的资源 | 在候选帧失败时执行 |
| unmount | 实例从成功发布的树中消失后 | 取消/失效 Effect、释放订阅和资源 | 因候选帧失败提前执行 |

Effect 绑定 `ComponentIdentity + generation`。第一阶段可以只实现“卸载标记 + 代际号”
的逻辑取消：回调到达时检查作用域是否仍 active；后续再增加 bridge 的真实 cancel。

Effect、组件状态和 Output 都必须经过候选提交边界：

- 候选帧失败：全部丢弃；
- resolve/preflight 成功并发布：原子提交 owner、Output 和生命周期集合；
- 发布后：应用消费已提交 Output；需要真实 surface 的 Effect 等 Target 确认 present 后启动；
- 实例消失：先提交新树，再执行 unmount 清理。

应用动作由 `ControllerOutcome` 一次性返回 `changed + effects`。Runtime 不得在 publish 时
轮询控制器的“待处理窗口命令”；Effect 必须进入同一个 `AppPublication`，只在 Target 成功
present 并回执 token 后执行。被 `rejected` 的 publication 不执行 Effect。

## 8. `ui!` 和组件包装层

`ui!` 是声明语法，不是事件运行时。它负责生成：

- 逻辑树和 children 关系；
- 节点交互能力声明；
- 类型化 `EventSlot`；
- 组件实例和动态集合身份；
- `InteractionIndex`、`LogicalPathIndex` 和 `LifecyclePlan`。

`ActionTarget` 是绑定语法的表面形式，编译结果进入统一的 InteractionIndex。它保存 typed
Action 或静态函数项，不保存任意闭包，不建立第二套注册表。

组合包装层位于 `tela-ui-dsl` 和 desktop/mobile kit 之间：

- kit 只负责视觉节点和基础交互能力，不依赖 DSL runtime；
- wrapper 负责 Props、owner State、局部 Event、Output 和 DSL 计划；
- 应用只使用 wrapper 和 `ui!`，不接触 owner、候选帧内部结构或节点事件表；
- 纯展示组件不强制创建 owner；只有声明私有状态、局部 handler 或 Effect 的组件才创建
  实例运行时。

### 8.1 新组件开发顺序

新增一个有交互的组件时，按下面顺序确认边界：

1. 先确定 Props、组件私有 State、Event、Output；不能先把应用字段塞进全局 `Signal`。
2. 用 `ui!`/`DslComponent` 生成视觉节点和交互能力；节点只声明命中、焦点、滚动等机制事实。
3. 在组件 owner 内处理连续输入和局部语义事件；只有稳定的业务结果才转换成 typed Output。
4. 让父组件或 Application 把 Output 映射为 typed Command；不要从 `SemanticKey` 或 `NodeId`
   反查业务意图。
5. 让 `FrameCoordinator` 完成候选帧 resolve、token 发布、Output 提交和生命周期通知；
   present 失败时调用 abort 路径，不能自行修改 active owner。
6. 为跨帧状态、卸载、旧 token 输入和候选帧失败分别写测试，再接入具体 Target。

如果 `ui!` 无法表达需要的 Props、事件、私有 State 或 children 关系，应停止在应用层
绕行并记录框架缺口，先讨论统一语义。不得引入字符串分发、全局状态或应用专用 Host
分支来掩盖 DSL 缺口。

## 9. 当前实现基线与后续决策

截至 2026-08，统一事件主干和代表性应用迁移已经建立。后续开发只能沿以下链路扩展，
不得恢复已删除的兼容入口：

- `tela-contract` 只公开 `KernelInteraction` 作为 Kernel 交互事实；
- `KernelInputPlan::dispatch` 是已发布帧的输入热路径；
  `DefaultApplicationProfile::dispatch_kernel_input` 和 `tela-core::handle_kernel_input` 只保留为
  一次性调用入口，不得用于 Target 高频循环；
- `FramedInteraction` 携带 `FrameToken`，所有 Target 输入必须先绑定实际来源帧；
- `FrameCoordinator` 在候选阶段验证 tree、ActionPlan 和组件路由，生成
  `InteractionIndex + LogicalPathIndex`，成功后一次发布；
- `render_component` 把候选 owner frame 附着到 `ViewOutput`，setup 创建的私有状态与
  opaque/kit 视觉输出使用同一事务；
- `dispatch_interaction` 生成应用 typed Action，`dispatch_component_interaction` 进入组件
  handler；两者都拒绝旧 token；
- 组件 Output 在事务中暂存，成功发布后才能由应用取得；生命周期通知同样只来自成功发布；
- `speed-gear`、`win32-editor`、`mobile-demo` 和 `desktop-demo` 的业务点击已使用 typed action 链路；
- `desktop-demo` 已删除应用自持有的第二套 active tree/frame/allocator，最终 layout、绘制、命中、
  Action/组件路由与候选 `ViewStateStore` 由同一个 `FrameCoordinator` 事务发布；
- `desktop-demo` 的预协调和最终发布都使用同一套 `ui!` 组合函数；无 action 的候选树只用于
  焦点、模态和 hover 收敛，不接收输入，也没有第二套手写 View；
- Transfer 的搜索与临时勾选、`desktop-ui-dsl` DraftInputView 的草稿与 IME 状态、Slider 的连续编辑已由组件 owner 持有；应用只接收稳定 Output；
- `TextInputSpec` 声明 active frame 的完整受控值，统一 Win32 target 的原生文本 channel 只负责
  present 之间的编辑累积，不再回调 Application 或读取组件私有状态；
- 节点通过 `KeyboardInputSpec` 声明接管的语义键盘意图。Target 只做物理键到
  `KeyboardIntentEvent` 的映射，Kernel 决定默认导航或发出 `KernelInteraction::Keyboard`，
  Slider handler 不再接触物理键码；
- 旧 UI event crate、全局事件注册表、字段值双发、字符串 intent 解析和应用字段匹配入口
  已删除，不是可恢复的兼容面。

当前保留一个明确但不应由应用旁路解决的组件能力缺口：通用 Form 尚未提供“父级 submit
协调多个子输入先 Commit，再按顺序汇总 Output”的协议。现有应用必须让文本通道先产生显式
`Commit`（例如 Enter 或 blur），再执行确认命令；不得从 Application 扫描 owner 私有状态。
真正出现多字段原子提交需求时，应先设计基于 `provide/inject` 的局部 Form coordinator 及其
候选帧事务顺序，再实现产品功能。

portable 单测、WGPU 离屏测试和 Win32 release 交叉构建用于证明代码与协议；它们不能证明
真实窗口已呈现、原生 IME/焦点顺序正确或目标设备视觉通过。平台验收台账必须继续区分这些证据。

### 9.1 新交互放在哪一层

开发前按以下顺序判断，不要先增加枚举分支：

1. 平台是否只是在报告原始事实？放在 Target 输入标准化层。
2. 是否涉及命中、焦点、捕获、手势、滚动或模态？放在 Kernel。
3. 是否只是某个组件的草稿、展开、临时选择或拖动过程？放在组件 State/Event。
4. 是否是组件对父级承诺的稳定结果？定义 typed Output。
5. 是否改变领域模型？映射为应用 Action/Command，进入唯一 reducer。
6. 是否调用窗口、bridge、网络、线程或定时器？形成 EffectIntent，由 Host 在提交边界后执行。

无法明确归层时，先讨论所有权和时序，不得用字符串 key、全局 Signal 或 Host 特判先把功能
跑通。

### 9.2 `ui!` 缺口处理

应用和公共组件默认使用 `ui!`。允许 opaque `UiNode` 的场景只有纯视觉 kit 输出，或已有
复杂视觉树在保持像素结果时接入 typed ActionPlan；opaque 不得携带另一套事件系统。

遇到以下情况必须视为框架缺口并讨论：

- 无法声明组件 Props、children、私有 State、Event 或 Output；
- 无法把文本 edit/submit/cancel 或连续 pointer 映射到 typed handler；
- 无法让 provide/inject 按逻辑树作用域工作；
- 候选失败时状态或 Output 无法回滚；
- 必须在应用层扫描节点、解析 key 或维护组件内部草稿才能实现需求。

讨论结果应优先补通用 DSL/runtime 能力，再继续应用功能。不得创建应用专用宏分支、隐藏
字符串协议或长期 adapter。

## 10. 开发验收标准

### 10.1 语义验收

- App 入口只处理 typed Command、组件 Output 和明确声明的状态观察；
- Scroll、Focus、Modal、Pointer capture 等机制不需要应用手工 match；
- 同一业务动作可以由按钮、快捷键和菜单进入同一个 reducer 分支；
- 组件内部搜索词、临时选择和拖动状态不会出现在全局应用事件中；
- Teleport 命中按视觉树，传播和 provide/inject 按逻辑树；
- 未绑定事件被安全忽略，不回退为字符串解析。

### 10.2 帧和生命周期验收

- 旧 `AppFrameToken` 输入不能修改当前 active owner 或 ViewStateStore；
- 候选帧失败不触发 mount/unmount，不覆盖 active owner；
- render 重复执行不会产生副作用；
- setup 对同一实例只执行一次；
- 实例卸载后旧 Effect 回调被丢弃；
- 列表重排按业务 key 保留状态，换 key 或换组件类型创建新实例；
- provide/inject 在惰性 children 展开时遵守逻辑作用域。

### 10.3 性能验收

- 连续 pointer/gesture 流不为每个样本创建完整祖先传播链；
- pointer capture 后事件直接进入 active recognizer/owner；
- 离散事件使用预计算逻辑路径，不扫描全树和解析字符串；
- 命中目标使用帧内整数索引，状态保持使用独立 SemanticKey；
- 高频输入不克隆 `UiFrame`，不重建 node table、focus graph 或 hit-region 索引；
- `dispatch` 只更新状态并返回 `publish_requested`，不得编码、复制或 resolve 新帧；
- Target 只在 `publish_requested` 时调用一次 `publish`，frame/status/effects 必须从同一
  atomic publication 读取；
- Win32 每个消息泵时间片最多处理有界条数/时长的输入，随后必须给失效窗口一次呈现机会；
  不得依赖低优先级 `WM_PAINT` 自然等到鼠标队列清空，也不得持续 post 自定义 frame 消息；
- 新事件绑定不引入全局锁、全局事件总线或宿主对象捕获。

### 10.4 工程验收

- Core、DSL runtime、每个 kit 和每个应用都有对应的单元/集成测试；
- `speed-gear`、`win32-editor`、`mobile-demo`、`desktop-demo` 全部通过统一事件路径；
- 每个应用只能有一份接收输入的 active tree/frame；Host 的 `ViewStateStore` 必须作为 candidate
  与 Composition 帧一起提交，不能在候选成功前先修改 active 状态；
- Win32 相关改动继续执行 release 交叉构建；
- native 与 WASM 会话都必须验证 `publish -> presented/rejected`；只有 `presented` token
  可以进入下一次 `AppFrameInput`；
- 需要真实 surface/present 的行为，必须保留对应平台验收，不以 portable test 代替；
- 静态搜索必须确认旧事件 crate、双栈交互类型、字段双发和字符串业务解析均未重新出现。

## 11. 业界依据

本文采用的不是单一框架模型，而是各框架中与 Tela 边界相符的部分：

- DOM/W3C：事件路径、capture-target-bubble、消费和默认行为；
- React：声明式 handler、逻辑树传播、组件状态和 portal 的逻辑归属；
- Vue：组件显式 emit，组件内部细节不自动成为全局事件；
- Flutter：原始 pointer 与语义 gesture 分层、gesture arena 竞争；
- Android：父级 interception、触摸流接管和嵌套容器消费；
- Compose：modifier 驱动的局部交互、raw pointer 与高层 gesture 分层、nested scroll；
- MFC/AppKit：命令路由和 responder chain 与原始 UI 事件分离。

Tela 的实现不能照搬这些框架的对象模型，因为 Tela 没有长期存活的原生 Widget 树；
所有路径、目标和组件 owner 都必须绑定到候选/已呈现帧及其提交事务。

## 12. 非目标

本阶段不做以下事情：

- 不在 Core 内引入通用 Signal、响应式数据库或 HTTP client；
- 不为所有事件增加全局订阅总线；
- 不把所有连续输入强行转换成冒泡事件；
- 不在 render 阶段启动不可回滚的网络或宿主副作用；
- 不为了保留旧字符串路由而牺牲 typed command 和组件边界；
- 不在没有真实应用需求前冻结 bridge 的强制取消 wire protocol；
- 不把树拍平当作独立事件模型，拍平只改变索引存储。

本文后续的任何 API 设计、组件实现和应用改动，都必须先回答：该行为属于输入、交互、
组件 Output、Command、状态还是 Effect；如果无法回答，就不能继续把它加入某个通用
`Action` 枚举。
