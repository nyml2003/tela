# 036-事件系统与组件生命周期机制

> 状态：开发基准稿。
>
> 本文是 Tela 后续事件系统、组件状态和生命周期实现的权威约束。它替代此前以
> `UiAction`、`EventRegistry`、`BindId` 和 key 路由为中心的讨论稿。现有实现与本文
> 不一致的部分，按迁移计划逐步收敛；不得为了兼容旧实现而继续扩大旧模型。

## 1. 设计结论

Tela 采用**基于已呈现帧的、类型化的、分层事件系统**。

事件系统不使用一个万能事件枚举，也不使用全局字符串事件总线。运行时必须明确区分：

1. 平台输入事实：宿主观察到的指针、键盘和文本输入；
2. Kernel 交互事实：命中、捕获、手势竞争、焦点、滚动和模态规约的结果；
3. 组件局部事件：组件根据交互事实处理自己的私有状态；
4. 组件 Output：组件向父级暴露的有限语义结果；
5. 应用 Command：按钮、菜单、快捷键和组件 Output 汇聚后的业务入口；
6. 应用状态与 Effect：业务模型变更和宿主/网络/桥接副作用。

核心关系是：

```text
AppFrameInput
  -> Kernel 交互规约
  -> 当前帧的 InteractionEvent
  -> 组件局部 handler
  -> ComponentOutput
  -> AppCommand
  -> 应用状态与 Effect
  -> 候选帧
  -> present 成功后提交
```

每一层只拥有自己的状态和副作用。下层可以是函数式状态转换，上层可以持有长期状态，
但不得跨层直接访问对方的所有者。

## 2. Tela 的不可变核心约束

事件系统必须服从 Tela 已经确立的运行时边界，而不是反过来改变这些边界：

- `AppFrameInput` 必须携带输入所针对的已呈现 `AppFrameToken`；旧帧输入不得进入新帧命中
  或组件状态处理；
- `UiTree -> resolve -> UiFrame` 是纯投影，`resolve` 不读时钟、随机数、宿主对象或
  业务 Signal；
- `ViewStateStore` 由 Core 持有焦点、滚动、指针会话等视图交互状态；它不是业务 Store；
- 组件 owner 持有组件实例的私有跨帧状态；候选帧状态只能在成功提交后替换 active 状态；
- 应用 Signal/Store 持有业务状态；业务状态不写入 `UiNode` 或 Core 的全局运行时；
- present 失败、surface 丢失或候选帧被丢弃时，不得部分提交状态、Output、mount 或 unmount；
- 宿主只负责平台生命周期、输入标准化、Effect 执行和帧呈现，不解释组件内部事件。

这意味着事件处理不是“收到动作后随便修改全局状态”，而是一次有帧来源、有所有者、有
提交边界的状态转换。

## 3. 运行时分层

### 3.1 平台输入层

平台 Target 将平台事件转换为 ABI 可传输的输入事实：

- 指针的 id、设备类型、阶段、位置、按钮和时间戳；
- 物理键、修饰键和重复标记；
- 受控文本值、输入焦点、提交、取消和 IME composition 阶段。

Target 不提前合成 `Click`、`Scroll` 或业务命令。多指、指针捕获、手势识别、嵌套滚动
和焦点路由由 guest Kernel 处理，保证 WebView、Win32、macOS、Android 和 iOS 共享同一
交互语义。

### 3.2 Kernel 交互层

Kernel 对一次输入执行显式状态转换：

```text
(UiTree, UiFrame, ViewStateStore, Input)
  -> (ViewStateStore', KernelInteraction[])
```

Kernel 负责：

- 命中测试和当前帧的 `NodeId` 解析；
- pointer capture 和 pointer session；
- gesture recognizer 竞争与胜者选择；
- nested scroll 的增量消费；
- 焦点迁移和焦点作用域；
- Modal/Teleport 的输入边界；
- 键盘导航、激活和文本输入目标；
- 由这些机制产生的视图状态变化。

Kernel 不负责：

- 解释 `command.*`、`folder.open.2` 等业务字符串；
- 更新应用模型；
- 调用 bridge、HTTP、线程、窗口或定时器；
- 直接读取或写入 Signal；
- 为组件构造闭包回调。

新的权威概念是 `KernelInteraction`，而不是继续扩张 `UiAction`。在迁移完成前，可以
由适配层把现有 `UiAction` 转换为该概念；新模块不得增加新的业务型 `UiAction` 变体。

### 3.3 当前帧交互索引

组件树构建时同时生成三类帧计划：

- `InteractionIndex`：`NodeId`、交互能力、组件实例和事件槽的映射；
- `LogicalPathIndex`：逻辑父级、组件边界和传播路径；
- `LifecyclePlan`：本帧出现的组件实例、状态类型和 Effect 作用域。

这些计划只属于候选帧。输入只能查找已呈现帧的计划，候选帧未提交前不能成为输入来源。

### 3.4 组件运行时层

组件运行时根据 `KernelInteraction` 找到最近的组件实例，执行局部 handler：

```text
(active owner, local event)
  -> (candidate owner, Consumed | ComponentOutput | CommandIntent)
```

组件 handler 可以：

- 修改组件私有状态；
- 消费事件，阻止继续传播；
- 发出有限的、声明过的 `ComponentOutput`；
- 产生一个待提交的 `EffectIntent`。

组件 handler 不可以：

- 修改应用模型的其他字段；
- 直接操作宿主窗口或渲染器；
- 直接调用 bridge 或 HTTP；
- 把组件内部搜索词、临时选择、拖动中间值广播到全局；
- 捕获一个会跨帧失效的 `NodeId` 或宿主对象。

### 3.5 应用命令层

应用只处理 typed command。组件 Output、快捷键、菜单和宿主命令可以映射到同一个应用
Action/Command，应用只维护一套 reducer 分支。

Command 的查找采用有限的 owner/responder scope：

```text
当前组件 owner
  -> 祖先组件 owner
  -> 当前窗口 scope
  -> 应用 root
```

这是命令路由，不是 UI 事件冒泡。未处理的命令可以继续向上，最终被丢弃并记录诊断；
不得回退为字符串解析。

## 4. 事件交付策略

事件按交付策略分类，而不是按“所有动作都能绑定”处理。

### 4.1 连续流：捕获、竞争和消费

适用事件：

- 原始 pointer move；
- 拖动和 splitter；
- 长按、缩放、旋转等手势；
- 文本 composition；
- 滚轮和触控板滚动增量。

规则：

- pointer down 确定候选目标和可捕获组件；
- pointer capture 后，后续流直接送到捕获 owner，不逐次沿祖先冒泡；
- 同一指针上的多个 recognizer 通过 gesture arena 竞争；
- nested scroll 传递未消费的剩余增量，而不是向所有祖先广播；
- 文本编辑流留在当前输入组件，提交/取消时才折叠为语义事件；
- 连续流可以有只读观察者，但观察者不能隐式获得业务修改权。

### 4.2 语义事件：逻辑树传播

适用事件：

- Activate；
- Submit；
- Select；
- Dismiss；
- Cancel；
- 一次完成的拖放或手势结果。

这些事件沿逻辑树执行：

```text
capture -> target/component -> bubble
```

事件上下文至少包含来源帧、目标 `NodeId`、当前逻辑节点、传播阶段和消费状态。

组件边界优先于应用边界：组件可以在 target 阶段消费内部事件并产出 Output；未消费的
事件才允许继续向逻辑父级传播。组件 Output 不自动重新作为内部事件广播。

### 4.3 状态通知：状态投影而非命令

适用状态：

- focus gained/lost；
- hover entered/left；
- pressed/selected；
- scroll position；
- IME composition 状态。

这些状态由 `ViewStateStore` 或组件 owner 保存，并通过下一帧投影外观。应用只有在明确
声明观察关系时才收到通知，不得在应用入口无条件 match 所有机制状态。

### 4.4 Command：独立的业务路由

按钮、菜单、快捷键、窗口标题栏和组件 Output 可以产生同一个 typed command：

```text
Button Activate ─┐
Menu Selection  ─┼─> AppCommand
Shortcut        ─┘
```

Command 不携带 UI `SemanticKey`，也不通过 `NodeId` 解析业务对象。动态业务对象必须
携带明确的领域 id 或类型化 payload。

## 5. 身份和地址模型

以下概念禁止混用：

| 概念 | 生命周期 | 唯一职责 | 禁止用途 |
|---|---|---|---|
| `NodeId` | 当前帧 | 命中和帧内索引 | 跨帧状态、业务命令 |
| `SemanticKey` | 跨帧 | 焦点、滚动、布局缓存、Teleport 锚点 | 事件地址、命令名 |
| `ComponentInstanceId` | 组件实例 | owner 状态、生命周期、Effect | 节点命中、业务字段名 |
| `EventSlot` | 当前帧 | 类型化事件绑定索引 | 全局字符串路由 |
| `CommandId`/应用 Action | 业务生命周期 | 应用命令语义 | UI 结构身份 |
| `FieldBinding` | 上层模型 | 可选的外部字段目标 | Core 机制事件路由 |

`SemanticKey` 只服务跨帧状态保持。静态节点默认使用自动路径身份；动态集合使用业务
实体 id；禁止为了事件路由新增 `command.*`、`grid-row-*` 之类的 UI key。

组件实例身份由 DSL 根据调用点、组件类型和动态集合 key 生成。应用不再手工创建或持有
`ComponentIdentity`。

Teleport 必须同时记录：

- 视觉父链：用于布局、绘制和命中；
- 逻辑父链：用于事件传播、组件 owner 和 provide/inject。

树拍平只能改变这些父链和索引的存储形态，不能改变它们的语义。

## 6. 受控值和状态所有权

新的权威边界如下：

```text
Core:       TextInput { node_id, edit }
Component:  InputChanged / SearchChanged / SelectionChanged
Application: Signal / Store / Reducer
```

Core 不再以 `BindId + ValueChange` 作为业务变更中心。现有 `BindId` 可以在迁移期作为
适配层，把旧输入映射到组件 Output 或应用 Action；新组件不得依赖字符串 `BindId` 作为
事件地址。

如果通用表单在应用迁移中证明需要直接绑定外部字段，再在 DSL/组件套件层增加类型化的
`FieldBinding`。该类型必须：

- 不进入 Core 的业务事件协议；
- 不复用 `SemanticKey` 或 `CommandId`；
- 在 DSL/组件边界完成类型检查；
- 能在候选帧失败和组件卸载时安全丢弃旧更新。

Signal 适合应用级、跨组件或异步源驱动的状态；组件普通私有字段由 owner 持有，不要求
所有状态都升级为 Signal。`provide/inject` 表达逻辑树上的有限作用域，不是全局状态总线。

## 7. 组件生命周期和 Effect

生命周期采用以下阶段：

| 阶段 | 时机 | 允许做的事 | 不允许做的事 |
|---|---|---|---|
| setup | 实例首次出现 | 创建/恢复 owner、声明依赖和 Effect 需求 | 依赖候选帧一定会提交的外部副作用 |
| render | 每次候选帧 | 读取 Props/State/Context，生成节点和事件计划 | 写状态、调用宿主、发请求 |
| handler | 交互到达时 | 更新候选状态、消费事件、产生 Output/EffectIntent | 直接提交应用或宿主副作用 |
| mount | 实例首次成功提交后 | 启动已声明的 Effect、申请需要已就位的资源 | 在候选帧失败时执行 |
| unmount | 实例从成功提交的树中消失后 | 取消/失效 Effect、释放订阅和资源 | 因候选帧失败提前执行 |

Effect 绑定 `ComponentInstanceId + generation`。第一阶段可以只实现“卸载标记 + 代际号”
的逻辑取消：回调到达时检查作用域是否仍 active；后续再增加 bridge 的真实 cancel。

Effect、组件状态和 Output 都必须经过候选提交边界：

- 候选帧失败：全部丢弃；
- present 成功：原子提交 owner、Output 和生命周期集合；
- 提交后：启动 mount Effect，应用消费已提交 Output；
- 实例消失：先提交新树，再执行 unmount 清理。

## 8. `ui!` 和组件包装层

`ui!` 是声明语法，不是事件运行时。它负责生成：

- 逻辑树和 children 关系；
- 节点交互能力声明；
- 类型化 `EventSlot`；
- 组件实例和动态集合身份；
- `InteractionIndex`、`LogicalPathIndex` 和 `LifecyclePlan`。

`ActionTarget` 如果继续保留，只能是绑定语法的表面形式，编译结果必须进入统一的
InteractionIndex；它不能拥有独立的字符串 EventRegistry。

组合包装层位于 `tela-ui-dsl` 和 desktop/mobile kit 之间：

- kit 只负责视觉节点和基础交互能力，不依赖 DSL runtime；
- wrapper 负责 Props、owner State、局部 Event、Output 和 DSL 计划；
- 应用只使用 wrapper 和 `ui!`，不接触 owner、候选帧内部结构或节点事件表；
- 纯展示组件不强制创建 owner；只有声明私有状态、局部 handler 或 Effect 的组件才创建
  实例运行时。

## 9. 迁移策略

迁移允许 breaking change。兼容层只服务迁移，不得成为新功能的依赖。

### 阶段 A：冻结旧入口

- 停止新增 `EventRegistry`、字符串 route、业务型 `UiAction` 和 `BindId` 使用；
- 将旧 headless event stack 放入明确的 legacy 适配模块；
- `ActionTarget` 只保留 DSL 表面，不再增加独立路由语义；
- 应用层新增代码只使用 typed Output/Command。

### 阶段 B：建立新 KernelInteraction 和帧索引

- 将原始输入、Kernel 机制和语义交互拆开；
- 建立基于已呈现帧令牌的 InteractionIndex 和 LogicalPathIndex；
- 为连续流实现 capture/gesture/nested-consumption；
- 为离散语义事件实现逻辑路径传播；
- 保持 `resolve` 和交互规约的纯函数测试。

### 阶段 C：迁移所有组件

所有组件都迁移到同一套 owner/handler/Output 规则，不保留“新 DSL 组件”和“旧 headless
组件”两套长期契约。

迁移重点：

- Transfer：验证内部搜索、临时选择、最终提交 Output；
- Slider：验证连续 pointer/gesture 与提交值的边界；
- WindowsTitleBar：验证窗口命令和视觉 hover 状态分离；
- Input/Dialog/Select/Table/Pagination：验证文本流、提交、取消、模态和动态集合；
- ScrollView/VirtualList：验证滚动消费、状态保持和列表重排。

### 阶段 D：迁移所有应用

当前应用全部迁移，不保留长期双栈：

- `speed-gear`：作为新 DSL 和组件 Output 的干净纵向样本；
- `win32-editor`：验证窗口命令、设置表单和多页面局部状态；
- `mobile-demo`：验证移动输入、列表和触摸手势；
- `desktop-demo`：最后迁移复杂模态、文件列表、快捷键和旧字符串路由，作为完整压力
  样本。

迁移完成后删除 legacy EventRegistry、旧 `UiAction` 业务分支、字符串 intent 解析和
旧 BindId 业务映射，而不是继续维护兼容分支。

## 10. 开发验收标准

### 10.1 语义验收

- App 入口只处理 typed Command、组件 Output 和明确声明的状态观察；
- Scroll、Focus、Modal、Pointer capture 等机制不需要应用手工 match；
- 同一业务动作可以由按钮、快捷键和菜单进入同一个 reducer 分支；
- 组件内部搜索词、临时选择和拖动状态不会出现在全局应用事件中；
- Teleport 命中按视觉树，传播和 provide/inject 按逻辑树；
- 未绑定事件被安全忽略，不回退为字符串解析。

### 10.2 帧和生命周期验收

- 旧 `AppFrameToken` 输入不能修改当前 active owner 或 ViewStateStore；
- 候选帧失败不触发 mount/unmount，不覆盖 active owner；
- render 重复执行不会产生副作用；
- setup 对同一实例只执行一次；
- 实例卸载后旧 Effect 回调被丢弃；
- 列表重排按业务 key 保留状态，换 key 或换组件类型创建新实例；
- provide/inject 在惰性 children 展开时遵守逻辑作用域。

### 10.3 性能验收

- 连续 pointer/gesture 流不为每个样本创建完整祖先传播链；
- pointer capture 后事件直接进入 active recognizer/owner；
- 离散事件使用预计算逻辑路径，不扫描全树和解析字符串；
- 命中目标使用帧内整数索引，状态保持使用独立 SemanticKey；
- 新事件绑定不引入全局锁、全局事件总线或宿主对象捕获。

### 10.4 工程验收

- Core、DSL runtime、每个 kit 和每个应用都有对应的单元/集成测试；
- `speed-gear`、`win32-editor`、`mobile-demo`、`desktop-demo` 全部通过统一事件路径；
- Win32 相关改动继续执行 release 交叉构建；
- 需要真实 surface/present 的行为，必须保留对应平台验收，不以 portable test 代替；
- legacy adapter 的使用点可通过静态搜索定位，并随着应用迁移逐步减少到零。

## 11. 业界依据

本文采用的不是单一框架模型，而是各框架中与 Tela 边界相符的部分：

- DOM/W3C：事件路径、capture-target-bubble、消费和默认行为；
- React：声明式 handler、逻辑树传播、组件状态和 portal 的逻辑归属；
- Vue：组件显式 emit，组件内部细节不自动成为全局事件；
- Flutter：原始 pointer 与语义 gesture 分层、gesture arena 竞争；
- Android：父级 interception、触摸流接管和嵌套容器消费；
- Compose：modifier 驱动的局部交互、raw pointer 与高层 gesture 分层、nested scroll；
- MFC/AppKit：命令路由和 responder chain 与原始 UI 事件分离。

Tela 的实现不能照搬这些框架的对象模型，因为 Tela 没有长期存活的原生 Widget 树；
所有路径、目标和组件 owner 都必须绑定到候选/已呈现帧及其提交事务。

## 12. 非目标

本阶段不做以下事情：

- 不在 Core 内引入通用 Signal、响应式数据库或 HTTP client；
- 不为所有事件增加全局订阅总线；
- 不把所有连续输入强行转换成冒泡事件；
- 不在 render 阶段启动不可回滚的网络或宿主副作用；
- 不为了保留旧字符串路由而牺牲 typed command 和组件边界；
- 不在没有真实应用需求前冻结 bridge 的强制取消 wire protocol；
- 不把树拍平当作独立事件模型，拍平只改变索引存储。
