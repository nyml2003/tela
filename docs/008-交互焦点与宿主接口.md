# 008-交互焦点与宿主接口

## 1. 输入能力

| 输入 | 能力 |
|---|---|
| 鼠标 | 点击、移动、滚轮、悬浮 |
| 键盘 | 按键、文本输入、输入法、剪贴板复制粘贴 |

输入事件从宿主进入，经命中测试定位到节点，最终输出类型化动作抛回宿主；**UI 内部不执行业务行为**。

交互层**只消费 `interact` 维度**（`InteractConcern`，见 [003-场景树与节点模型](003-场景树与节点模型.md)）：可点/可悬停/可聚焦/输入/模态都在该槽位声明，布局与绘制不读取它们。

```
宿主输入事件
  → 命中测试（HitRegion 携带预合并 clip + 滚动坐标换算 + 模态拦截）
  → 焦点图转移 / 动作生成（规约式，不依赖布局）
  → UiAction 抛给宿主执行
```

## 2. 焦点系统：规约式状态转移

> 决策：彻底抛弃基于控件屏幕坐标、距离计算的空间四向跳转。整套焦点系统完全建立在**组件树 + 规约式状态转移**之上，不保留空间导航作为逃逸选项。

两套焦点模型可在界面中共存，共享同一棵焦点作用域树：

| 模型 | 导航方式 | 适用 |
|---|---|---|
| PC 模型 | Tab / Shift+Tab 沿组件树序切换；输入框光标、选区操作 | 浏览器、桌面 |
| 主机模型 | 方向键沿焦点图转移；确认、取消 | 游戏主机手柄 |

### 2.1 核心原理

焦点依附组件树节点；**方向键跳转不走屏幕几何计算**。焦点系统是一棵以可聚焦节点为顶点的有向图（焦点图），边的生成与遍历全部建立在组件树关系上：

```
焦点图 G = (V, E)
  V：组件树中的可聚焦节点（由 interact 维度声明）
  E：输入按键 → 下一焦点节点，由三级规约生成
转移：next(focus, input) -> Option<FocusTarget>   // 纯函数，不读布局结果
```

**焦点身份默认由 core 维护**

当前焦点以跨帧稳定的 `semantic_key` 存在 `ViewStateStore`，并在每帧映射到临时 `node_id`。普通组件只声明可聚焦性和树结构，不传 `focus_key`：

- 默认 `auto-path` 覆盖顺序稳定的常规 UI；
- 动态但非虚拟的集合可声明 `auto-stable-identity`，稳定身份仍由 core 分配；
- 动态集合分子组件可在自身项目边界声明该策略，并以稳定结构语义帮助 core 区分同形项；它不生成或暴露实际 key；
- 虚拟列表等离屏 item 需要跨销毁/重建随业务实体保持的场景，或 core 无法可靠推导同一实体身份的特殊集合，业务复用实体 ID 提供 `semantic-id`；
- 业务显式焦点规约表达“下一步去哪”，不表达“当前节点的焦点 key 是什么”。

这保证约八成页面不需要接触焦点身份，同时不牺牲虚拟化和高级身份场景。具体 key 策略见 [005-key身份策略](005-key身份策略.md)，状态仓库见 [004-更新策略与状态保持](004-更新策略与状态保持.md)。

### 2.2 焦点转移规约的三级来源与解析

三个来源（按覆盖度由低到高）：

1. **标准容器自动生成**：列表、ScrollView、Stack 等容器根据子项顺序自动生成本地焦点转移规则（上/下/左/右 → 相邻子项），业务不用逐个配置。**自动规则只生成容器内部项间边**。网格容器焦点逻辑属未来扩展（Grid 首版不支持，见 [006-布局引擎](006-布局引擎.md) 1）。
2. **默认树关系（含边界穿越默认回退）**：普通页面依靠组件树父子（进入/离开）、兄弟（切换）关系完成焦点进出，零配置。容器边界处（首项再往前 / 末项再往后）方向键**没有显式边时，自动抛回父作用域**，父作用域按**树序**解析下一个可聚焦目标（兄弟节点 / 下一个容器的入口），父组件零配置。该解析不读布局、树序静态可推导，且容器不指名兄弟、不破坏封装。
3. **业务显式规约**：自由艺术排版页面，由业务显式书写局部跳转规约（禁用跳转、强制指定落点），用代码直接表达设计意图。需要精确控制边界行为（如 2D 栅格视觉序 ≠ 树序）时，用显式边 + 方向化 entry/exit 端口（见 2.9）覆盖默认回退。

**解析规则（替换覆盖语义）**：

- 对同一 `(当前焦点节点, 输入指令)`，若声明了**显式跳转规则**，则直接**替换**该按键对应的所有自动生成规则——容器内部自动边、容器边界默认回退逻辑**全部失效**，保证单输入对应**唯一跳转目标**，消除多候选歧义。
- 仅当**无匹配显式规约**时，才依次执行：容器自动跳转 → 容器边界默认回退。
- 该解析是静态的：给定树 + 焦点图，任一 `(节点, 输入)` 的目标唯一可推导，不依赖布局。

### 2.3 按键语义

- 确认：触发当前焦点节点的主动作。
- 取消：**语义固定为沿组件树向上回退**（到父/祖先焦点组），不按空间方向。**终止条件分两种**：
  - 焦点在模态子树内 → 取消**先关当前模态**，焦点回到打开该模态时保存的位置；
  - 否则 → 沿树回退到最近焦点组出口。
- 弹窗/模态层天然和组件树层级绑定：焦点进入模态子树后，图外节点不可达。

### 2.4 为什么完全舍弃空间导航

空间导航本质是**运行时启发式算法，属于非确定模型**。即便愿意写补丁代码，也无法根除模型层面的固有缺陷：

| 缺陷 | 说明 |
|---|---|
| 布局扰动带来隐性 bug | 像素级布局改动可能悄悄改变跳转结果 |
| 跨组件边界难以约束 | 空间最近邻会窥探子组件内部控件，破坏组件边界 |
| 无法静态分析 | 跳转依赖渲染结果，不能离线推导、测试、录制回放 |
| AI 操控不方便 | 无法直接枚举合法下一焦点，只能模拟按键猜屏幕位置 |

### 2.5 收益

- 焦点转移行为**可静态推导，不依赖布局渲染结果**：可单元测试、状态导出、录制回放；布局改动不会悄悄破坏导航。
- 严格维护组件边界隔离：父组件只与子组件的**入口、出口契约**打交道，不窥探子组件内部控件。
- 业务规则优先级最高：禁用跳转、强制指定落点等逻辑是显式规约，不需要黑名单补丁。
- 适配 AI 操控 UI：直接枚举合法下一焦点，不用模拟按键猜屏幕位置。

### 2.6 代价与约束

- 团队约束：**视觉排版顺序尽量对齐逻辑焦点顺序**，避免"视觉上某个控件就在该方向，但按键跳不过去"造成用户困惑；框架提供开发期检查告警辅助该约束（见 [005-key身份策略](005-key身份策略.md) 的开发期检测）。
- 框架基建成本：列表、ScrollView、Stack 等基础容器需完整实现内部焦点转移的生成逻辑，属框架一次性投入。

### 2.7 反模式提醒

不等于要求所有页面手写庞大的全量状态转移矩阵。标准容器自动生成大部分规则，只有跨组件边界、自由布局场景才需要补充少量显式规约。

### 2.8 设计

- 焦点作用域树（`FocusScope`）标记可聚焦节点与导航分组，是焦点图生成的基础。
- 每个作用域声明适用的焦点模型；模型只影响"焦点如何移动"，不改变可聚焦节点集合。
- `FocusModel` trait 抽象转移策略，PC 与主机各一个实现：
  - PC：组件树序的线性 Tab 序，支持文本光标/选区操作。
  - 主机：方向键沿焦点图边转移，确认/取消固定语义。
- 同一棵焦点树可同时被两个模型驱动（页面同时支持键盘与手柄）。
- **焦点转移是纯函数**：`next(focus, input)` 不读取布局、不读取时钟，可离线复现（与 [003-场景树与节点模型](003-场景树与节点模型.md) 的纯操作保证一致）。
- 焦点状态存于视图状态仓库，随 key 匹配在帧间保持。

### 2.9 FocusScope entry/exit 端口契约

把 2.5 提到的"入口/出口契约"从概念升级为**构建期静态约束**：若父焦点图可直接连子 `FocusScope` 内部节点，就会击穿组件封装——子组件内部焦点节点重构会直接损坏上层焦点逻辑。

#### 端口定义（方向化）

- **entry 方向端口**：外部焦点按方向 D 打入当前 `FocusScope` 时落地的内部目标节点，等价 modal default-focus / autoFocus。`entry_up`/`entry_down`/`entry_left`/`entry_right` 分别绑定各方向的进入落点。
- **exit 方向端口**：本 Scope 按方向 D 发生焦点逃逸（Esc、Shift+Tab、关闭陷阱）时向外部输出焦点跳转源，等价 restore-focus 语义。`exit_up`/`exit_down`/`exit_left`/`exit_right` 分别绑定各方向的逃逸出口源。
- **方向无关简写**：无方向修饰的 `entry`/`exit` = 四方向绑定同一节点（模态弹窗这类与方向无关的组件）。
- **方向 = 按键方向（键身份）**，不是屏幕几何——与"无空间导航"一致（见 2.4）。

> 重要区分：`entry`/`exit` 是 Scope 的**对外逻辑端口**，不是真实焦点节点；端口绑定 Scope 内部真实焦点 id。方向化端口主要服务**主机方向键模型**；PC Tab 模型按线性序落点（默认 `entry` 或 Scope 内首个可聚焦）。

#### 解析顺序

- **进入**（`A -> child.entry_*`）：按进入方向 D 匹配 `child.entry_D` → 无则默认 `entry` → 无则 Scope 内首个可聚焦。
- **逃逸**（`child.exit_* -> B`）：父作用域按逃逸方向 D 查 `child.exit_D` 的连线 → 无则**默认回退**到父作用域按树序解析（见 2.2）。

#### 精简条文

> 复合组件的 `FocusScope` 应声明方向化 `entry`、`exit` 端口，实现焦点的封装隔离。
> 1. `entry_*`：外部焦点按方向进入本 Scope 的接入点，绑定 Scope 内部焦点 id；方向无关的 `entry` 等价四方向同绑；可为 null。
> 2. `exit_*`：Scope 按方向逃逸的逻辑出口，绑定 Scope 内部焦点 id；方向无关的 `exit` 等价四方向同绑；可为 null。
> 3. 静态约束：父 Scope 的 `focus_graph` **禁止直接引用子 Scope 内部节点 ID**，仅允许连接子 Scope 的方向化 `.entry_*`、`.exit_*`。
> 4. Scope 内部的 `focus_graph` 可自由引用内部全部焦点节点。
> 5. 提供 `unsafe_internal_ref(...)` 作为逃逸口子，编译通过但产生 Linter 警告，仅限特殊高级场景。
> 6. 约束仅作用于声明式焦点图；命令式焦点调用依靠编码规范约束。

#### 最佳实践

- ✅ 每个具备封装语义的复合组件（弹窗、下拉、自定义面板），其根 `FocusScope` 显式声明 `entry`、`exit`（方向无关简写即可）。
- ✅ 需要方向精确的容器（列表/ScrollView）声明方向化端口：`entry_down`→首项、`entry_up`→末项、`exit_down`→末项、`exit_up`→首项。
- ✅ `entry_*`、`exit_*` 只能绑定**本 Scope 内部**焦点节点 ID，禁止跨 Scope 绑定。
- ✅ 父组件焦点图跨 Scope 跳转只使用 `child_scope.entry_*` / `child_scope.exit_*`，绝不写子内部原始 id。
- ✅ 若组件无明确唯一入口（普通非锁定面板），允许端口为 null；无逃逸场景允许 `exit_*` 为 null。
- ✅ 当 `entry_*` 绑定的节点动态销毁：运行时降级，回退到该方向次选 / Scope 内首个可聚焦节点。
- ❌ 禁止父 `focus_graph` 直接写 `to="@dialog.confirm_btn"` 穿透访问子内部 id。
- ⚠️ 万不得已要穿透时，使用 `unsafe_internal_ref("@dialog.confirm_btn")`，产生 Linter 警告，记录技术债务。
- ✅ 嵌套 FocusScope：子 Scope 本身作为父 Scope 内部节点，子 Scope 的方向化端口是父 Scope 合法的连线目标。
- ✅ 即使开启虚拟列表，`semantic-id`、FocusScope 端口契约互不替代，各司其职。

#### 伪代码示例

子组件封装弹窗（方向无关简写，对外只暴露端口，不暴露内部按钮 id）：

```
component ConfirmDialog(visible: bool) {
    FocusScope(id="confirm_dialog_scope",
        entry="@confirm_btn", exit="@cancel_btn", contain=true, when=visible) {
        Button(id="confirm_btn", label="确认")
        Button(id="cancel_btn", label="取消")
        Input(id="remark_input", placeholder="备注")
        focus_graph {          // 内部自由引用
            @confirm_btn -> @cancel_btn;
            @cancel_btn -> @remark_input;
            @remark_input -> @confirm_btn;
        }
    }
}
```

容器方向化端口示例（列表：从上方进入落首项，从下方进入落末项）：

```
component MenuList(items) {
    FocusScope(id="menu_list_scope",
        entry_down="@item1", entry_up="@item_last",   // 方向化入口
        exit_down="@item_last", exit_up="@item1") {   // 方向化出口
        // items...
    }
}
```

父组件合法写法（只连方向化端口）：

```
component AppPage {
    Button(id="open_dialog_btn", label="打开弹窗")
    ConfirmDialog(id="my_dialog", visible=...)
    MenuList(id="menu")
    Button(id="save_btn", label="保存")
    focus_graph {
        @open_dialog_btn -> my_dialog.entry;      // ✅ 打入子入口（方向无关简写）
        my_dialog.exit -> @open_dialog_btn;       // ✅ 接收子的出口逃逸
        @open_dialog_btn -> menu.entry_down;      // ✅ 向下进入列表，落首项
        menu.exit_down -> @save_btn;              // ✅ 列表下向逃逸接续
    }
}
```

非法写法（静态编译报错，禁止穿透）：

```
focus_graph {
    @open_dialog_btn -> @my_dialog.confirm_btn;   // ❌ 击穿封装
}
```

逃逸口子（Linter 警告，记技术债务）：

```
focus_graph {
    @open_dialog_btn -> unsafe_internal_ref("@my_dialog.confirm_btn");  // ⚠️ WARN
}
```

> 伪代码中的 `focus_graph`/`@id`/`.entry_*` 在实现期映射为 Rust builder API 等价表达，本文档保留伪代码便于说明语义。

#### 运行时行为语义

1. `A -> child.entry_D`：将焦点推入 `child` FocusScope，按方向 D 解析落点（`entry_D` → 默认 `entry` → 首个可聚焦）；绑定节点销毁/不可聚焦时运行时降级到次选，不崩溃。
2. `child.exit_D -> B`：`child` Scope 内沿方向 D 发生焦点逃逸（Esc / shift-tab / 关闭陷阱）触发该连线，将焦点交给 B；`exit_D` 仅定义**逃逸源逻辑点**，不强制必须聚焦 exit 绑定的那个内部节点。
3. 容器边界处方向键无显式边时：**默认回退**到父作用域按树序解析（见 2.2）。
4. entry 绑定节点被销毁：不崩溃，运行时自动降级，不修改静态 DSL。

### 2.10 Teleport 焦点迁移与 tab_index（决策）

**Teleport 焦点规则（对齐 Flutter Overlay）**：Teleport 的子节点，**焦点遍历链跟随目标渲染位置（ModalHost），脱离原始逻辑树**。

- 逻辑树：Teleport 子节点依然保留原始父子关系，上下文、语义、生命周期继承来源节点；
- **焦点遍历链重挂载**：Teleport 输出子树加入目标 Scope（ModalHost）的焦点遍历序列，不再参与原父 Scope 的 Tab 遍历；
- Tab 顺序：多个 Teleport 按插入 ModalHost 的渲染顺序参与 Tab，视觉上浮层可正常 Tab 进入、Tab 退出；
- **语义树（semantics）保留原始位置**：只修改键盘 Tab 导航链，屏幕阅读器语义结构不被破坏（对齐 Flutter OverlayPortal 取舍）。

**DrawOrder 与焦点边界（绘制层级 ≠ Tab 导航顺序）**：

- DrawOrder 只改变绘制、命中测试的视觉 z 序，**完全不改动焦点遍历**；
- 同一父 Scope 内即使提升 `InnerTop` 视觉层级，Tab 遍历仍维持原逻辑树顺序；
- 想改 Tab 顺序用独立原语 `tab_index`（`InteractConcern` 上的整数，`-1` 移出 Tab 序列）；
- 避免一套参数同时控制渲染与键盘导航，语义解耦（业界统一原则：绘制层级 ≠ 键盘 Tab 导航顺序）。

**FocusTrap（焦点陷阱，底层最小原语）**：

- core 不内置完整 FocusTrap 逻辑；底层仅提供 `FocusScope.trap_focus: bool`：
  - `trap_focus=true`：Tab 遍历**不离开本 Scope**；到达首项 Shift+Tab 回绕到末项，到达末项 Tab 回绕到首项；
- ESC 拦截、点击外部关闭、自动聚焦首项、关闭后恢复焦点，全部由上层 `tela-widgets` 封装 `FocusTrap` 组件（业务交互策略不属于底层遍历内核）。

**保存/恢复焦点契约**：

- 底层提供两个动作：`UiAction::SaveFocus`（保存当前焦点 node_id 入 ViewStateStore）、`UiAction::RestoreFocus`（恢复上次保存的焦点）；
- **不做自动隐式恢复**：弹窗/下拉组件在上层显式调用（打开前 Save、关闭后 Restore）；
- 焦点迁移（打开下拉自动聚焦列表第一项）在上层组件完成，core 只响应"请求聚焦某 node_id"指令。

**边界总结**：

| 场景 | 行为规则 |
|---|---|
| 普通节点 Tab | 按 FocusScope 内逻辑树深度优先遍历；DrawOrder 不影响 Tab 顺序；可用 `tab_index` 调整 |
| Teleport 子树 | 渲染到 ModalHost，焦点链迁移至 ModalHost Scope；原树不再遍历该子树；生命周期/上下文保留来源节点 |
| `trap_focus=true` | Tab/Shift+Tab 在 Scope 内循环，不能跳出；不处理 ESC、点击外部 |
| 局部 DrawOrder | 仅改变绘制、命中测试；**完全不改动焦点遍历** |
| 弹窗关闭回焦点 | 底层 Save/Restore 原语；上层组件显式调用，不自动隐式恢复 |

```rust
// 下拉组件内部，上层 tela-widgets
Dropdown(
    trigger = Button("打开下拉"),
    content = Teleport(
        target = ModalHost,
        child = FocusScope(trap_focus = true, children = menu_items),
    ),
)
// 打开时：SaveFocus()，请求聚焦菜单第一项；
// 关闭时：RestoreFocus() 回到触发按钮。
```

### 2.11 键盘输入、意图与运行时键位表（D54，✅ 自动化验收完成，画布验收待确认）

**核心原则：按键、映射和意图是三层不同的模型**

- `RawKeyboardEvent` 描述平台观测到的物理键、修饰键、按下/释放和 repeat；
- `KeymapSnapshot` 由宿主/应用保存，负责把 `KeyCombo` 翻译为 `KeyboardIntent`；
- `KeyboardIntent` 描述 UI 意图：焦点前进/后退、方向移动、确认、取消或 `Invoke(ShortcutId)`；
- core 只消费已经解析的 `KeyboardIntentEvent`，按既有焦点图规约并输出 `UiAction`；它不保存用户配置、不读取 JSON、不做键盘布局转换。

物理键来自平台物理代码，例如浏览器 `KeyboardEvent.code`，并归一化为 USB HID 数值的 `PhysicalKey`。可打印文本和 IME 组合态不经快捷键映射，而是继续走文本输入通道；不再存在以 `Key::Char` 表示物理组合键的运行时接口。

**键位表所有权与作用域**

- 键位表归宿主/应用层；完整、校验通过的不可变 `KeymapSnapshot` 才能替换当前表；
- UI 树中的逻辑容器只声明 `KeymapScopeId`，不保存 `KeyCombo -> ShortcutId` 映射；
- 应用按当前焦点的作用域路径查询键位表：最近作用域优先，逐层向父作用域回退，最后查询应用默认层；
- Teleport 和 ModalHost 仍使用焦点树上的实际作用域链，绘制顺序不参与解析；
- 同一层内的重复组合键是配置错误；替换失败时必须保持旧表不变。

```text
平台 RawKeyboardEvent
  -> 应用 KeymapSnapshot（当前 KeymapScopeId 路径）
  -> KeyboardIntentEvent
  -> core 焦点图 / UiAction::ShortcutActivated
  -> 应用 Controller 或宿主业务
```

`FocusNext`、`FocusPrevious`、`MoveFocus`、`Activate` 和 `Cancel` 由 core 的纯焦点规约处理；`Invoke(ShortcutId)` 只产生语义动作，保存、关闭、撤销等业务副作用仍在上层。方向焦点移动允许长按 repeat；确认、取消和业务快捷键默认忽略 repeat。

**全局与文本例外**

- 不受 UI 焦点约束的浏览器或平台命令由宿主在应用键位表之前处理，不进入 core；
- 画布宿主在键位表命中非文本 UI 意图时同步阻止浏览器默认行为，尤其是 Tab；
- 隐藏 textarea 只承担文本、`beforeinput` 与 IME；组合期间不得把可打印键转成快捷键；
- Esc 只解析为 `Cancel` 或 `Invoke(ShortcutId::Escape)`，关闭模态的业务规则仍由上层实现。

**实施状态**

`RawKeyboardEvent` 仅在应用层键位表中出现；`tela-core::InputEvent::Keyboard` 只消费 `KeyboardIntentEvent`。`ShortcutScope` 只声明 `KeymapScopeId`，不再保存静态映射。文件管理器的 `application/keymap.rs` 支持校验后的 JSON 整表替换；CPU 与 WGPU 浏览器入口都归入同一个 `App::handle_raw_key`。完整落点、测试和画布人工验收项见 [020-字体基线焦点与键盘意图实施目标](020-字体基线焦点与键盘意图实施目标.md)。

## 3. 嵌套模态弹窗

- 弹窗栈（modal stack）管理多层模态；页面/模态栈作为**独立顶层子树**（ModalHost），栈顶子树天然全局最上，与树序堆叠一致。
- 模态弹窗**拦截下层界面输入**：命中测试只对栈顶模态及其内容生效，下层不响应。
- 关闭当前模态后栈弹出，下层恢复响应；焦点回到被打开时保存的位置。
- **取消键在活动模态内优先关模态**：只要 modal stack 存在，`Cancel` 先关闭栈顶模态；即使宿主尚未投影首个模态焦点或旧背景焦点仍短暂存在，也不会穿透到页面。关闭后的业务动作和显式 `RestoreFocus` 仍由上层完成。
- **悬浮层（Teleport）点击外部**：基座命中 portal 外部区域时仅抛 `UiAction::TeleportClickOutside(teleport_node_id)` 事件，**不内置关闭规则**——关闭逻辑完全交由宿主业务实现（适配编辑器、模态、普通页面差异化需求）；上层 Dropdown/Tooltip 组件套件封装通用"点击外部关闭"逻辑，降低业务样板代码。
- 模态属于视图状态（弹窗开关），不进业务数据；弹窗的开关意图作为 `UiAction` 抛给宿主执行。

## 4. 平台能力边界（不是通用 `Host` trait）

核心不执行业务、IO、网络、存储，但这不意味着所有平台能力必须塞进一个公共 trait。不同平台实际需要的组合差异很大：浏览器有隐藏文本编辑器和 DOM IME，Win32 有 HWND、消息循环和 GPU surface，离线渲染没有窗口或输入。把它们抽象为一个巨型 `Host` 会把不存在的能力和生命周期强加给每个适配方。

因此，平台 SDK 在最外层使用**场景所需的窄通道**：输入适配把平台事件翻译成应用事件；帧消费把 `UiFrame` 交给具体 renderer；剪贴板、IME、时钟和资源加载只在真正需要它们的组件/应用边界出现。`tela-contract` 继续持有纯数据类型，`tela-core` 不获得平台对象。

原生 WASM 应用采用 `tela-app-abi` 的版本化包协议：SDK 向 guest 派发 `AppEvent`，读取 `UiFrame` 与 `AppStatus` 的序列化结果。该协议不是替代 core 的内部接口，也不把 HWND、DOM 或业务 Store 泄漏进 WASM；详细的包格式和 Win32 开发流程见 [023-平台SDK与WASM开发包](023-平台SDK与WASM开发包.md)。

- `UiAction` 是类型化交互指令：点击、输入、焦点移动、滚动、弹窗开关、**悬浮层点击外部（`TeleportClickOutside(teleport_node_id)`）**、**业务值变更（`ValueChange(BindId, Value)`）**、**焦点保存/恢复（`SaveFocus`/`RestoreFocus`）**等，宿主决定业务行为。`ValueChange` 是唯一业务变更通道，`BindId` 由 `InteractConcern` 声明、core 仅透传标识不读写业务数据；纯视图动作（滚动/模态/焦点）不带 `BindId`，走 `node_id` 链路（见 [012-业务数据绑定](012-业务数据绑定.md)）。
- 剪贴板/IME 是宿主能力：核心把"需要复制/粘贴/组合输入"的意图传给宿主，宿主落地，不反向依赖平台。
- 时钟由宿主注入，保证核心可离线确定性复现（PRD 七-1 与 003 的纯操作保证）。

## 5. 规则

- 🔧 交互动作一律以 `UiAction` 抛给宿主，核心内无业务副作用。
- ✅ 交互只消费 `interact` 维度，不读取 `layout`/`visual`。
- ✅ 焦点系统为组件树 + 规约式状态转移，**禁止任何形式的屏幕空间几何导航**。
- ✅ 焦点转移是纯函数（`next(focus, input)`），不读取布局、时钟，可静态推导。
- ✅ 取消键语义固定为沿组件树向上回退；焦点在模态子树内时**先关当前模态**，否则回退到最近焦点组出口；模态层与组件树层级绑定。
- ✅ 业务显式规约采用**替换覆盖语义**：对同一 `(节点, 输入)` 存在显式规约时替换所有自动规则（内部自动边 + 边界默认回退失效），保证单输入唯一目标；无显式规约才走自动跳转 → 默认回退。
- 🔧 双焦点模型共享焦点作用域树，模型只决定转移策略，不改变可聚焦节点集合。
- ✅ 容器边界穿越默认回退父作用域按树序解析（父零配置、静态可推导、不破坏封装）。
- ✅ 端口为方向化：`entry_*`/`exit_*` 按方向绑定，方向无关 `entry`/`exit` 等价四方向同绑；进入按方向解析落点。
- ✅ 父 `focus_graph` 禁止引用子 Scope 内部节点 ID，仅允许连接方向化 `.entry_*`/`.exit_*`（构建期静态检查）。
- ✅ `unsafe_internal_ref` 逃逸口子产生 Linter 警告，仅限特殊高级场景并记录技术债务。
- 🔧 `entry_*`/`exit_*` 只能绑定本 Scope 内部焦点 id；entry 绑定节点销毁时运行时降级到该方向次选/首个可聚焦节点。
- 🔧 端口契约约束仅作用于声明式焦点图；命令式焦点调用依靠编码规范。
- ✅ Teleport 子树焦点遍历链迁移至目标 Scope（ModalHost），原树不再遍历该子树；semantics 保留原始位置（见 2.10）。
- ✅ 绘制层级 ≠ Tab 导航顺序：DrawOrder 不改焦点遍历；Tab 顺序用 `tab_index`（-1 移出序列）独立调整。
- 🔧 `trap_focus` 仅做 Scope 内 Tab/Shift+Tab 循环；ESC、点击外部、自动聚焦、关闭恢复属上层 `FocusTrap` 封装。
- ✅ `SaveFocus`/`RestoreFocus` 为显式原语，无自动隐式恢复；焦点迁移由上层发起、core 响应聚焦请求。
- ✅ 物理键、键位表和键盘意图严格分离：应用把 `KeyCombo` 解析为 `KeyboardIntent`，业务只匹配语义动作。
- ✅ `KeymapScopeId` 只声明 UI 结构；键位映射归宿主/应用，支持完整快照校验与运行时替换，不能存入组件。
- ✅ core 不做键盘布局转换、键位 JSON 或用户偏好；它只按焦点树处理键盘意图。
- ✅ 全局快捷键归宿主/adapter；IME 与文本输入保持独立通道，不能由快捷键映射截获。
- ✅ Esc 映射为 `Cancel` 语义动作；core 对活动 modal 只弹出视图态并输出 `CloseModal`，应用再执行关闭业务 modal 与焦点恢复。
- 🔧 开发期检测：视觉排版顺序与逻辑焦点顺序偏差时告警（对齐约束）。
- 🔧 模态栈拦截下层输入，命中测试只对栈顶生效。
- 🔧 剪贴板、IME、时钟、纹理、字形度量都保留在外层窄通道，核心零平台依赖。
