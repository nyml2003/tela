# 005-key身份策略

## 1. 目标

key 用于跨帧节点匹配、实例复用与视图状态保留（焦点、光标、滚动、选中/展开）。四种策略配置在容器节点，向下生效，子容器可覆盖。目标是**减少业务维护成本**：大多数场景业务不需要为 UI 构造专用 key，也不需要管理焦点 key。

| 策略 | key 来源 | 业务负担 | 适用场景 | 是否全局默认 |
|---|---|---|---|---|
| `auto-path` | 基座按节点树位置索引自动生成 | 零配置 | 顺序固定的静态界面 | ✅ 全局默认 |
| `auto-stable-identity` | 基座首次出现自动分配内部稳定身份 | 不传任何 ID | 动态面板、可拖拽列表（业务无实体 ID） | 否 |
| `semantic-id` | 业务传入业务已有的实体主键 | 复用业务 ID | 虚拟列表及 core 无法可靠推导身份的实体项 | 否 |
| `manual` | 业务完全自行提供 | 全量自管 | 高级兜底，不鼓励日常使用 | 否 |

## 2. 四种策略详解

### 2.1 auto-path（全局默认）

按节点在树中的位置路径（父路径 + 兄弟索引）自动生成 key。

- 优点：零配置，适合顺序固定的静态界面。
- 约束：兄弟节点增删移位会改变 key，导致后续节点被判定为"新节点"而丢失状态。因此**不适用于**动态列表/可排序列表。
- 实现：容器子节点遍历时，路径 = 父容器路径 + 子索引；等价兄弟内容改变不影响 key。

### 2.2 auto-stable-identity

容器内节点首次出现时，基座自动分配内部稳定身份；后续兄弟节点插入、删除、调换顺序，**原有节点 key 保持不变**。业务不需要传入任何 ID。

- 约束与保证：
  - 组件类型变化判定为全新节点，分配新 key（类型是身份的一部分）。
  - 节点销毁后身份可**延迟回收**，避免 ID 无限膨胀。
- 在可拖拽排序、动态增删面板等场景下，状态随内容而非位置保持。
- 集合分子组件可以在自己的动态项目边界声明此策略，例如 `Toolbar` 的条件命令项；它只声明策略，实际 key 仍由 core 分配，页面调用方不传也不保存 key。
- **不适用于虚拟化列表**：离屏 item 不在树中，身份随滚动释放/重建，跨滚动状态必然丢失；虚拟化场景必须用 `semantic-id`（见 2.3）。
- 不做全局默认（它需要内部身份分配器，且对纯静态树有额外开销）。

**身份分配算法（已实现）**：
1. 容器持一个单调递增 `next_id` 与一张"上轮分配表"（路径/指纹 → id）。
2. 首帧：按遍历顺序为每个节点分配 id，记下每个 id 对应的**内容指纹**（类型 + 关键属性哈希）。
3. 后续帧：对每个子节点，先在"上轮分配表"中查找：同位置命中则复用；未命中则扫描可复用 id——取"内容指纹相同且未被本帧占用"的上轮 id 复用（保证类型变化不误复用）；否则分配新 id。
4. 位置移动的节点通过内容指纹匹配复用旧 id，从而在拖拽排序时保持身份与状态。
5. 销毁回收：id 不立即释放，进入回收待定；连续 N 帧未出现且不再被复用时回收，避免 id 无限膨胀。

> 实现覆盖插入、删除、重排、类型切换和销毁回收；回归证据见 [`m4_identity_state.rs`](../crates/tela-core/tests/m4_identity_state.rs)。

### 2.3 semantic-id

业务把已存在的实体主键作为身份提示传入，基座据此生成 key。

- 业务仅复用已有业务 ID，不需要为 UI 构造专用 key。
- 适合数据驱动列表、表格：行增删排序时状态随实体 ID 保持。
- **虚拟列表容器强制要求** item 显式 `semantic-id`，无默认身份语义；业务手动管理全量数据，虚拟列表只负责可视区渲染。
- 同一容器内 semantic-id 重复 → 构建期校验报错。

### 2.4 manual

业务完全自行提供 key，基座只负责校验唯一性与匹配。

- 用于极端自定义场景（如跨容器共享身份、复杂的合并单元格）。
- 日常不鼓励：把身份责任完全交还给业务，违反"减少业务维护成本"的目标。

### 2.5 焦点身份的默认责任

焦点 key 不是组件 API，也不是业务状态。`tela-core` 负责两个层面：

1. `UiTree` 按当前容器的 key 策略生成 `semantic_key`；
2. `ViewStateStore` 用该 key 保持、重映射和回收当前焦点。

因此，普通页面、表单、工具栏、树和非虚拟化动态面板不应传入“焦点 key”：

- 顺序稳定的普通 UI 使用全局默认 `auto-path`；
- 有增删、拖拽或重排但没有可靠业务实体 ID 的非虚拟集合，声明 `auto-stable-identity`，稳定身份仍由 core 分配；
- 组件可以根据自己拥有的稳定结构语义（例如 Toolbar 的命令绑定）辅助 core 区分同形项目，但不得构造、缓存或向业务暴露 tela key；
- 虚拟列表等 item 会离屏销毁、之后又按数据实体重建的场景，或 core 无法可靠推导同一实体身份的特殊集合，业务复用已有实体 ID 作为 `semantic-id`；
- `manual` 只留给跨容器共享身份等高级例外，不得作为日常焦点保持手段。

这是一条默认优先的策略：目标是让约八成常规 UI 只声明可聚焦和正常节点结构，其余身份、当前焦点和跨帧保持均由 core 处理。

## 3. 开发期检测与提示

开发环境（`tela-debug` feature 或调试宿主）自动检测并输出显性提示，把隐性错误转成显性：

- 同一容器内 key 重复 → 告警。
- 在虚拟列表容器上使用非 `semantic-id` 策略（auto 系列）→ 告警/报错。
- `semantic-id` / `manual` 在结构不稳定的容器上使用，而 `auto-stable-identity` 更合适 → 提示。
- 在顺序不稳定的列表上误用 `auto-path` → 提示改用 `auto-stable-identity` 或 `semantic-id`。
- 在非虚拟普通组件上显式传入焦点身份 → 提示移除，交由默认策略或 `auto-stable-identity`。
- 更新策略在连续帧间频繁翻转 → 提示（见 004-5）。

## 4. 状态保持协同

- 同一 key 新旧树匹配 → 视图状态仓库中的槽位复用。
- 新 key → 分配新状态槽；key 消失 → 状态延迟回收。
- 命中区域与视图状态都按 key 稳定，因此拖拽/重排后焦点、光标、滚动、选中仍跟内容走。
- **与 FocusScope 端口契约各司其职**：`semantic-id`/`auto-stable-identity` 负责**跨帧身份与状态保持**（数据与视图状态归属），FocusScope `entry`/`exit` 负责**焦点封装隔离**（谁可以打进/逃出组件）。两者互不替代：虚拟列表 item 仍需显式 `semantic-id`，不会因端口契约免除；端口契约也不提供身份保持能力。

## 5. 规则

- ✅ `auto-path` 为全局默认。
- ✅ 当前焦点和默认焦点身份由 `tela-core` 的 `UiTree`/`ViewStateStore` 维护；常规组件不管理 `focus_key`。
- ✅ key 在容器内唯一，重复由构建期校验拦截。
- ✅ `auto-stable-identity` 类型变化即新身份；销毁后延迟回收，防 ID 膨胀；不适用于虚拟化列表。
- ✅ 虚拟列表必须显式 `semantic-id`，无默认身份语义。
- 🔧 开发环境自动检测重复 key 与策略误用，输出显性提示。
- 🔧 `manual` 不鼓励日常使用，仅在高级场景兜底。
