# 026-架构迭代宪章

> **状态：🟡 第一批边界已实现，能力 Lock 仍是后续工作。** 本文定义 Tela 的迁移判据、目标地图与近期约束。
> 002 继续描述既有总体分层；本文记录新增 `DefaultApplicationProfile`、中性 Guest Runtime、独立移动
> Guest 和 Android Target 后的架构裁定。
>
> 本文不是“大而全插件系统”的设计承诺。实现只在真实移动需求证明边界之后发生，不引入每帧动态
> 分发、反射、万能 `Host` trait 或运行时插件 ABI。

## 1. 要解决的不是“再抽象一次”，而是重新获得控制

Tela 已有 Win32、macOS、WebView 三种真实目标端。问题不在于 crate 数量，而在于新增代码
逐渐难以回答以下问题：

1. 一个应用究竟选择了哪些能力，为什么会依赖它们？
2. 一个目标端究竟原生承诺了哪些能力，哪些只是当前某个 renderer 或 SDK 的实现细节？
3. 一段跨端代码应该共享实现、共享协议，还是根本不应共享？
4. Android、iOS、游戏或未来终端的需求应该落在哪个责任域，怎样避免污染普通业务页面？

本宪章建立的不是运行时控制器或万能 Host trait，而是一个构建、打包和架构审查阶段可见的
**控制面**：

- World Map 说明代码的责任归属与依赖方向；
- 应用与目标的 Manifest / Lock 在真正需要多能力选择时说明兼容关系；
- 迁移台账说明已有 crate 的真实位置、风险和下一次验证机会；
- 复用判据阻止“为了未来”提前造抽象。

这些信息不进入每帧运行路径，不以虚调用、反射或动态插件 ABI 换取可扩展性。

## 2. 根本判据：按不变性决定复用单位

> **绝对一致 → 复用代码；语义一致 → 复用协议；概念一致 → 只共享抽象边界。**

| 不变性层级 | 允许的复用方式 | 约束 |
|---|---|---|
| 绝对一致 | 同一 crate 中复用实现 | 两处必须真的使用同一段代码；不能靠平台分支维持“共享” |
| 语义一致 | 共享类型化协议、数据模型或 ABI | 每个目标端保留自己的生命周期、适配和实现 |
| 概念一致 | 只共享命名、边界或问题定义 | 不建立 trait、端口或公共 crate，直到出现可验证的共同语义 |

由此导出以下规则：

1. 共享域中出现 if macOS、if Win32、if Android、if terminal 等目标行为分支，即说明共享边界
   选错。目标专属 crate 可以拥有目标专属代码；共享 crate 不能借条件分支伪装通用。
2. 先实现，再抽取。第二份真实实现出现前，不因“看起来会复用”而创建通用 runtime、资源协议
   或插件接口。
3. 物理目录是已稳定责任域的投影，不是预测未来的草图。没有必要为了新地图立即搬迁全部 crate。
4. 一个框架可以提供默认能力组合，但不能限制直接 Rust 库 API 访问更低层能力。

## 3. 当前事实基线

下表只记录当前代码已能验证的事实。Android 只代表第一份移动实现；它不自动证明 iOS、TUI 或游戏
可以复用同一段宿主代码。

| 事实 | 当前证据 | 架构含义 |
|---|---|---|
| tela-contract 与 tela-core 承担节点、布局、更新、焦点、交互和 UiFrame 语义 | crates/tela-contract、crates/tela-core | 它们构成 Kernel，但不应认识 renderer 或目标平台 |
| `DefaultApplicationProfile` 显式拥有默认布局 cache、resolve、焦点与输入组合 | tela-core/src/profile.rs、tela-demo/src/application/runtime.rs | 默认 Kernel 组合在应用装配处可见，但没有虚调用或运行时替换 |
| Win32 与 macOS 共用 tela-native-sdk-runtime | tela-win32-sdk、tela-macos-sdk、tela-native-sdk-runtime | 这是桌面缓存和生命周期共享，不等于“所有 native”都应复用它 |
| `tela-guest-runtime` 只拥有 Wasmtime guest、无窗口 verifier 与严格远程 bundle 校验 | tela-guest-runtime | 它不认识窗口、surface、IME、缓存或任一 Target SDK；Android 只复用这一中性执行语义 |
| Android 有独立 `tela-android-sdk`、`tela-mobile-demo` 与 `tela-mobile` bundle channel | crates/tela-android-sdk、crates/tela-mobile-demo、ops | 移动页面、模拟领域和 Activity 生命周期均不从 desktop demo 或桌面 runtime 继承 |
| WebView 的 JS 半边自行处理 DOM 生命周期、rAF、IME 和输入 | tela-webview-sdk/web | WebView 与桌面共享 ABI 或帧渲染时，不应因此被塞进同一 GUI 循环 |
| tela-render-wgpu、tela-render-raster、tela-render-canvas 消费 UiFrame，而不依赖 tela-core | 各 renderer Cargo 依赖 | renderer 是独立的 Presentation provider，而不是 Kernel 的下游业务层 |
| 现有 .tela Manifest 只含 ABI、WASM 与资源信息 | tela-bundle/src/manifest.rs | 它尚不包含应用能力 Lock，不能被误认为已经是通用能力包格式 |
| IconProvider 目前只有 Material 实现，上层仍直接消费 IconName | tela-icon、tela-ui、tela-demo | 图标语义与 Material provider 尚未完全分层；这是一项待真实需求验证的迁移点 |
| FrameSink、ResourceAdapter 缺少真实多实现和生产消费者 | tela-contract、tela-resource-protocol | 它们是候选或遗留抽象，不能作为未来插件体系的地基 |
| ComponentRuntime 仍在 tela-demo 内 | tela-demo/src/application/reactive.rs | 它是框架实验，不应在没有第二个应用前被宣布为通用 runtime |

当前架构的主要风险是：把桌面同构外推成全平台同构，把单实现接口当成成熟扩展点，或让 bundle、
renderer、host 与业务应用的职责混成一个“跨端层”。

## 4. Tela World：两条正交的组织轴

### 4.1 横向执行链

    直接 Rust API / DSL / 可选企业框架
                    ↓
            应用装配与组件组合
                    ↓
    Primitive → Atomic → Molecular → Business
                    ↓
        Kernel：布局 / 更新 / 焦点 / 交互
                    ↓
          UiFrame 与资源、视觉语义
                    ↓
             Renderer provider
                    ↓
    Target Host：循环 / 表面 / 输入 / IME / 生命周期

输入和动作沿反向链路返回：Target Host 适配平台事件，Kernel 处理焦点与交互，应用控制器或状态
驱动下一次更新。Renderer 不拥有应用循环；Target 不定义业务交互。

### 4.2 一级、二级、三级责任目录

| 一级域 | 二级域 | 三级能力与职责 |
|---|---|---|
| Kernel | Contract | 节点、样式、约束、脏标记、焦点、输入、动作、帧语义 |
| Kernel | Engine | 树解析、布局、更新、焦点、交互；由 Application Profile 整体选择 |
| UI Capability | Primitive | Box、Text、Image、Icon 等语义原语；可选 Sprite、Tile、Scene 等领域原语 |
| UI Capability | Atomic | Button、Input、Checkbox、Scrollable 等带稳定交互契约的组件 |
| UI Capability | Molecular | FormField、SearchBox、Menu、Dialog、Table 工具单元等组合组件 |
| UI Capability | Business | CRUD、工作台、行业组件，以及游戏 HUD、场景等领域封装 |
| Presentation | Renderer | WGPU、Canvas、Raster 与未来 renderer；只消费帧与本地视觉能力 |
| Presentation | Visual / Resource Provider | 文字测量与绘制、字体、图标、图片、纹理等实现 |
| Target | Host | 各端独立的 GUI 循环、表面、坐标、输入、IME、生命周期与资源接入 |
| Application | Composition | 直接 Rust API、DSL 前端、MVC 组合、可选状态管理与路由框架 |
| Control Plane | Capability Resolution | 应用与目标 Manifest、Lock、严格匹配报告 |
| Control Plane | Delivery | bundle、ABI、开发分发与其它交付方式；不把任一格式设为唯一应用模型 |

Primitive → Atomic → Molecular → Business 是 UI 能力的依赖层级。通用 UI、企业、游戏等则是可选
**能力域**，可跨越这些层级贡献实现。游戏不是与 CRUD 竞争的一条横向主链：未被应用选择时，
它不应进入普通业务应用的依赖闭包。

每个组件能力应表达自身的语义状态、输入与动作、布局或渲染需求；它不能直接依赖某个目标端的
窗口 API、DOM API 或 renderer 私有对象。

### 4.3 不预设无条件成立的 std

Tela 不需要在第一期先定义“所有端都必须支持的 std 组件集”。一个默认能力集只是某个应用、
发行版或框架显式选中的能力包组合。能力 Lock 尚未实现，当前由 crate 依赖、应用根部选择和
`ops check` 的依赖方向规则提供第一层可见性；不能因为名称中带 std 就假定跨端可用。

## 5. Application Profile 与能力选择

### 5.1 Application Profile

Application Profile 只选择一整组 Kernel 算法：布局、更新、焦点与交互必须作为相互一致的组合
出现，不能在应用运行中被若干能力包零散替换。

第一期已经将当前默认组合显式命名为 `DefaultApplicationProfile`，并由应用装配处可见地选择：

- 不提前定义 ApplicationProfile trait；
- 不引入 trait object、动态注册或运行时插件加载；
- 保留当前默认行为和调用兼容性；
- 当第二份真实 Profile 出现时，再以其与默认 Profile 的共同点决定抽取代码或协议。

游戏等领域若确实需要不同的 Kernel 行为，应提供完整 Application Profile，并由应用根部选择。
它不能在普通页面运行过程中按组件替换某一个内核算法。

### 5.2 能力 Manifest、Lock 与严格匹配（尚未实现）

目标模型如下：

    应用 Manifest ──解析──> 应用能力 Lock
    目标 Manifest ──解析──> 目标能力 Lock
    两个 Lock    ──匹配──> 原生满足 / 不兼容 / 缺失 + 诊断

应用 Manifest 只声明直接选择的能力包与 Application Profile。解析器计算传递能力闭包，编译阶段
负责发现代码使用了未声明能力的情况。目标 Manifest 声明目标 Host、Renderer、视觉或资源 provider
实际能原生提供的能力。

第一期的匹配规则刻意收窄：

- 仅处理稳定能力标识、直接依赖、传递闭包和严格匹配；
- 目标构建时发现缺失或不兼容，应给出明确诊断并拒绝激活该目标产物；
- 通用开发 bundle 在加载时也应再次匹配；
- 不处理版本求解、多版本共存、自动降级、替代内容或能力回退。

能力版本、回退策略和包管理分发形式可能在后续出现，但它们不是当前架构成立的前提。

### 5.3 bundle 与 ABI 的边界

现有 `.tela` 与 `tela-app-abi` 是一种已支持的动态应用交付协议，常用于开发。Android 的第一份
实现证明了**严格远程 bundle 校验与 Wasmtime 执行**可共享：它使用 `tela-guest-runtime`，但不使用
桌面 `tela-native-sdk-runtime` 的缓存、CLI 或生命周期。此证据不规定所有应用、所有 Target 都必须
采用 WASM、bundle 或同一个 loader。

## 6. Target 原则：平台循环不做伪统一

Target 域拥有完整的目标端生命周期、窗口或视图、表面、坐标变换、输入与 IME 接入。Win32、
macOS、WebView、Android、iOS 从一开始都是独立实现；是否共享代码只能由后续真实实现证明。

近期移动端策略：

1. Android 是第一份移动端证据：`GameActivity`、Winit、Vulkan/WGPU、触摸、原生 IME 和系统 Back
   均留在 `tela-android-sdk`。
2. Android 不复用 `tela-native-sdk-runtime`；它仅复用中性 `tela-guest-runtime` 的严格远程加载与
   Guest ABI 语义，且没有 cache fallback。
3. `tela-mobile-demo` 是独立移动 Presentation 与独立静态 mock domain，不是 `tela-demo` 的 CSS 或
   条件编译分支。
4. iOS 独立预留，不预先创建“mobile runtime”；Android 与 iOS 都存在后，再对照真实实现裁定代码、
   协议或边界的复用层级。

Renderer 与 Target Host 也保持分离：同一 renderer 可以在多个目标中复用，只要代码确实相同；
但 renderer 的可复用性不推导出 GUI 循环和生命周期的可复用性。

TUI 只作为一个架构反证题，不进入近期路线图：若未来接入它必须修改既有共享 crate、在共享代码
加入终端分支，或把 GUI 假设写回 Kernel，则应重新审视能力边界。

## 7. 当前 crate 的迁移台账

| 当前对象 | 目标责任域 | 当前结论与下一次验证机会 |
|---|---|---|
| tela-contract、tela-core、DefaultApplicationProfile | Kernel | 保持平台无关；默认 Profile 已显式化，不提前泛化算法接口 |
| tela-text、tela-icon、tela-widgets、tela-ui | UI Capability / Presentation | 逐步分清语义原语、组件与视觉 provider；不因单一 Material 实现立刻拆包 |
| tela-render-* | Presentation | 保持只消费 contract / UiFrame 的方向；未来 renderer 以真实 provider 身份加入 |
| tela-win32-sdk、tela-macos-sdk、tela-native-sdk-runtime | Target（桌面） | 限定为桌面缓存/生命周期共享，不升级为通用 native 或 mobile runtime |
| tela-guest-runtime | Delivery execution | Wasmtime、严格远程校验和无窗口 verifier；禁止依赖任何 Target SDK |
| tela-android-sdk、android/ | Target（Android） | GameActivity、Vulkan surface、触摸、IME、Back；不静态链接业务 Guest |
| tela-mobile-demo | Application（mobile） | 独立移动页面和 mock domain，通过 `tela-mobile` channel 动态交付 |
| tela-webview-sdk | Target（WebView） | 保持 WebView 自己的 DOM、IME、rAF 与页面生命周期；只在已验证处共享协议或实现 |
| tela-app-abi、tela-bundle | Control Plane / Delivery | 继续作为动态交付能力，不推导为唯一应用运行模型 |
| tela-demo | Application | 保留为应用与框架实验；第二个真实应用出现前不抽取通用 ComponentRuntime |
| FrameSink、tela-resource-protocol、单实现 IconProvider | 候选边界 | 不为“消灭孤儿”而复活或扩大；等待生产消费者和第二实现 |
| ops 架构检查 | Governance | 保持现有门禁；新域出现稳定依赖模式后，再从真实 Cargo 图提炼通用规则 |

## 8. 近期迁移约束

近期工作按以下顺序推进：

1. 维护本宪章与现状台账，所有新增平台或能力先在地图上定位。
2. 功能优化和 Android 实现按真实需求推进；只抽取已经被重复验证、且不需要目标分支的部分。
3. `DefaultApplicationProfile` 已落地；下一份真实 Profile 出现前不抽象 trait。
4. Android Target、mobile bundle channel 与架构门禁已落地；下一步只在真实多能力应用出现时评估
   Manifest/Lock。
5. 物理目录迁移仅随着稳定边界发生；不进行一次性全工作区搬迁。

以下事项明确不属于近期工作：

- 不实现运行时动态插件 ABI；
- 不实现完整包管理、版本求解或多版本共存；
- 不实现自动降级与回退语义；
- 不创建 universal Host、ShellDriver 或跨 Android/iOS 的 mobile runtime；
- 不因为只有一个实现就复活资源协议、FrameSink 或其它候选抽象；
- 不将 TUI 变成近期平台任务；
- 不修改 002 来把目标架构伪装为当前事实。

## 9. 变更评审清单

任何后续架构相关变更都应在评审中回答：

1. 该代码属于 World Map 的哪个一级、二级、三级域？
2. 它是应用直接选择的能力，还是某项能力的传递实现？
3. 它与已有实现是绝对一致、语义一致，还是仅概念一致？
4. 若要共享，是否能保证共享代码没有目标行为分支？
5. 若要新增协议，是否已有两个真实实现和一个明确消费者？
6. 若涉及目标端，生命周期、输入、IME、表面和资源责任是否仍留在目标域？
7. 若涉及应用交付，是否错误地把现有 bundle / ABI 推定为唯一运行模型？

## 10. 暂缓但应持续记录的问题

1. 能力包的标识命名、Manifest wire format 与 Lock 的持久化格式。
2. 能力版本、兼容区间和多版本选择策略。
3. 严格匹配稳定后，自动降级应由目标端、能力契约还是应用侧以何种方式表达。
4. `tela-mobile-demo` 之后的第二个移动应用是否足以证明可抽取的移动组件或 DSL 边界。
5. iOS 出现后，哪些移动端语义值得抽取为协议。
6. 目录名称和 crate 粒度；只有稳定责任域才能决定其最终物理投影。

这些问题不应阻塞当前功能优化或 Android 的第一份真实实现；它们的答案必须来自实现证据，而不是
提前写入通用抽象。
