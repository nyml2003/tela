# 022-构建产物与浏览器宿主目录

> **状态：✅ 已实现。** 本文定义浏览器宿主源码、Rust wasm 工件和静态发布目录的物理边界。

## 1. 结论

仓库不再使用 `demo/`。浏览器与原生开发 SDK 的文件都按可编辑源码与可删除产物严格分离：

```text
crates/tela-demo/             Rust 文件管理器场景与 wasm 导出
crates/tela-app-abi/          WASM guest 与平台壳共享的版本化数据包
crates/tela-bundle/           bundle 格式与完整性校验
crates/tela-win32-sdk/        Win32 开发壳源码
crates/tela-macos-sdk/        macOS AppKit/Metal 开发壳源码
crates/tela-native-sdk-runtime/ 可复用 bundle/Wasmtime/lifecycle runtime 源码
web/
├── public/                   可编辑的静态页面模板
└── src/                      可编辑的浏览器宿主与 raw WebGPU 诊断逻辑
ops/
└── src/infrastructure/       Node wasm 冒烟验证与静态服务适配器
dist/                         Git 忽略；仅允许构建产物
```

`dist/` 不承载源码、文档、手写脚本或独立实验 crate。删除整个目录后，项目必须能仅通过受控
构建命令恢复全部内容。

## 2. 产物组成与来源

完整构建后，`dist/` 的每项都有唯一来源：

| `dist/` 项 | 来源 | 生成者 |
| --- | --- | --- |
| `index.html` | `web/public/index.html` | `web/build.mjs` |
| `rawgpu.html` | `web/public/rawgpu.html` | `web/build.mjs` |
| `assets/tela-web/app.js` 与 source map | `web/src/main.ts` | esbuild |
| `assets/tela-web/rawgpu.js` 与 source map | `web/src/rawgpu.ts` | esbuild |
| `tela_demo.wasm` | `crates/tela-demo` CPU wasm | `ops build demo` |
| `tela_demo_gpu.js`、`_bg.wasm`、`.d.ts` | `crates/tela-demo` 的 `webgpu` wasm | wasm-bindgen |
| `tela-dev/tela-demo.tela` | `tela-demo` 的 `app-wasm` + `assets/` | `ops build bundle` |
| `tela-dev/latest.json` | 上述 archive 的 SHA-256、ABI 和 URL | `ops build bundle` |
| `win32/tela-win32-sdk.exe` | `crates/tela-win32-sdk` GNU Windows target | `ops build win32` |
| `macos/Tela.app/Contents/Info.plist` | `crates/tela-macos-sdk/resources/Info.plist` | `ops build macos` |
| `macos/Tela.app/Contents/MacOS/tela-macos-sdk` | `crates/tela-macos-sdk` aarch64 macOS target | `ops build macos` |

浏览器宿主始终从发布根加载 wasm：CPU 是 `/tela_demo.wasm`，GPU glue 是
`/tela_demo_gpu.js`。因此 `ops serve` 只需以 `dist/` 作为静态根，无需路径重写。

## 3. 构建与所有权

`ops build all [--gpu]` 是默认发布组合入口：它先删除并重新创建由工作区路径模型推导出的
`dist/`，随后依次发布 CPU wasm、可选 GPU glue、前端 bundle 和 `tela-dev` 开发包。这样完整构建不会
留下上一次构建的陈旧文件。`ops build win32` 仍是单独的显式目标，因为它依赖 GNU Windows 交叉工具链。

单目标构建不清空 `dist/`：

- `ops build demo` 只写 CPU wasm；`ops build demo --gpu` 只写 GPU glue；
- `ops build frontend` 只重建 `assets/tela-web/` 并复制两个 HTML 模板；
- `ops build bundle` 只写 `tela-dev/`，先完成临时 archive，再原子发布 `latest.json`；
- `ops build win32` 只写 `win32/tela-win32-sdk.exe`，应用内容不被嵌入 exe；
- `ops build macos` 只在 Apple Silicon macOS 写 `macos/Tela.app`，应用内容不被嵌入 App；
- `ops verify gpu` 会先执行前端构建，保证 `rawgpu.html` 与其 bundle 同步，然后只打印 URL 并等待
  人工打开页面上报结果；它不启动浏览器；
- `ops verify demo` 通过 `ops/src/infrastructure/wasm-smoke.ts` 加载发布 wasm，验证首帧、尺寸、
  frame trace 和客户端壳像素分区；`--build` 在 CLI 组合层先执行 CPU 构建。

完整构建是唯一允许重置 `dist/` 的命令。文件系统删除操作经过 `FsPort.resetDir`，且目标只能是
`WorkspacePaths.distDir`，避免构建逻辑散布任意递归删除。

## 4. 删除的遗留边界

历史 `wgpu-mvp` crate 与 `mvp.html` 是一次性诊断对照，不再构成产品或构建路径，已移除。
保留的原生 WebGPU 环境诊断页改为 `web/public/rawgpu.html` + `web/src/rawgpu.ts`：它不经过
`wgpu`，用于区分浏览器/GPU 环境故障和 tela 的 WGPU 渲染路径故障。

## 5. 验收

```bash
ops check
ops build all --gpu
ops build win32
ops build macos # 仅 Apple Silicon macOS
ops verify demo
git check-ignore -v dist/index.html
git ls-files dist
```

最后一条应无输出，说明 `dist/` 没有被版本控制；前一条应显示根 `.gitignore` 的 `/dist/` 规则。
不通过手工复制、编辑 `dist/` 或保留旧 `demo/` 文件来满足验收。
