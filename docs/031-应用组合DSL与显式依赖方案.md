## 0. 阅读关系与实施状态

本文承接 026 的分层、030 的 Headless / Signal / 双 Kit 方案，以及 Kernel 已有的 `UiNode`、
`SemanticKey` 与 `IdentityAllocator`。它补的是 **Application 如何组合这些能力**，不是重写它们。

当前源码已经成立的事实与本文的目标状态必须分开看：

| 主题 | 当前事实 | 本文目标 |
|---|---|---|
| `UiNode` | 纯数据节点；不持有业务回调 | DSL 只构造它和帧期附属计划，不把闭包塞回节点。 |
| `SemanticKey` | `UiTree::new_with_allocator` 校验时才生成；默认策略为 `AutoPath` | 观察订阅在树构建成功后以解析后的 `SemanticKey` 为锚点。 |
| `Signal<T>` | 已归属 `tela-ui-dsl` 的单线程响应式状态 | 保持单线程模型；DSL 只显式登记读取依赖。 |
| `ComponentRuntime` | 已归属 `tela-ui-dsl`，以 `SemanticKey` 建立订阅 | 按帧 reconcile 订阅图，并提供 batch / 唤醒协议；Host 的 active-frame 边界仍由 D9 关闭。 |
| `EventRegistry` | 将已验证来源的 `UiAction` 路由为 `RoutedEvent` / `HeadlessEvent` | 保留其 Headless 合约；D9-B 下 Host 先校验 `FramedUiAction` 的 token，再将内层 `UiAction` 交给它。DSL 原生动作不依赖 Headless。 |
| 应用视图 | desktop 仅迁移了 runtime 观察；mobile Browse 已用 DSL `Signal` / `ActionFrame` 构建，Preview 暂保留 direct-Rust island | 保持 Browse 的回归边界后，再决定是否迁移 Preview 或 desktop。 |

因此，“`@watch` 使用 `SemanticKey`”是当前 DSL runtime 的 API；`ComponentPath` 只保留给 Headless
Root/Part 与事件路由。030 的 Signal 段落已同步改用 `SemanticKey`；两份文档不得再把 `ComponentPath`
并列为当前 `watch` 主键。

### 0.1 非目标

本文明确不做下列事情：

| 不做 | 原因 |
|---|---|
| 把 DSL 下沉到 Kernel | Kernel 只消费纯契约，不认识业务 Action、TypeId Context 或宏语法。 |
| 把闭包、`dyn Fn` 或借用的应用状态放进 `UiNode` | 这会破坏帧重建、快照、跨层值对象和身份复用边界。 |
| 用隐式依赖收集替代 `@watch` | 刷新边界必须在源码中可见、可审计。 |
| 注入 `AppState`、`&mut AppState`、`ComponentRuntime` 或 `Signal` | 状态读写需要显式参数和 ActionHandler；Context 只承载稳定能力。 |
| 提供跨 kit 的通用视觉 `<Button>`、`<SearchInput>` 适配器 | 030 已决定 recipe 留在 kit 内部，不能为 DSL 重新引入跨 kit 视觉抽象。 |
| 承诺局部子树重组 | V1 仍是一旦任一观察项变化便重建应用根帧；key 先用于正确订阅与将来的优化空间。 |
| 用本设计声称现有节点 `Send`、`Serialize` 或性能数据已达标 | 这些不是本文已验证的当前 API 或基准结论。 |

## 1. 要解决的矛盾与总模型

传统 Rust UI 写法常把回调闭包附着在节点上；Tela 的帧架构则要求每帧可以无条件丢弃旧树、构造新树。
两者的共同边界应当是：**视图树只携带数据，行为与订阅都在树外按帧协调。**

应用层形成以下闭环：

1. `AppState` 持有业务数据与 `Signal<T>`；渲染函数以不可变方式读取它。
2. `ui!(build { ... })` 展开为普通 Rust 构造代码，产出 `ViewOutput<A>`：其中只有纯 `UiNode` 会进入 Kernel，
   本帧的 `WatchPlan` / 动作绑定则由私有 `PlanBundle<A>` 随该输出值携带。
3. Kernel 构建 `UiTree`，通过 `IdentityAllocator` 为每个节点解析稳定 `SemanticKey`。
4. 成功的树和暂存计划一起交给运行时协调；运行时以解析后的 key 替换上一帧订阅图。
5. Host 接收一帧调度请求后重建根视图；底层输入由 Kernel 产出 `UiAction`。D9-B 采纳后，Host 用采样时的
   `FrameToken` 将其包装为 `FramedUiAction`，DSL 的帧级动作表才把它转为应用 Action。只有采用 Headless
   组件时，才额外经过 Headless 的事件路由 adapter。
6. `ActionHandler` 获得可变业务状态，更新 `Signal`；下一帧重复该闭环。


## 2. 纯数据树与应用动作

### 2.1 `UiNode` 的硬边界

`UiNode` 只表达布局、视觉、内容、身份与 Kernel 可理解的交互开关。它不得保存：

- 捕获环境的闭包；
- 指向 `AppState`、`ViewBuild`、`Signal<T>` 或 Host 的借用；
- `TypeId` Context；
- `WatchPlan`、订阅句柄或应用动作注册表；
- 任意依赖某一帧栈地址的函数对象。

这不是语法偏好，而是帧边界。树可在本帧构建、由 Kernel 校验、交给 Renderer，随后整体被替换；业务行为与
订阅拥有比树更长的生命周期，必须由外部运行时保存。

### 2.2 Action 是值，不是节点回调

视图里对无输入动作使用枚举值：

~~~rust
enum UserAction {
    Save,
    Delete(TaskId),
    Search(String),
}

ui!(build {
    // 这是纯数据值，不是捕获闭包。
    <ButtonLike action={UserAction::Save} />
})
~~~

`ButtonLike` 和下面的 `InputLike` 仅用于说明动作绑定的目标语义，**不是** V1 要新增的跨 Kit DSL
标签；V1 的真实视觉入口仍是第 6 节中的 kit Rust 表达式。

带输入的组件使用 trigger 明确声明的**不捕获、强类型**映射。V1 的 `on_input` 接收
`fn(String) -> UserAction`：`String` 来自 Kernel 的 `TextInputEvent::Edit`；`on_submit` 同样接收
`fn(String) -> UserAction`，但只响应 `TextInputEvent::Commit`。因此枚举构造器和普通函数项都可直接使用，
并在宏展开时被强制转换为对应的函数指针。映射器及其生成的 Action 不能放入 `UiNode`；它们属于本帧的
应用动作绑定。以下写法是目标语义，而非已实现宏语法：

~~~rust
ui!(build {
    <InputLike on_input={UserAction::Search} />
})
~~~

需要把 item 的稳定纯数据连同 payload 生成 Action 时，使用显式的 `with_context`，而不是捕获闭包：

~~~rust
fn rename(task_id: TaskId, value: String) -> UserAction {
    UserAction::Rename { task_id, value }
}

ui!(build {
    <InputLike on_input={with_context(task.id, rename)} />
})
~~~

`with_context(context, mapper)` 只接受 `context: Clone + Send + Sync + 'static` 的纯值及
`mapper: fn(Context, Payload) -> Action`。它在 `ActionPlan` 外部存放 context 和函数指针；每次分发时克隆
context 并调用 mapper。对直接文本映射，宏只接受路径形态（`ExprPath`），并生成 `fn(String) -> A` 的类型检查；
对带 context 映射，只接受形态受识别的 `with_context(<context 表达式>, <mapper 路径>)` 调用。任意工厂调用、原始
`UiAction` 转换和闭包表达式都不接受。Rust 的语法树无法区分“函数项 / 枚举构造器路径”和同类型的局部函数指针
变量，因此后者在满足相同 `fn` 类型时也会通过；这不形成闭包或回调逃生门。可审计的硬约束是：本帧动作计划中
只能保存函数指针，以及由 `with_context` 封装的纯 context，绝不保存闭包或捕获环境。`action` / `on_cancel` 接受
Action 纯值表达式。

直接 DSL 文本动作与传统 `BindId` 受控字段是**互斥的状态所有权模型**。一个以 `on_input` / `on_submit` /
`on_cancel` 绑定的 input 根必须没有 `bind_id`：其 ActionHandler 负责更新下一帧的受控值。仍使用 `bind_id`
的字段继续走 Kernel / Headless 的 `ValueChange` 协议，不能同时再登记 DSL 文本 action，避免一次 Edit 出现两条
业务写入路径。

业务副作用、异步请求和多项状态修改都在 `ActionHandler` 中执行，而不写进视图树：

~~~rust
impl AppState {
    fn handle(&mut self, action: UserAction, runtime: &ComponentRuntime) {
        match action {
            UserAction::Save => self.save(),
            UserAction::Delete(id) => self.delete_task(id),
            UserAction::Search(keyword) => runtime.batch(|| {
                self.filter.set(keyword);
                self.page.set(1);
                self.loading.set(false);
            }),
        }
    }
}
~~~

这里的 `runtime.batch` 只是要实现的普通 Rust API；`@batch` **不是** `ui!` 指令。

## 3. `ViewBuild` 与显式能力 Context

### 3.1 状态显式、能力注入

`ViewContext` 是每帧构建期的能力作用域，只承载可拥有、稳定、与业务可变状态分离的对象。例如：

- `Theme`、本地化格式化器、权限策略；
- `AppConfig`、只读 feature flags；
- `Arc<ReportApiClient>`、`Arc<dyn Clock + Send + Sync>`；
- 请求追踪 ID、不可变会话描述等 newtype 值。

它不承载 `AppState`、`&mut AppState`、`ComponentRuntime`、`Signal<T>`、UI 树或任何局部可变引用。
视图所需状态必须显式进入函数参数，写操作只能由事件后的 ActionHandler 获得：

~~~rust
fn render_dashboard(
    build: &mut ViewBuild<UserAction>,
    app: &AppState,
) -> ViewResult<ViewOutput<UserAction>> {
    ui!(build {
        // ...
    })
}

fn handle(&mut self, action: UserAction, runtime: &ComponentRuntime) {
    // 只有这里拥有对业务状态的可变访问。
}
~~~

这条规则消除了“在构建树时从 TypeId 表中借出 `&mut AppState`，又递归构建子树”的借用冲突，也保证状态变化
仍从一个可检查的 Action 边界发生。

### 3.2 持久父链，而不是共享可变表

概念上的数据形态如下：

~~~rust
struct ViewContext {
    parent: Option<Arc<ViewContext>>,
    entries: HashMap<TypeId, Arc<dyn Any + Send + Sync>>,
}

impl ViewContext {
    fn child(
        parent: Arc<Self>,
        entries: impl IntoIterator<Item = ProvidedValue>,
    ) -> ViewResult<Arc<Self>>;

    fn inject<T: Send + Sync + 'static>(&self) -> ViewResult<&T>;
}
~~~

这是说明责任的伪 API，不是要求直接采用某个字段名。关键约束是：

1. 每个 `ui!` 块创建一个不可变子作用域，父作用域通过 `Arc` 链接并保持可借用。
2. 子块可遮蔽父块的同类型能力；同一块中重复提供同一个实际 `TypeId` 是构建错误。
3. `@inject` 返回当前块生命周期内的 `&T`，而非把 `Arc<T>` 作为业务 API 泄漏出去。
4. 宏先收集本块的 provide 前导声明，再一次性创建子作用域；不能在渲染过程中修改共享 Context。
5. `ViewBuild::with_scope` 必须在 `Result` 返回和 panic unwind 时恢复父作用域，不能让失败子树污染兄弟节点。
6. 宏必须先把当前 scope 的 `Arc` 克隆到局部变量，再从这个局部变量取得 `&T`；不能让注入引用借自
   `ViewBuild` 本身，否则子视图无法同时拿到 `&mut ViewBuild`。

`Arc` 只用于拥有 Context 中的能力值和父链，**不是**把现有单线程 `Signal<T>` 改成线程安全状态的理由。

### 3.3 `@provide`：必须显式写类型

语法固定为：

~~~rust
@provide(expression: Type);
~~~

例如：

~~~rust
ui!(build {
    @provide(config: AppConfig);
    @provide(client: Arc<ReportApiClient>);
    @provide(Theme::dark(): Theme);
    @provide(RequestId::new(): RequestId);

    { render_header(build, app) }
})
~~~

宏在类型检查后按声明类型写入当前子作用域；它不依赖变量名或期望类型推导。显示的类型仍要与表达式的真实 Rust
类型匹配，否则由 Rust 编译器拒绝。

`@provide` 在每次构建时求值并消费其表达式。长期稳定或昂贵的能力应由根应用持有，并在这里传入
`client.clone()` 等拥有值；把 `Uuid::new_v4()`、网络连接创建或带副作用的初始化直接写在 render 前导区，
会导致它每帧重新创建，通常不符合“稳定能力”的定义。

为保持“先建立作用域、再构建内容”的确定性，`@provide` 只能出现在一个 `ui!` 块的前导区：在任何
`@inject`、`@watch`、标签或普通子表达式之前。需要局部遮蔽时，使用嵌套块：

~~~rust
ui!(build {
    @provide(Theme::light(): Theme);

    <Column>
        { ui!(build {
            @provide(Theme::dark(): Theme);
            { render_dark_panel(build, app) }
        }) }
    </Column>
})
~~~

同一底层类型需要多个实例时使用 newtype，而不是依赖变量名：

~~~rust
struct PrimaryColor(String);
struct SecondaryColor(String);

ui!(build {
    @provide(PrimaryColor("#ff5733".into()): PrimaryColor);
    @provide(SecondaryColor("#33ff57".into()): SecondaryColor);
    // ...
})
~~~

### 3.4 `@inject`：必须显式写类型，并传播错误

语法固定为：

~~~rust
@inject(local_name: Type);
~~~

例如：

~~~rust
ui!(build {
    @inject(theme: Theme);
    @inject(config: AppConfig);
    @inject(client: Arc<ReportApiClient>);

    <Column>
        <Text>{format!("{}", config.api_base_url)}</Text>
        { render_header(build, app, theme, client) }
    </Column>
})
~~~

宏展开的等价语义是 `let local_name = scope.inject::<Type>()?;`，其中 `scope` 是当前块建立后保留的局部
不可变 Context。调用点无需写 `?`，因为 `ui!` 本身返回 `ViewResult<ViewOutput<A>>`；只有把它
放进父 DSL child 位置或交给 `FrameCoordinator::prepare` 时，才消费这个输出值。

无法从任意条件分支、独立函数或运行时 TypeId 查找中证明“某类型一定已提供”，所以缺失能力必须是结构化错误：

~~~rust
// DSL runtime 私有类型；不复用 Headless 的 ActionTrigger。
enum DslTrigger {
    Click,
    TextEdit,
    TextCommit,
    TextCancel,
}

enum ViewBuildError {
    MissingProvider { type_name: &'static str, site: ViewSite },
    DuplicateProvider { type_name: &'static str, site: ViewSite },
    UnresolvedWatchAnchor { site: ViewSite },
    ActionTargetRequiresSingleRoot { site: ViewSite },
    ActionTargetCapabilityMismatch { trigger: DslTrigger, site: ViewSite },
    DirectTextActionHasBindId { site: ViewSite },
    DuplicateActionBinding { key: SemanticKey, trigger: DslTrigger, site: ViewSite },
    // 其他树和指令构建错误。
}
~~~

`ViewSite` 记录源文件、行和列，服务诊断；它绝不是跨帧身份或 `SemanticKey` 的替代品。发布版本也不得静默
注入默认值或跳过缺失 provider。

### 3.5 作用域与借用时序

~~~plantuml
@startuml
title ui!(build { ... }) 的词法 Context 作用域
participant "父 ViewBuild" as parent
participant "ui! 宏展开" as macro
participant "子 ViewContext" as scope
participant "子视图函数" as child

parent -> macro : 进入 ui!(build { ... })
macro -> scope : 收集 @provide 并创建不可变 child scope
macro -> scope : @inject<T>() -> &T
macro -> child : render_child(build, app)
child -> scope : 透过当前 scope 查找能力
child --> macro : ViewResult<ViewOutput<A>>
macro -> parent : 无论 Ok/Err/unwind 都恢复父 scope
@enduml
~~~

中间组件只要以同一个 `build` 调用子视图，就能在该词法块内看见父能力；它不需要显式转发 Context 参数。
这不是全局变量，也不是 thread-local。离开块后子 scope 立即失效，兄弟块只能看到父 scope。

## 4. `@watch`：显式声明读取依赖

### 4.1 表面语法和刷新语义

语法为：

~~~rust
@watch(local_name, &signal_expression);
~~~

它把 `&Signal<T>` 的**一次求值结果 clone 为本地 `Signal<T>` 值**，并将“当前渲染位置读取该 Signal”加入本帧
`WatchPlan`。因此 `local_name` 的类型是 `Signal<T>`，不是借自 `ViewBuild`、也不是长期保存的 `&Signal<T>`；
宏会先完成 clone，再创建订阅计划。这让 `@watch(detail, &signals.get(id))` 一类来源即使经由临时值取得，也不会把
临时借用带出指令语句。`@watch` 的第二个参数仍必须是显式的 `&Signal<T>` 表达式，不能隐式把任意值转换为 Signal。

例如：

~~~rust
fn render_task_table(
    build: &mut ViewBuild<UserAction>,
    app: &AppState,
) -> ViewResult<ViewOutput<UserAction>> {
    ui!(build {
        @watch(tasks, &app.tasks);
        @watch(filter, &app.filter);
        @watch(page, &app.current_page);
        @watch(loading, &app.is_loading);

        <Column>
            { if loading.get() {
                ui!(build { <Text>{"Loading"}</Text> })
            } else {
                ui!(build { <Text>{format!("{} items", tasks.get().len())}</Text> })
            } }
            <Text>{format!("page {}", page.get())}</Text>
        </Column>
    })
}
~~~

`@watch` 不是隐式追踪：未声明的 `app.user_profile` 即使变化也不成为这个视图的刷新原因。它也不是
`@inject`：前者订阅会变的单线程状态，后者读取一次性的、可拥有的稳定能力。

V1 的失效粒度是 **整帧根重建**。任一被观察 Signal 变化时，运行时把对应 `SemanticKey` 标脏，并请求
一次下一帧；当前应用根重新执行。key 用来保证订阅属于正确的跨帧节点和为未来局部更新保留信息，而不代表
V1 已经实现了局部 recompose。

### 4.2 为什么宏不能直接取得自动 key

先前“宏展开时向上找到最近 `SemanticKey`”的说法不成立。自动身份分配发生在已完成的 `UiNode` 树交给
`UiTree::new_with_allocator` 之后；在宏展开、甚至普通节点构造时，默认 `AutoPath` 或
`AutoStableIdentity` 的最终 key 都尚未存在。

正确流程是两阶段的：

~~~plantuml
@startuml
title @watch 的两阶段身份解析与订阅协调
participant "ui!(build { ... })" as dsl
participant "ViewBuild" as build
participant "ViewOutput<A>" as output
participant "UiTree / IdentityAllocator" as tree
participant "ComponentRuntime" as runtime
participant "Signal<T>" as signal

dsl -> build : 记录 WatchHandle（Signal clone）
dsl -> output : finish(root, PlanBundle)
output -> tree : 取出纯 UiNode
tree -> tree : 验证 + DFS 分配 NodeId / SemanticKey
tree --> output : UiTree（key 已解析）
output -> runtime : resolve PlanBundle 并 reconcile
runtime -> signal : 建立或替换订阅
signal -> runtime : 变化通知
runtime -> runtime : dirty.insert(SemanticKey)
runtime -> runtime : 可选 request_frame()
@enduml
~~~

`NodeAnchor` 是 DSL / build runtime 的私有临时概念，不进入 `UiNode` 或公开 Kernel 契约。它的确定编码是
**本帧已实际 lowering 后的 DFS child path**：根为空 path，普通真实 child 追加其实际 child index；`Fragment`
在 lowering 时展开，`For` 在本帧按实际 item 输出展开，opaque `UiNode` 则按实际 DFS 计数。`AnchorResolver`
在已校验的 `UiTree` 上按同一 child path 定位节点，再读取对应的最终 `SemanticKey`。

宏不得以 token 数、源代码位置或预估 DFS 序号充当 anchor。每个含 DSL 指令的子视图将 pending plans 私有地
携带在其 `ViewOutput<A>` 内；父 body 在确定该 child 的真实位置时，对该 bundle 统一 rebase path。
因此嵌套 `ui!`、条件分支、`For` 和 kit 表达式的**根节点**都以本帧真实树形为准；path 只在本次构建中存在，
跨帧稳定性仍完全由最终 `SemanticKey` 提供。普通 Rust 表达式返回的 opaque `UiNode` 对 DSL 而言恰好是一个
真实 child：它可以成为该表达式或 `ActionTarget` 的锚点根，但 DSL 不能把计划锚定到它未公开的内部后代；需要内部
观察或动作时，kit 必须显式暴露相应真实节点，或由子视图用 DSL 构造该子树。

### 4.3 锚点规则

`@watch` 依附于它所在的结构位置，规则如下：

| 书写位置 | 订阅锚点 | 说明 |
|---|---|---|
| `ui!` 块前导区 | 当前 `ui!` 块的真实根节点 | V1 要求该块最终恰有一个真实根；宏在根完成后把前导 watch 绑定到该根，绝不生成 `Group` / WatchScope。 |
| 某个 `<Column>`、`<Row>` 等节点体内 | 该最近包裹节点 | 节点自己的最终 `SemanticKey` 是订阅拥有者。 |
| 子视图自己的 `ui!(build { ... })` 块 | 子视图自己的真实根或其中节点 | 父视图的 watch 不会自动继承。 |
| `<For>` / `VirtualList` 的 item 根内 | 该 item 根的显式业务 key | 动态列表绝不允许用索引或结构路径冒充稳定身份。 |

示例：

~~~rust
ui!(build {
    <Column>
        @watch(tasks, &app.tasks); // 绑定到此 Column

        <For each={tasks.get()} key={task.id}>
            {|task| ui!(build {
                <Row>
                    @watch(detail, &app.details.get(task.id));
                    <Text>{task.name.clone()}</Text>
                </Row>
            })}
        </For>
    </Column>
})
~~~

示例里的 `task.id` 是局部业务身份，而不是索引。它由内部 `KeySegment` 在 Kernel identity 解析期与父
`SemanticKey` 合成最终全树唯一 key；多个列表和嵌套列表不需要由应用手写前缀，详见第 11 节的 B2。

列表中观察共享 `tasks`、`filter` 等全局 Signal 时，应在循环外声明一次。每个 item 观察自身 `detail` 的场景
可以成立，但 item 根必须有显式、稳定的业务 key，且运行时应在 item 离开当前可见窗口时释放订阅。特别是
`VirtualList` 中不得为同一个共享 Signal 建立 N 个等价订阅。

默认 `AutoPath` 对静态结构可用，但它不保证插入、删除、重排后的业务身份；`AutoStableIdentity` 是 opt-in
策略，不替代列表数据的业务 key。Kernel 已对虚拟列表项要求显式 semantic key，这一约束继续有效。

当前 Kernel 中的 logical `Group` 虽不产生绘制命令，却会参与 DFS 路径。因此它作为 WatchScope 包住一个
原本的根节点时，默认 `AutoPath` 的后代会从例如 `/0/` 变成 `/0/0/`。这会改变已有焦点、滚动、事件和
视图状态使用的 key，故 Group 不是“身份透明”的实现。V1 已明确禁止为 watch 自动插入它。

### 4.4 Fragment、根节点与顶层观察

`Fragment` 是 DSL 期语法组合，不是 Kernel 的实际节点。

| 方案 | 结论 | 原因 |
|---|---|---|
| 用 `Group` 作为顶层 WatchScope | 否决 | 它是实际节点，会改变 AutoPath。 |
| 新增 `NodeKind::Fragment`，但 DFS 跳过它 | 不采用 | 当前 `UiTree` 的 `UiNode` DFS、`NodeId` 和 `SemanticKey` 三者一一对齐；跳过其中一个节点会破坏命中、焦点与交互索引。 |
| DSL 内部 Fragment lowering | 已确定 | `<Fragment>` 在宏 / Composition 阶段扁平化为父节点 children，不进入 `UiNode`、布局、绘制或身份分配。 |

候选 lowering 形态如下；`ViewChild` 是 DSL 的内部构造值，不是新的 Headless 组件或 Kernel 契约：

~~~rust
enum ViewChild {
    Node(UiNode),
    Fragment(Vec<ViewChild>),
}
~~~

在一个真实父节点内，Fragment 可以安全消失：

~~~rust
ui!(build {
    <Column>
        <Fragment>
            <Text>{"Hello"}</Text>
            <Text>{"World"}</Text>
        </Fragment>
    </Column>
})
// lowering 后等价于 Column 的两个直接 Text 子节点。
~~~

但 Fragment 没有 `SemanticKey`，因此不能作为 `@watch` 锚点，也不能“替顶层提供一个逻辑 root key”。
`@provide` / `@inject` 是词法构建指令，不是 Fragment 的节点属性；它们不因 Fragment 出现而改变作用域规则。
Fragment 同样不能解决 opaque kit `UiNode` 与 `NodeAnchor` 的对应关系，只能消除宏额外引入的包装层。

V1 规定每个 `ui!(build { ... })` 块 lowering 后恰有一个真实根节点。顶层 `@watch` 锚定该根的最终
`SemanticKey`；`Fragment` 永远不能成为逻辑 root 或 watch anchor。语法上把单个真实节点包在顶层
`<Fragment>` 中只是无意义的透明写法，可以被接受，因为 lowering 后仍是同一个真实 root；顶层 Fragment
lowering 为零或多个真实节点、以及没有真实根的顶层 `@watch` 都是构建诊断。`UiForest` / `UiTree::new_many`
是未来独立的 Kernel 设计，不作为本 DSL 迁移的一部分。

### 4.5 订阅图必须按帧协调

直接从 `ui!` 的每帧构建调用持久订阅入口会重复安装订阅，因此运行时必须将“登记计划”和“安装订阅”拆开：

1. 成功构建 `UiTree` 后，解析本帧所有 `PendingWatch` 的 key。
2. 对同一 `(SemanticKey, Signal)` 去重，生成新的订阅图。
3. 原子替换上一帧图：已卸载 key 的订阅释放；仍存在但依赖变化的订阅替换；未变化项可复用。
4. 初始协调不产生 dirty，也不主动唤醒，避免“建树 -> watch -> 脏 -> 立即建树”的循环。
5. 若本帧 DSL、树校验或锚点解析失败，丢弃新计划，保留上一帧有效订阅图和可显示帧。
6. 无法解析锚点时返回 `ViewBuildError::UnresolvedWatchAnchor`；所有构建模式均不得静默跳过。

迁移后的运行时订阅主键是 `SemanticKey`，而非 `ComponentPath`。`ComponentPath` 仍用于 Headless
Root/Part 路由；二者不能互相偷用，因为它们分别表示组件语义路径和实际帧内节点身份。

动作绑定也有同样的时序问题：在 DSL 期登记的 `action={A}` 尚未拥有最终节点 key，必须与 WatchPlan 一样
在成功建树后解析其锚点，并生成 `ActionFrame`。`ActionFrame` 按最终 `NodeId` 找到 trigger binding；D9-B
再以 `FrameToken` 证明这个 `NodeId` 来自当前 active frame。若某动作来自 Headless adapter，adapter 还必须
验证该 `EventFrame`、`ActionFrame` 与 token 属于同一成功帧。不能在宏期保存未解析的 node id 或假定
`SemanticKey` 已经存在。

## 5. `Signal`、批处理与下一帧调度

### 5.1 保持单线程信号模型

当前 `Signal<T>` 基于 `Rc`、`RefCell` 与同步回调，本文延续这一选择。不要为了批处理或 Host 回调把它改成
`Arc<Mutex<_>>`、`Atomic*` 或跨线程 subscriber；那会扩大所有现有 API 和渲染线程模型的风险。

Signal 变化只做两件事：将订阅的 `SemanticKey` 写入 dirty 集合，并在适当时机请求下一帧。它不得在通知
回调中同步重入 render、布局或 Renderer。

### 5.2 `runtime.batch` 的目标语义

批处理是 ActionHandler 中的普通 Rust，不是 DSL 语法：

~~~rust
runtime.batch(|| {
    self.tasks.set(new_tasks);
    self.page.set(2);
    self.loading.set(false);
});
~~~

目标语义：

| 规则 | 结果 |
|---|---|
| 多个 Signal 写入同一 key | 一个 `BTreeSet<SemanticKey>` 条目。 |
| 外层 batch 内的多次写入 | 外层结束前只累积 dirty，不重复请求帧。 |
| 嵌套 batch | 只有最外层结束可以请求帧。 |
| 非 batch 的一次写入 | 记录 dirty，并至多请求一帧。 |
| Host 没有 `FrameInvalidator` | 现有 `take_dirty()` 轮询流程仍可消费 dirty。 |
| dirty 已有待处理帧 | `frame_requested` 阻止重复唤醒，直到 Host 开始/消费该帧后重置。 |
| 闭包 panic | 需要 RAII guard 恢复 batch 深度，不能永久压住后续唤醒。 |

`FrameInvalidator` 是可选端口，只承担 `request_frame()` 调度，不运行用户逻辑，也不直接渲染。协议已经
确定：Runtime 持有 dirty 与请求去重状态；Host 在真正开始消费一帧时调用 `runtime.begin_frame()`，由该入口
原子确认并重置请求状态。Host 销毁时必须解除 Runtime 对 invalidator 的弱引用或等价端口，后续写入只保留
dirty，不得访问已销毁 Host。

## 6. V1 DSL 表面与 Kit 边界

### 6.1 调用形式

DSL 显式接受构建器，唯一公开拼写是 `ui!(build { ... })`：

~~~rust
fn render_mobile_browse(
    build: &mut ViewBuild<MobileAction>,
    app: &AppState,
) -> ViewResult<ViewOutput<MobileAction>> {
    ui!(build {
        // 指令和声明式结构
    })
}
~~~

不使用固定变量名、thread-local、函数属性宏或隐式全局构建器。这样嵌套视图、测试和多窗口构建都拥有可见的
构建上下文。

### 6.2 V1 支持的结构能力

| 类别 | V1 | 规则 |
|---|---|---|
| 结构标签 | `Column`、`Row`、`Frame`、`Stack`、`Text`、`Icon`、`Image` | 宏在编译期展开为当前 contract/foundation 构造器调用。 |
| 集合标签 | `For`、`VirtualList` | `For` 必须提供稳定 `key`；不提供 `<Index>`。`VirtualList` 必须显式提供当前窗口 `items`、`total_items`、`first_item_index`、`item_height`、`item_spacing`、`overscan`；DSL 不猜测窗口。 |
| 动作绑定包装器 | `ActionTarget` | 不产生 `UiNode`；必须恰有一个真实子根，将 `action` / `on_input` / `on_submit` / `on_cancel` 计划锚定到该根。 |
| 条件与分支 | 普通 Rust `if` / `match` 表达式 | 不引入 `<Show>`、`<Switch>`、`<Match>`。 |
| 子视图 | `{ render_child(build, app) }` 或 `{ ui!(build { ... }) }` | `IntoViewChild<A>` 只接受四种明确值：`UiNode`、`ViewResult<UiNode>`（均视为无 DSL plan 的 opaque child）、`ViewOutput<A>` 与 `ViewResult<ViewOutput<A>>`（保留并 rebase DSL plan）。 |
| 指令 | `@provide`、`@inject`、`@watch` | 全部只在宏可识别的结构位置生效。 |
| 批处理 | 无 | 使用 `runtime.batch`。 |

属性值保持 Rust 表达式，例如 `gap={16.0}`、`key={task.id}`。宏只生成构造代码，不在运行时解析标签或属性字符串。
错误信息应尽可能归到 DSL 源位置和对应 Rust 类型错误。

`ActionTarget` 是能力包装器，不是跨 Kit 视觉组件，也不是 Kernel `NodeKind`。它与 `Fragment` 一样不增加
DFS 节点，但比 Fragment 更严格：只能产出一个真实子根，并把自身声明的 action plan 重新锚定到该根。它允许
应用把各 target 的 kit 构造器放在 DSL 中，同时不让 DSL crate 依赖任何 kit：

~~~rust
ui!(build {
    <Column>
        <ActionTarget on_input={UserAction::Search}>
            { mobile_search_field_for_dsl(search_value) }
        </ActionTarget>

        <ActionTarget action={UserAction::Refresh}>
            { MobileIconButton::new(refresh_icon(), "mobile.refresh").into_node() }
        </ActionTarget>
    </Column>
})
~~~

建树后，`ActionTarget` 会验证锚定根的 `InteractConcern`：`action` 要求 `clickable`，`on_input` / `on_submit` /
`on_cancel` 要求 `input: Some(TextInputSpec)` 且 `bind_id: None`。子根不唯一、能力不匹配、直接文本动作与 `BindId` 冲突、
或在同一 target 上重复绑定同一 trigger 都返回 `ViewBuildError`，而不是静默注册永远不会触发的 action。
`ActionTarget` 可以位于 `ui!` 顶层，只要其唯一子根就是该块要求的唯一真实根；顶层 `@watch` 在 lowering 后绑定这
个子根。它本身不形成指令作用域，不能在其 body 中声明 `@watch` / `@provide` / `@inject`，也不能把多个 child
隐式变成 Fragment；它只服务“外部构造的一个真实节点”的动作锚定。当前 `MobileSearchField::new` 总会设置 `bind_id`，因此 mobile DSL 迁移必须提供
一个保留 `TextInputSpec`、但不设置 `bind_id` 的 unbound field 构造路径。该路径还必须把节点的 `SemanticKey`
（或等价 `IdentityConcern`）与可选 `BindId` 分离，不能继续以同一参数同时表达二者；可采用
`MobileSearchField::unbound(content, semantic_key)` 一类 API。上例的 `mobile_search_field_for_dsl` 表示该应用 /
kit 侧的目标构造函数。

### 6.3 不做跨 Kit 视觉标签

V1 故意不把下列名字变为“根据目标自动选 Kit”的 DSL 标签：

~~~rust
// V1 不承诺提供这些跨 Kit 标签。
<Button />
<SearchInput />
<Dialog />
~~~

它们的视觉结构、交互密度和 recipe 属于各自 Kit。业务视图通过普通 Rust 表达式接入目标 Kit：

~~~rust
ui!(build {
    <Column>
        { MobileScaffold::new(/* ... */).into_node() }
        { MobileCell::new(/* ... */).into_node() }
    </Column>
})
~~~

这符合“绝对一致才复用代码；语义一致复用协议；概念一致只共享抽象边界”的平台原则，也避免 DSL crate 同时
依赖 mobile-kit 与 desktop-kit 形成反向耦合。日后若需要跨 kit 的通用组件，必须先在 Headless 层确立稳定
语义合约和独立适配边界，不能直接把某一 kit 的 recipe 泛化成全局默认。

### 6.4 物理 crate 划分

D6 已确认采用 A：物理 crate 固定为以下两个单向依赖 crate：

| crate | 责任 | 可依赖 |
|---|---|---|
| `tela-ui-dsl` | `ViewBuild`、`ViewContext`、`ViewOutput` / `WatchPlan`、结构适配、错误类型及宏 re-export | contract、core；不依赖 Headless 或任何 kit。 |
| `tela-ui-dsl-macros` | `ui!` 的解析、语法错误与 Rust 构造代码生成 | `proc_macro` 解析依赖；不得反向依赖 `tela-ui-dsl` 或 kit。 |

宏 crate 通过生成对运行时 crate 的受限路径调用完成协作；运行时 crate re-export `ui!`。不预建
`tela-ui-composition`：只有出现第二个真实的非 DSL consumer 后，才能基于复用证据另行抽取。不得为了方便令
proc-macro 依赖应用或 kit。

V1 的 DSL 直接构造 Kernel `UiNode`，再由 `tela-core` 构造 `UiTree`；它不以接入既有 Headless 为前提。
如后续确有 Headless 组件事件需要，可新增单向的 `tela-ui-dsl-headless` adapter（依赖 DSL 与 Headless），把
Headless 路由结果接到 DSL 的动作计划。不得让现有 Headless 构造 API 反向决定 DSL 的树、身份或作用域模型。

## 7. 动作与事件链

### 7.1 动作层不以 Headless 为前提

DSL 的 `ActionRegistry<A>` 是应用层的纯数据动作计划：它按最终 `SemanticKey` 与**内层** Kernel `UiAction` 的触发
语义映射到 `A`，再交给 `ActionHandler`。D9-B 采纳后，入口实际接收带来源 token 的 `FramedUiAction`，先验证 token
再读取其内层动作；这条路径先服务 DSL 原语和 kit 的普通 Rust 构造器，不要求预先接入既有 Headless。

已有 `EventRegistry` 仍负责 Headless `Root/Part`、`BindId` 与 `HeadlessEvent` 的组件契约。某个 DSL 视图
选择 Headless 组件时，adapter 必须先经过该注册表，再把 `RoutedEvent` 映射到同帧的 `ActionRegistry<A>`；
不能为了方便把应用 Action 塞入 Headless，也不能让 Headless 成为 DSL 的必经建树路径。

推荐的应用层链路是：

~~~plantuml
@startuml
title D9-B 下的 DSL 原生动作链与可选 Headless adapter
participant "Target input" as host
participant "Kernel" as kernel
participant "ActionRegistry<A>" as actions
participant "ActionHandler" as handler
participant "AppState" as state
participant "EventRegistry (optional)" as headless

host -> kernel : pointer / text / key input
kernel --> host : UiAction
host -> actions : FramedUiAction（DSL 原语 / 普通 kit）
host -> headless : 已验证 UiAction + active EventFrame（仅 Headless 组件）
headless -> actions : FramedRoutedEvent / FramedHeadlessEvent（保留同 token）
actions -> handler : A（纯值）
handler -> state : 业务更新 / runtime.batch
@enduml
~~~

`ActionRegistry<A>` 是应用拥有、按帧重建的注册表：无输入绑定保存 `A` 值；有输入绑定保存由 trigger
确定类型的函数指针，以及可选的显式纯 context。D9-B 中的 `FramedUiAction` 是 Composition 的
`{ token: FrameToken, action: UiAction }` 外层值；Headless adapter 的 `FramedRoutedEvent` / `FramedHeadlessEvent`
同样只是在 `RoutedEvent` / `HeadlessEvent` 外保留该 token。它们都不是 Kernel 或 Headless 的新领域类型。
动作层不能改变 `UiNode` 纯数据边界；Headless adapter 也不能把 Root/Part 事件解释泄漏进 DSL 原生建树 API。

仅 `ActionFrame` 的 `NodeId` 映射不足以拒绝旧帧事件：D9-B 下 DSL 原生路径先比较 `FrameToken`，再由
`ActionFrame` 查找当前 trigger；选择 Headless 的 adapter 还必须验证配对的 `EventFrame`、`ActionFrame` 与 token
同帧，不能把旧 `RoutedEvent` 映射到新 frame 中同 key 的新 Action。WatchPlan 与 ActionPlan 共享
AnchorResolver，但它们的生命周期、错误和注册表类型保持分离。

### 7.2 强类型 payload 动作 API（已确定：B）

DSL 原生 `ActionFrame` 的 trigger 分类只依赖 Kernel `UiAction`，不能复用 Headless 的 `ActionTrigger` 类型。
带 payload 的 V1 表面 API 采用 **trigger 声明强类型 payload** 的 B 方案：属性名决定 Kernel 事件与 payload
类型，宏要求直接映射是可 coercion 为对应函数指针类型的 `ExprPath`，或是受识别的 `with_context` 调用；不允许
应用在属性里自行猜测或转换 `UiAction`。宏不会也不能依据 `ExprPath` 的名字区分函数项和同类型局部函数指针，
但仍会拒绝闭包与任意运行时映射工厂。

V1 中这些属性只由透明的 `<ActionTarget>` 承载。它必须有且只有一个真实子根，pending action 的
`NodeAnchor` 指向该子根而不是包装器自身；完成 `UiTree` 构建后，ActionPlan 才据此生成最终
`SemanticKey` / `NodeId` 映射。后续若某个 DSL 语义元素直接提供相同属性，它也必须 lowering 为同一
`ActionTarget` 语义，不能另建一套动作注册方式。

| DSL 属性 | Kernel 来源 | 交给 mapper 的 payload | 映射器类型 | 分发语义 |
|---|---|---|---|---|
| `action={A}` | `UiAction::Click` | 无 | `A` 纯值 | 每次 click 克隆当前帧保存的 `A`。 |
| `on_input={f}` | `UiAction::TextInput { event: TextInputEvent::Edit { .. }, .. }` | `String` | `fn(String) -> A` | 每个 Edit（含 IME composition）产生一个 Action；防抖、搜索请求等仍由 ActionHandler 决定。 |
| `on_submit={f}` | `UiAction::TextInput { event: TextInputEvent::Commit { .. }, .. }` | `String` | `fn(String) -> A` | 只在提交边界分发；不与 `on_input` 合并。 |
| `on_cancel={A}` | `UiAction::TextInput { event: TextInputEvent::Cancel { .. }, .. }` | 无 | `A` 纯值 | 仅用于 input 取消语义，例如清除搜索或恢复业务投影。 |

`TextInputEvent::Cancel` 只触发显式的 `on_cancel`，绝不回退触发 `on_input` 或 `on_submit`。它不暴露 selection
payload；未来若确有需要，必须先定义新的稳定类型。Pointer、Gesture、Scroll、Focus、Select 等也遵循相同规则：
在本文件或对应组件契约明确“属性名 -> `UiAction` 变体 -> payload 类型”之前，DSL 不接受这些属性。

构建期 / 解析期分别承担不同验证：宏在编译期拒绝闭包、未知动作属性和显然错误的属性位置；树成功后，
`ActionPlan` 验证 `ActionTarget` 的唯一子根及其 `InteractConcern` 能力。`action` 必须锚到 `clickable` 根；
`on_input` / `on_submit` / `on_cancel` 必须锚到 `input: Some(TextInputSpec)` 且 `bind_id: None` 的根。同一最终
`SemanticKey + trigger` 的重复绑定是 `ViewBuildError::DuplicateActionBinding`，不采用“后者覆盖前者”的隐式规则。

`UiAction::ValueChange { bind_id, value }` 不是 node-key 动作，不能被 `on_input` 偷换或按 `NodeAnchor` 路由。
它继续遵守 `BindId` 的 Kernel / Headless 受控字段协议；直接 DSL 文本动作的 target 因而必须没有 `bind_id`。
若未来需要把 `ValueChange` 映射为 Application Action，必须新增专用 `BindId` adapter，并以现有 input / form
回归定义其类型与 generation 语义。

这是受控输入构造语义的一次明确 breaking change：`InteractConcern::bind_id` 仍是可选字段，但现有
`MobileSearchField::new` 将同一个字符串同时用于节点身份和默认业务写入路径。迁移后，`ValueChange` 只是在
声明 `bind_id` 的字段上的唯一业务变更通道；未声明 `bind_id` 的 input 可以把 `TextInput` 生命周期映射为 DSL
Application Action。迁移同一 PR 必须提供将 `SemanticKey` 与可选 `BindId` 分离的 unbound 构造路径，并同步调整
Kernel 受控字段 API 文档、mobile 输入事件测试和 demo；不保留“既登记 `BindId` 又登记 DSL 文本 action”的兼容桥。

宏生成的概念形态如下；`ActionBinding` / `TextActionMap` 是 DSL runtime 内部类型，绝不写入 `UiNode`：

~~~rust
enum PendingAction<A> {
    Click { anchor: NodeAnchor, action: A },
    Input { anchor: NodeAnchor, map: TextActionMap<A> },
    Submit { anchor: NodeAnchor, map: TextActionMap<A> },
    Cancel { anchor: NodeAnchor, action: A },
}

enum TextActionMap<A> {
    Unary(fn(String) -> A),
    // 由 with_context 产生；实现是 sealed 的 data + fn pointer，不能由应用塞入闭包。
    Bound(Box<dyn SealedTextActionMap<A>>),
}
~~~

`SealedTextActionMap<A>` 只由 DSL runtime 内部的 `with_context` 构造器实现：其具体实例保存
`Context` 与 `fn(Context, String) -> A`，在分发时克隆 context 后调用函数指针。它不是 `dyn Fn`，也不向应用
开放实现 trait 的入口；`Box` 仅用于在同一帧的异构 ActionPlan 中擦除 `Context` 的具体类型。

`on_input={UserAction::Search}` 由宏在带有期望类型的局部位置展开，等价于 `let map: fn(String) -> UserAction =
UserAction::Search;`。这既保留 Rust 的枚举构造器语法，也让类型不匹配在编译期失败。一个同类型的局部函数指针
变量也会满足这条 Rust 类型规则；它仍然只是函数指针，而不是捕获闭包。动作 `A` 在 UI 线程的 `ActionFrame` 中
要求 `Clone + 'static`；只有跨线程投递到 ActionHandler 时才额外要求 `Send + 'static`。

需要业务 context 时使用 `with_context(context, mapper)`，其中 `mapper` 的形状固定为
`fn(Context, String) -> A`，且 `Context: Clone + Send + Sync + 'static`。它把 context 当作纯值保存在本帧
动作计划中，而非捕获变量。`ui!` 宏在 `action`、`on_input`、`on_submit` 与 `on_cancel` 的属性值处拒绝
`ExprClosure`；无捕获闭包也不作为函数指针的例外放行。

Headless adapter 若存在，只负责把同一成功帧的 `RoutedEvent` 交给 `ActionRegistry<A>`；它不改变上述 DSL
属性的 payload 类型、也不进入 DSL core crate。

## 8. mobile browse 垂直切片

第一阶段只选 mobile browse 页面，而不是同时迁移 desktop 与 mobile。原因是它已经覆盖安全区、导航、搜索、
列表/空态与触控动作，并且 mobile 业务视图本来就应独立于 desktop 重写。

切片应达到如下边界：

| 层 | V1 必须证明 | 不在 V1 里证明 |
|---|---|---|
| DSL | `ui!(build { ... })`、结构标签、嵌套子视图、显式错误传播 | 所有 114 组件族的 DSL 标签。 |
| Context | `@provide` / `@inject` 类型显式、遮蔽和缺失诊断 | 注入可变状态或全局 service locator。 |
| Watch | 根节点绑定的 watch、节点锚点、显式 `For` item key、VirtualList 窗口卸载释放 | 局部 recompose 或跨线程 Signal。 |
| Action | 至少一条 browse 交互穿过 DSL `ActionRegistry` 到应用 handler；如使用 Headless 组件，再单独证明 adapter 链。 | 一次性泛化所有输入/手势 payload。 |
| Host | 保持 mobile 安全区、受控搜索、Raster 参考和 D9 active-frame 合同 | Android / iOS 真机验收。 |

mobile Browse 已将 route 与 query 收敛为 `Signal`，由 `FrameCoordinator` 持有 runtime，并在 Host 开始候选帧时消费
dirty；Preview 仍是 direct-Rust island。后续迁移不得只替换 `render` 函数，仍须保留当前受控输入、安全区与 raster 测试。
受控搜索可使用已确定的 `on_input={UserAction::Search}`；其每次 Edit 的 debounce、查询取消与陈旧结果处理仍在
ActionHandler / Application 投递层完成，不进入 DSL 动作映射器。

## 9. 迁移顺序与验收

第 11.7 节的 D1-D8 已关闭。当前 Browse 和 direct iOS adapter 按 D9-B 的推荐合同完成了局部实现，用于验证
candidate transaction 与输入 provenance；这不等于 D9 已被正式关闭。I1 已由第 11.8 节关闭；I2-B 已将 remote guest
provenance 固化为版本化 ABI，仍需完成第 11.9 节 R1 的真实 Target 验收。

关闭后建议按风险从低到高推进，每一步保留可测试的边界：

1. 新建 DSL runtime / proc-macro crate，仅实现结构节点和 `ViewResult<ViewOutput<A>>`，不接 Signal 或事件。
2. 实现不可变 `ViewContext`、显式 `@provide` / `@inject`、词法作用域恢复和错误诊断。
3. 为 DSL 产物设计内部 `NodeAnchor` 与 `WatchPlan`，先用树级单元测试验证自动 key、显式 key、列表重排和
   未解析锚点。
4. 将 `ComponentRuntime` 的观察主键从 `ComponentPath` 迁至 `SemanticKey`，实现按帧 reconcile、卸载和
   不自触发的初始安装；同步更新 desktop 的现有使用点和 030 文档。
5. 加入 `batch`、可选 `FrameInvalidator` 与 Host 消费 dirty 的严格时序测试。
6. 实现 DSL 原生 `ActionRegistry<A>` 与第 7.2 节强类型 payload trigger；仅在实际使用 Headless 组件时新增 adapter，并覆盖 Button / Input / BindId 的真实事件路径。
7. 只迁移 mobile browse 页面，并跑现有树、事件、Raster、安全区和输入回归。
8. 根据度量决定是否推广到其他 mobile 视图；desktop 另行评估，不以“语法可用”推断跨目标可复用。

每步至少应有下列测试类别：

| 测试 | 要验证的失败模式 |
|---|---|
| proc-macro compile-fail / trybuild | 缺类型、错误指令位置、`@provide` 非前导区、缺 key 的动态列表。 |
| Context 单元测试 | 父链查找、同块重复、子块遮蔽、错误后作用域恢复、`&T` 生命周期。 |
| WatchPlan / tree 测试 | AutoPath 静态结构、真实根绑定、显式 key、`For` 重排、锚点失败不替换旧图、VirtualList 窗口卸载。 |
| runtime 测试 | 同 key 合并、嵌套 batch、panic 安全、初次 reconcile 不标脏、无 invalidator 的轮询兼容。 |
| event 集成测试 | 若采纳 D9-B，验证 `FramedUiAction -> ActionFrame -> ActionHandler`；采用 Headless 的组件另测“token 校验后的 `UiAction + EventFrame -> EventRegistry -> FramedRoutedEvent -> adapter -> ActionRegistry -> ActionHandler`”，含输入 payload 与 BindId。 |
| mobile 产品回归 | 安全区、搜索、列表、空态、导航、触控事件、Raster 参考。 |
| benchmark | anchor / plan / reconcile / dirty / frame 调度的真实成本；不预设数字。 |

当前已有依赖最小化的测量入口
[`crates/ui/dsl/examples/frame_cost.rs`](../crates/ui/dsl/examples/frame_cost.rs)。可用
`cargo run --release -p tela-ui-dsl --example frame_cost -- --nodes 1000 --iterations 200`
采集同一机器上的观测值。它刻意只覆盖 DSL 的宏 lowering、列表 key 解析、watch plan、reconcile、dirty 与
frame 调度；不得把结果外推为 Kernel layout、renderer、Target present 或整帧的性能结论。

## 10. 实施审查与验证项

本节记录的是已确定设计的实现风险与验收，不再把已决事项伪装成待裁决问题。第 11 节是决策状态的唯一来源。

### 10.1 已确定设计的验收

| 已确定设计 | 必须证明 |
|---|---|
| `NodeAnchor` 使用本帧真实 DFS child path | 嵌套 `ui!`、条件、`Fragment`、`For`、VirtualList 窗口与 opaque kit `UiNode` 都能解析到正确最终 key；不得按 token 数或预估 DFS 序定位。 |
| 顶层 watch 不插入 `Group` | DSL 前后相同的真实根与子树保留同一 AutoPath；顶层多根 / Fragment / 无真实根 watch 均产生诊断。 |
| `For` 的内部 `KeySegment` | 两个列表可复用相同局部 id；嵌套列表、重排、过滤和 VirtualList 窗口移动后最终 key 仍唯一且跟随业务项。 |
| 透明 `ActionTarget` | 顶层的唯一 child 可作为 `ui!` 的真实根，顶层 watch 解析到该 child，且 target 不改变 DFS path；零 / 多个 child、错误 capability 与 `bind_id` 双路写入均产生诊断。 |
| DSL 原生 `ActionFrame` | 若采纳 D9-B，旧 token 的 `UiAction` 不能执行新 action；Headless adapter 使用时必须与 EventFrame 共享同一个 token。 |
| 失败帧 | DSL / tree / anchor / Host resolve 失败不会发布新 watch/action 图；若采纳 D9-B，Host profile / view state 也保留上一成功状态并记录诊断。 |
| `runtime.begin_frame()` | request 去重、nested batch、Host 销毁、无 invalidator 轮询和 panic unwind 都不会丢唤醒或永久抑制后续帧。 |

### 10.2 高风险迁移项

| 问题 | 当前源码关联 | 审查要求 |
|---|---|---|
| `ComponentPath` 改为 `SemanticKey` | 迁移已落在 DSL runtime、desktop 观察调用点与 030 的 Signal 描述 | 不留下双语义 `watch`；`ComponentPath` 只保留 Headless Root/Part 路由。 |

### 10.3 需要收紧或量化的边界

| 问题 | 风险 | 验收方式 |
|---|---|---|
| 同一 signal/key 重复登记 | N 次订阅会制造无用回调 | `(SemanticKey, SignalId)` 去重与卸载测试。 |
| `SignalIdentity` | 不能泄漏 `Rc` 地址或错误宣称跨进程序列化 | `SignalInner` 内部 `SignalId(u64)`、异构去重和 clone 测试。 |
| `IntoViewChild` | 隐式转换掩盖 `Result`、列表或 child 错误 | 只接受 `UiNode` / `ViewResult<UiNode>` 这两种 opaque child，以及 `ViewOutput<A>` / `ViewResult<ViewOutput<A>>` 这两种携带 DSL plan 的 child；compile-fail 覆盖 `Vec` 与歧义。 |
| 强类型 payload 映射 | 任意闭包、未声明 trigger 或 `BindId` 双路写入会破坏纯数据动作模型 | 验证 `on_input` / `on_submit` 的 `ExprPath -> fn(String) -> A` 类型约束、`on_cancel`、`with_context` 纯值绑定、IME Edit/Commit 分流、`bind_id: None` 和闭包 compile-fail。函数项与同类型局部函数指针在 Rust 层不可区分，不把“变量来源”伪装成可验证约束。 |
| `Send + Sync` Context | 可能排除 Target 主线程能力 | 在每个 target 的 capability 注入点审计；不能用 `unsafe` wrapper 绕开约束。 |
| 异步回 UI 线程 | 单线程 `Signal<T>` 不能从后台直接 set | 后台先投递 Action；窗口销毁和陈旧结果在 Application 投递层处理。 |
| 文档一致性 | 030 与 031 的当前/目标状态可能混淆 | 迁移 PR 同步更新 030、API 文档与迁移记录。 |

#### B2 已确认：内部 `KeySegment`

应用代码只写局部业务 key；`KeySegment` 是宏 lowering 与 Kernel identity 分配器之间的 `#[doc(hidden)]` ABI plumbing，
不属于受支持的应用 API，应用不应导入、构造或依赖它。Kernel 在 parent key 已解析后立即合成最终 key，因此全树唯一性、VirtualList 校验与后续
WatchPlan 都看到同一个最终 `SemanticKey`。同父 sibling collection 的 scope 来自 macro 固定 declaration
scope；不能把下面的二元拼接示意误读为“没有 scope 也足以避免所有碰撞”。

~~~rust
// 应用只提供局部业务身份。
<For each={tasks} key={task.id}>
    {|task| <Row>{task.name}</Row>}
</For>

// 概念上的内部 lowering；不属于应用 API。
parent_semantic_key + internal KeySegment(task.id) -> final SemanticKey
~~~

嵌套列表重复这个过程：外层 item 的最终 key 成为内层 parent，得到 `outer/inner/...` 的稳定链。组合发生在
`UiTree` 身份解析期，而不是 Macro 或 WatchPlan 的后处理期。

### 11.6 P1 已确认：trigger 声明强类型 payload（B）

P1 选择 B。DSL 属性拥有稳定、可审计的 payload 类型，而不是把原始 `UiAction`、`Value` 或 Headless 事件
暴露给业务视图。V1 的完整规则见第 7.2 节：透明 `ActionTarget` 锚定一个真实子根；`action={A}` 对应 click；
`on_input={f}` 与 `on_submit={f}` 分别接收 Edit / Commit 的 `String`，`on_cancel={A}` 对应 Cancel；
`with_context` 是绑定额外纯数据的唯一入口；闭包、未声明 trigger、能力不匹配 target 与
`BindId::ValueChange` 的隐式转换均被禁止。

#### D9：Host active-frame 边界（待确认）

**台账状态：唯一待确认项。** 现有 mobile Browse、direct iOS adapter 与远程 ABI 已按方案 B 的形状做了
接口和回归验证，用来证明它可实施；在明确采纳前，它们只能被视为候选实现，不能把本文中所有“D9-B 下”
的条件性描述读成正式规范。

`FrameCoordinator` 只能事务化它自己拥有的 allocator、watch 和 DSL action snapshot。当前
`DefaultApplicationProfile::reconcile_tree` 会原地更新 `ViewStateStore` 的 focus / hover / pointer，`resolve` 会原地
更新 layout cache；而 Kernel `UiAction` 只带本帧 `NodeId`，新树可以复用相同数值。若 Host 在候选 resolve 前直接
操作 active profile / state，或在新帧发布后接收旧 surface 采样的动作，便会违反“失败不污染上一帧”和“旧帧动作必须
丢弃”两项既定保证。

| 方案 | 描述 | 结果 |
|---|---|---|
| A. 约定式 Host | Host 自行承诺先读后写、只投递当前帧动作；不引入候选 Host state 或 frame token。 | 实施最小，但保证无法由 API 检查；失败候选、异步输入或 queued event 很容易突破约定。 |
| B. Host 候选事务 + `FrameToken` | Host 为 profile / `ViewStateStore` / scroll clamp 等候选副作用建立 staging transaction；成功时在同一 GUI-loop 临界区交换 Host state 与 DSL active frame。Host / Composition 在该 swap 时分配单调 `FrameToken`，Target 在采样输入时把它与 `UiAction` 封成 `FramedUiAction`；DSL 和可选 Headless adapter 都拒绝 token 不等于 active frame 的动作。 | **推荐。** 不修改 Kernel `UiAction`，同时把 profile 状态和动作来源纳入可验证的 active-frame 合同。普通帧不得无条件深拷贝整张 layout cache；实现应优先 journal / copy-on-write，完整 clone 仅能在已量化且有界时采用。 |
| C. Kernel 统一拥有 | Kernel 吸收 profile、view state、Host transaction 和 frame generation。 | 否决候选。它会把 Target / Application 生命周期下沉到 Kernel，违反既有所有权边界。 |

D9-B 的最低契约如下：

1. 候选 resolve 与 renderer preflight 只可写入 Host 的 staging profile / view state；任一**提交前**错误或丢弃都保持 active Host state、DSL active frame 和 token 不变。成功 swap 后的实际 present 失败属于 Target recovery，记录诊断并保留逻辑 active frame，不倒退到旧树。
2. 成功提交是同一个 Host 帧循环临界区内的无失败 swap：先完成所有可能失败的 resolve，再发布 tree / frame / watch / action、Host state 和新 token。
3. Target 把输入规范化为 `UiAction` 时，必须同时保留其来源 `FrameToken`；`FrameCoordinator::dispatch` 和 Headless adapter 都以 token equality 为前置条件，不能只按可复用的 `NodeId` 路由。
4. `UiAction` 仍是 Kernel 的纯事件值，不携带应用 generation；`FrameToken` 是 Composition / Host 的外层包装，不能反向污染 Kernel contract。
5. `FrameToken` 是 active-frame 的唯一外层 provenance，不等同于 `ActionFrame::generation()` 或
   `EventFrame::generation`。一次成功提交可以把三者关联到同一 active frame，但 adapter 只能使用提交时保存的关联，
   不能以它们的数值恰好相同作为正确性条件。
6. `FrameCoordinator::commit_with` 的 Host commit callback 只允许执行已经准备好的、不可失败且不可重入的 state
   swap；它不得回调应用逻辑、派发输入或在 callback 内观察尚未完成发布的 active frame。若 Host 不能提供这种临界区，
   就不满足 D9-B，必须在 composition 之外建立等价的事务边界。

#### D2 已确认的最低不变量

无论选择哪种 collection scope 来源，下列不变量不得变化：

1. 应用提供的 `key={...}` 是 item 的局部业务标识，禁止索引充当业务 key。
2. 同一个真实父节点下的两个 collection 可以各自拥有 `id = 1`，最终 `SemanticKey` 仍必须不同。
3. collection scope 必须每次都参与合成，不能在检测到碰撞后才改变既有 item 的 key。
4. `KeySegment` 的字符串表示必须 injective：分隔符、转义符和内部保留段不能使不同的 scope / item 组合得到同一
   `SemanticKey`。
5. 最终 key 仍只在 Kernel identity 解析期形成；macro 与 WatchPlan 都不得提前拼接完整字符串。
6. 所有 Kernel key consumer，包括 FocusScope、Teleport、VirtualList 与事件/状态投影，必须读取同一份已解析的
   final key，而不是只读取 `UiNode.identity.semantic_key` 的原始字段。
7. `For key={...}` 的表达式必须先经 D8 选择的业务 key 转换协议成为一个 owned、canonical 的局部值；它不能
   依赖 `KeySegment` 的公开构造，也不能在一次 lowering 中重复求值。

#### D2 已确认的 scope 生成规则

D2-A 已确认，scope 的生成必须遵守以下边界：

1. 它由 proc macro 针对**同一个透明 parent body 中每一处 `<For>` 声明**在编译期固定；不能由运行时输出的
   `ViewChild` 数、当前 collection 数量或 `items.len()` 计数。
2. 条件分支、过滤结果、空列表和窗口移动只能改变是否存在 item，不能重编号另一个已声明的 collection。
3. `<Fragment>` 不建立新 scope；它的 `<For>` 仍属于其 lowering 后的真实 parent body。嵌套真实节点和嵌套
   `ui!` 则各自拥有新的 parent 范围。
4. 已明确接受：源码插入 / 重排 `<For>` 后，新编译版本的 collection scope 可以变化；V1 不承诺 hot reload
   下跨源码结构修改保留动态 item 状态。
5. 最终字符串的内部编码必须保留 parent key 的全部字节，且对 scope 与 item segment 使用无歧义编码；不能通过
   `trim_end_matches('/')` 等归一化让两个不同 parent key 合成同一个 final key。

#### D4 已确认的 DSL 提交序列

无论 D9 最终选择何种 Host 细节，DSL 自身的失败边界必须成立：

1. 新 `ViewBuild` 只产生候选 root、watch plan 和 action plan，不修改 active runtime。
2. 候选 root 经 identity 分配、tree validation、anchor/action capability validation 和 frame resolve 后，才有资格成为
   `PreparedFrame`。
3. 任一阶段失败时保留上一 `UiTree`、`UiFrame`、watch graph、`ActionFrame` 与 allocator 的成功状态，并输出诊断。
4. 成功时以同一代际替换 active tree / frame / watch graph / action frame。D9 关闭前，不能把“只按 active
   `NodeId` 路由”误称为足以拒绝旧 frame action；旧动作的 provenance 由 D9 的 `FrameToken` 补足。

#### D7 已确认的最低不变量

无论选择哪种 item root API，下列事实不能被绕过：

1. 一个 `<For>` item 在 lowering 后必须恰有一个真实 root；语法上包一层 `<Fragment>` 只有在它最终仍为一个真实
   root 时才等价于无 Fragment。多 root item 或没有 root 都是构建诊断。
2. `KeySegment` 附着于该 item root，并由其真实 parent 的最终 `SemanticKey` 合成；它不能附着于透明 `For` 或
   `Fragment`。
3. 当前 Kernel 只允许 identity 挂在 identity-capable 容器 / 逻辑节点上，不能把 `For` key 直接挂到 `Text`、`Image`
   等 primitive；DSL 必须给出有源位置的诊断。
4. item root 的 identity 决定 item 生命周期；root 以下的子节点可以拥有独立显式 `SemanticKey`，但它们不能代替 item
   root 的 business key。

### 11.8 I1 已关闭：计划携带的子视图组合

早期实现把本帧的 WatchPlan / ActionPlan 暂存在共享 `ViewBuild` 中，依赖父 DSL 的 expression plan marker 捕获
子表达式执行期间新增的计划。这让内联写法正确，却错误地使普通 Rust 局部变量的执行时序成为视图身份的一部分。

`ui!(build { ... })` 现在返回 `ViewResult<ViewOutput<A>>`。`ViewOutput<A>` 私有地携带纯 `UiNode` 和不进入 Kernel 的
`PlanBundle<A>`；`IntoViewChild<A>` 只对这个明确类型、`UiNode` 以及它们的 `ViewResult` 形式开放。父 body 降低 child 时
将 bundle 按真实 DFS 位置 rebase，之后 `FrameCoordinator::prepare` 再在验证成功的 `UiTree` 上解析最终 key。

因此内联与局部变量两种正常 Rust 写法语义相同：

~~~rust
let leading = ui!(build {
    <ActionTarget action={Action::Back}>{ back_visual() }</ActionTarget>
})?;

ui!(build {
    <Row>{ leading }</Row>
})
~~~

I1 选择并实现了“携带 PlanBundle 的显式子视图值”。计划仍不写入 `UiNode`，因此不破坏 Kernel 的纯数据、快照或
身份边界；`FrameCoordinator::prepare` 也不再接收一个与 plan 分离的 `ViewBuild` 参数。`UiNode` 仍可通过
`ViewOutput::opaque` 作为没有 DSL plan 的 kit / legacy child 进入同一组合路径。

### 11.9 I2 已落实：远程 guest 的 `FrameToken` ABI

direct iOS 使用静态链接的 `MobileApp`，已经让 Target 在 `frame()` 返回 `(&UiFrame, u64)`（非零 `FrameToken` 的
ABI 友好表示），并只在 Metal 实际 `Presented` 后保存该值；触摸、键盘和 IME 再把它回传给 Application。远程 guest
现在采用同一个 provenance 原则，但使用 delivery ABI 自己的 `AppFrameToken`，不把 Composition 类型泄漏进 bundle 协议。

I2 采纳并实现原 B（版本化 breaking ABI）：

1. `tela-app-abi` packet version 已从 2 升为 3，bundle `ABI_VERSION` 已从 3 升为 4；旧 bundle 因 manifest ABI
   不匹配被拒绝，不能与新 Host 静默混用。
2. `AppEvent` 现在区分系统分支 `Viewport` / `ReplaceKeymapJson` 和帧输入分支
   `FrameInput { source_frame_token: AppFrameToken, input: AppFrameInput }`。`AppFrameToken` 基于 `NonZeroU64`，
   `0` 不能作为“未知来源”的伪 token。
3. `AppStatus` 发布 `Option<AppFrameToken>`。mobile guest 直接发布 `FrameCoordinator` 的 active token；desktop guest
   在每次成功 `ensure_frame()` 后递增自己的 delivery token。两者都在处理帧输入前验证来源，陈旧 token 不得进入
   pointer、key 或受控文本状态。
4. Android、Win32、macOS 与 WebView Host 分别保存最新逻辑 `frame_token` 和最后一次实际 `Presented` 的
   `presented_frame_token`。只有 renderer 成功提交后才更新后者；resize、surface lost 或关闭会清除它。后续
   pointer、key、IME 只能由该值编码为 `FrameInput`。
5. WebView 的 `WebAppStatus.frame_token` 映射为 `bigint | undefined`；浏览器壳不使用最新 status 直接发输入，
   而是在 `render_gpu()` 成功后把该次 frame/status 对应 token 保存为 `presentedFrameToken`。

该迁移已经由 ABI round-trip、mobile/desktop guest 的“viewport 生成新帧后拒绝旧 token 输入”回归、desktop/mobile
release WASM bundle 的 Wasmtime 初始化与 viewport 校验，以及 WebView host 的 wasm-bindgen 构建和 TypeScript
typecheck 覆盖。它关闭的是 remote ABI 的架构选择，不自动替代 D9 对所有应用 Host staging transaction 的更宽约束。

#### R1：真实 Target acceptance（未关闭，非架构待决）

| 编号 | 缺口 | 当前证据 | 需要的验收 |
|---|---|---|---|
| R1 | 当前 Linux 工作机无法完成 Android、Windows、macOS 的真实 surface 呈现与陈旧输入回归。 | ABI、guest WASM、WebView wasm-bindgen 和 Host 源码迁移已通过；`cargo-win32 check --target x86_64-pc-windows-gnu -p tela-target-win32` 及 `ops build win32` 均已通过。Android 项目私有 Rust 工具链存在，但未安装 `aarch64-linux-android` target；macOS shell 按平台约束不可在 Linux 运行。 | Android 真机、Windows、macOS 分别构建并运行；在成功 present 后触发一次状态更新，再注入旧 frame token 的 pointer / key / IME，确认 guest 不改变状态；随后注入当前 token，确认正常路由。 |

## 12. 已确认规则速查

| 主题 | 最终规则 |
|---|---|
| 视图执行 | 每帧重建纯 `UiNode` 树；无节点回调、无活组件实例。 |
| 子视图组合 | `ui!` 返回 `ViewResult<ViewOutput<A>>`。该值私有携带 `PlanBundle<A>`；嵌套 DSL child 会在父 body 中按真实 DFS 位置 rebase，普通 `UiNode` 则作为无 plan 的 opaque child。 |
| 业务动作 | Action 是纯值；副作用和 mutation 在 ActionHandler。 |
| Context | `@provide(value: Type)` / `@inject(name: Type)` 一律显式类型；只注入 owned static capability。 |
| 状态 | `AppState` 显式传入视图；禁止 `@inject(&mut AppState)` 或注入 Signal/runtime。 |
| `@watch` | `@watch(name, &signal)` 显式登记；顶层 watch 必须绑定到该 `ui!` 块的唯一真实根，计划树外保存，建树后用 `SemanticKey` reconcile。 |
| 身份 | 静态结构可用 AutoPath；动态项必须显式业务 key。`For` 的局部 key 经 `ItemKey` 转换、固定 collection scope 与内部 `KeySegment` 在 Kernel identity 解析期合成为最终 `SemanticKey`；不引入第二套 path 身份。 |
| 刷新 | V1 是整根帧重建；一批写入最多请求一帧。 |
| `@batch` | 不存在；在 handler 中调用 `runtime.batch(|| ...)`。 |
| DSL V1 | 只使用 `ui!(build { ... })`；提供结构标签、`For`、显式窗口 `VirtualList` 和 Rust 表达式逃生口。 |
| DSL 动作 | 透明 `ActionTarget` 将 `action={A}`、`on_input` / `on_submit` / `on_cancel` 锚定到唯一真实子根；`on_input` / `on_submit` 使用强类型 `fn(String) -> A`，`on_cancel` 是纯 Action 值，三个文本 trigger 都要求 input 根的 `bind_id: None`；可通过 `with_context` 绑定纯数据；Headless 仅是可选 adapter。 |
| Kit | 视觉组件仍是各 kit 的普通 Rust 构造器；不建立跨 kit recipe adapter。 |
| 活跃帧 | direct Host 已按 D9-B 预实现 candidate transaction 与 `FrameToken`；remote delivery ABI 已按 I2-B 迁移为 `AppFrameToken` + `FrameInput`，但 D9 的正式确认和 R1 真实 Target 验收仍是完成条件。 |
| 错误 | 缺 provider、重复 provider、未解析 watch 锚点返回结构化错误；不 panic、不静默降级。 |

D1-D8 已固化应用 DSL 的边界；当前实现已经完成 Browse / direct Host 的垂直验证，I1 已由 `ViewOutput` 关闭，I2-B
也已完成 ABI 迁移。D9 的正式确认与 R1 关闭后，再决定是否扩展到 Preview 或 desktop；现有 Headless 的重做或 adapter
不得阻塞这条主线。
