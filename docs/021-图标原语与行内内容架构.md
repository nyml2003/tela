# 021-图标原语与行内内容架构

> **状态：✅ 已实现。** 本文取代 019/020 中“`tela-widgets` 持有 Icon/`IconButton`、`IconLabel` 是最终组合”的过渡方案。它定义图标、行内内容和光学校正的长期边界；已关闭的问题归档见 [016](016-已解决问题归档.md)。

## 1. 目标与结论

图标不是 core 的新节点种类，也不是某个业务页面的文本 hack。它同时有三类不同职责：

1. **图标语义与来源**：同一个“文件夹”可以来自 iconfont、SVG、图片图集或平台原生资源；
2. **原子交互外壳**：按钮负责背景、按压、禁用、焦点、交互与默认身份；
3. **行内排版模式**：图标、文字、徽点、计数和任意小节点需要组合为一行。

因此长期结构为：

```text
tela-fonts ----> tela-text ----> GlyphInkMetrics
     |                                |
     +----> tela-icon <----------------+
                 | IconVisual { UiNode, IconOpticalMetrics }
                 v
            tela-core 的既有 Text / Image / 几何原语
                 ^                         ^
                 |                         |
     tela-widgets::Button             tela-ui::Text / InlineSlot / IconButton
                                               |
                                           tela-demo
```

- `tela-core` 只提供通用的 `VisualConcern::visual_offset`，不认识图标；
- `tela-icon` 拥有 `IconKey`、provider、资源特有映射和实际墨迹的光学度量；
- `tela-widgets` 拥有按钮等原子交互，不拥有图标来源或“图标 + 标签”布局；
- `tela-ui` 拥有可复用的行内组合模式；
- `tela-demo` 只将文件领域语义映射到通用 `IconName` 和领域颜色。

这条边界同时保证：普通组件和页面不管理 tela key；Raster、Canvas、WGPU 消费同一 `UiFrame`；更换图标来源不需要修改 core/renderer 帧协议。

## 2. 不采用的方案

| 方案 | 不采用原因 |
| --- | --- |
| `NodeKind::Icon` / `DrawPayload::Icon` | 会让每个 renderer、frame trace、clip 和测试都出现图标特例；iconfont 本质已可由 Text 表达。 |
| 将 `Icon` / `IconButton` 固定在 `tela-widgets` | 混合图标来源、按钮交互和行内排版，无法自然表达 suffix 或任意行内内容。 |
| 单独维护 `IconLabel` | 只能覆盖“一个图标 + 一段文字”，不能泛化到 prefix/suffix、状态点、计数、图片或未来 provider。 |
| 页面层手写 `y` 偏移 | 偏移会随字体、字号、行高、provider 和 renderer 漂移，也绕开统一测试。 |
| 用 `DrawPayload::Custom` 承载 SVG | 当前 Raster 与 Canvas 跳过 Custom；这会造成同一 DSL 的跨后端视觉分叉。 |

## 3. crate 职责与依赖

| crate | 公开能力 | 可依赖 | 明确不负责 |
| --- | --- | --- | --- |
| `tela-core` | 值树、布局、命中、焦点、draw 投影；通用 `visual_offset` | `tela-contract` | 图标语义、字体解析、provider、renderer 特例 |
| `tela-text` | 受控字体度量、覆盖事件、`GlyphInkBounds`、逻辑 `GlyphInkMetrics` | contract、fonts、`ab_glyph` | 图标 API、纹理、DPR 策略、UI 状态 |
| `tela-icon` | `IconKey`、`IconProvider`、`IconVisual`、`IconOpticalMetrics`、Material provider | contract、core、fonts、text | renderer、Button 状态、业务映射、key 管理 |
| `tela-widgets` | `Button`、输入控件、IME/受控值等原子交互 | contract、core、fonts | 图标来源、行内组合、业务命令 |
| `tela-ui` | `Text`、`InlineSlot`、`IconButton`、Toolbar 和其他分子模式 | contract、core、fonts、text、icon、widgets | renderer、领域 Store、tela key 管理 |

`ops check` 的 architecture gate 对 `tela-icon` 和 `tela-ui` 的真实 Cargo 依赖做白名单检查。`tela-icon` 依赖 core 的唯一目的，是把解析结果降低为已有 `UiNode`；core 不反向依赖它。

## 4. 公开模型

### 4.1 语义键与 provider

```rust
pub struct IconKey(String);

pub trait IconProvider {
    fn resolve(&self, request: IconRequest) -> Result<IconVisual, IconResolveError>;
}

pub struct IconVisual {
    // 私有：UiNode 与 IconOpticalMetrics
}
```

`IconName` 是当前 Material Symbols Rounded 受控子集的枚举，转换为来源无关 `IconKey`。码位映射属于 `MaterialIconFontProvider` 的私有实现，调用方不能依赖 Unicode codepoint；自定义 provider 可直接消费 `IconRequest`。

首个 provider 输出：

```text
IconKey("folder")
  -> MaterialIconFontProvider
  -> TextContent { font: FontRef("tela-icons"), text: material glyph }
  -> IconVisual { node, metrics }
```

`IconVisual` 既保留节点，也保留该来源测得的 `IconOpticalMetrics { box_size, ink_center_y }`。这避免 UI 层重新测字体或猜测偏移。

### 4.2 core 的唯一通用扩展：visual_offset

`VisualConcern::visual_offset` 是纯绘制位移。resolve 将其加到 draw command 的 geometry；若 payload 是 Text，也加到绝对 `baseline_y`。下列值必须保持原样：

- `LayoutBox`、Row/Column/Stack 尺寸和 scroll bounds；
- `HitRegion` 与点击坐标；
- key、默认焦点和状态归属；
- 祖先 clip 的逻辑矩形。

所以图标的可见轮廓可以微调，而点击目标仍是稳定的逻辑行盒。core 测试覆盖该不变量。

### 4.3 逻辑墨迹度量

`tela-text::glyph_ink_metrics(&TextContent)` 从受控字体 outline 得到逻辑坐标的 `GlyphInkMetrics`。它使用与 core 文本叶子相同的首行 baseline 规则：字体 ascent 先钳制到 line box，再将 outline 的 y-up 边界转换为 Tela 的 y-down 坐标。

它与 `GlyphInkBounds` 的职责不同：

| API | 坐标 | 用途 |
| --- | --- | --- |
| `GlyphInkBounds` | 物理像素，受 raster scale/覆盖像素影响 | Raster/WGPU 分配足够容纳溢出墨迹的纹理 |
| `GlyphInkMetrics` | 逻辑像素，不受 DPR/取整影响 | provider 计算光学中心和 `visual_offset` |

Provider 默认把图标墨迹中心放到图标逻辑盒中心。`Text` 与直接 `Icon` slot 组合时，会把目标中心换算到经过 `CrossAlign::Center` 后的图标局部坐标，再调用 `IconVisual::into_node_aligned_to_ink_center`。没有固定魔数，也不会用页面私有偏移。

## 5. 行内组件 API

### 5.1 Text 与 InlineSlot

没有 prefix/suffix 时，`Text` 直接生成一个 core Text primitive，不引入额外布局节点。有任一 slot 时，它生成一个 `CrossAlign::Center` 的单行 `Row`：

```rust
use tela_icon::{Icon, IconName};
use tela_ui::{InlineSlot, Text};

let label = Text::new("设计")
    .text_metrics(13.0, 18.0)
    .prefix(Icon::new(IconName::Folder).size(20.0))
    .gap(8.0);

let with_suffix = Text::new("同步完成")
    .suffix(InlineSlot::new(status_dot_node));
```

`prefix` / `suffix` 接受三种情况：

- `Icon` 或已解析的 `IconVisual`：保留 provider 的光学度量，得到与文字实际墨迹中心的对齐；
- `UiNode`：无需专用包装；
- 其他能构建为 node 的 core builder：显式用 `InlineSlot::new(...)`，避免泛型 `From` 与 Rust coherence 冲突。

`Text` 是单行公共模式，不替代富文本、多行折行或复杂表格布局。后者继续使用 core 文本原语和普通容器。

### 5.2 IconButton

`tela-ui::IconButton` 只组合，不复制状态机：

```text
IconButton
  -> Text { prefix: Icon, optional label }
  -> tela-widgets::Button::content(UiNode)
```

它直接使用 `tela_widgets::ButtonVariant`、`ButtonPalette`、`ButtonState`，因此 hover、selected、disabled、danger、交互根节点和 core 默认 identity 仍只有一份实现。仅图标场景直接给 Button 内容一个 `Icon` node；带标签场景必经 `Text` 的精确行内对齐。

## 6. key、局部状态与事件

图标、Text 和 IconButton 都只构建结构/视觉节点；它们不生成、保存或暴露 tela key。约 80% 的普通场景由 core 的默认身份和焦点策略管理。

特殊集合仍遵循既有例外：虚拟列表或 core 无法从结构可靠推导实体身份的情况，业务提供稳定 `semantic-id`；这不是图标组件的职责。按钮本地 pressed/hover 的视觉快照属于原子组件的局部交互，业务动作仍经 `UiAction` / `UiIntent` 回到上层容器。

## 7. provider 扩展路线

现阶段实现的是 Material iconfont。后续可加入：

1. **图片图集 provider**：输出已有 Image 节点并报告本身实际墨迹/可视边界；
2. **平台 provider**：由宿主预先将平台资源降低为确定的本地节点，不把平台句柄放入 `UiFrame`；
3. **SVG / 向量 provider**：先设计值语义 `VectorPath` 或 `Picture` primitive，完成 contract、core draw 投影、Raster、Canvas、WGPU、clip、frame trace 和像素测试后才允许输出它。

SVG 不能暂时放进 `CustomDraw`：Raster/Canvas 会跳过它，无法保证同一 DSL 的一致视觉结果。新的 provider 也必须报告 `IconOpticalMetrics`；不允许因为素材来源变化退回页面级 y 偏移。

## 8. 迁移与兼容策略

本次直接删除而非保留 deprecated shell：

- 删除 `tela-widgets::{Icon, IconButton, IconName}`；
- 删除 `tela-ui::IconLabel`；
- `tela-demo` 改为直接依赖 `tela-icon`，所有图标文字行收敛到 `tela-ui::Text`；
- `Toolbar` 改为消费 `tela-ui::IconButton`，复用 widgets Button 类型。

这是一套 workspace 内部 API，不存在外部兼容承诺。保留旧 re-export 会使调用方继续选择错误层，并阻断 provider 与行内 slot 的扩展。

## 9. 验收与门禁

自动化覆盖应至少证明：

- 每个内建 `IconName` 可由 Material provider 解析为 `tela-icons` Text 节点，未知 `IconKey` 被拒绝；
- `GlyphInkMetrics` 与 core 的首行 baseline 使用同一行盒语义；
- `visual_offset` 改变 draw geometry / Text baseline，却不改变 layout、命中与 clip；
- `Text` 无 slot 时保持单一 Text primitive；有 Icon prefix 或任意 suffix 时形成正确的行内 Row；
- `IconButton` 只有一个 widgets Button 交互根，且带标签时复用 Text；
- demo 的品牌、导航、工具栏、文件行在 frame/raster 级测试中验证实际墨迹中心；
- `ops check`、格式、workspace 测试与 wasm WebGPU compile 通过。

浏览器视觉验收仍由用户在已有页面进行；本实现不自行启动 Chromium。人工确认 Raster 与 WGPU 都使用同一页面 DSL，并检查带图标文本的视觉中心、FocusRing、键盘导航和全视口绘制。

## 10. 非目标

- 不在本次实现 SVG parser、图标在线下载、完整 Material Symbols 字库或图标主题切换；
- 不为图标引入业务 Store、全局状态、页面 key 或 renderer 特例；
- 不将 `Text` 扩展成富文本/多行排版框架；
- 不以单一 renderer 截图或浏览器自动化替代跨后端代码与门禁验证。
