# 012-业务数据绑定（BindId）

> **状态：历史设计记录。** 本文的 `BindId`、`UiAction::ValueChange` 与 `tela-widgets`/`tela-ui`
> 分层已随 036 事件系统重构删除（当前 contract 中已无这些类型；受控输入经 `InteractConcern.input`
> 与组件 Output/AppCommand 表达）。单向数据流与"视图状态/业务状态隔离"两条底线仍然有效；
> 现行事件与组件生命周期基准见 [036-事件系统与组件生命周期机制梳理](036-事件系统与组件生命周期机制梳理.md)。

> 业务数据响应式绑定的完整方案：基座只提供**纯类型契约**（`BindId` + `UiAction::ValueChange`），响应式运行时、双向同步全部封装在上层组件套件与宿主，core 保持纯函数、零副作用。`tela-widgets` 提供原子控件和基础绑定/IME，`tela-ui` 提供组合组件及 `UiIntent` 命令出口；组件局部草稿、批处理与后续调度边界见 [015](015-tela-ui与局部交互状态.md)。

## 1. 架构底线（不变）

1. **单向数据流**：业务数据完全归宿主持有，`tela-core` 只接收宿主传入的数据快照渲染 UI。
2. 基座**不内置响应式/Signal/订阅系统**，无运行时副作用，`resolve` 保持纯函数，离线快照、多环境渲染一致性不受破坏。
3. **两类状态严格隔离，互不干扰**：
   - **视图临时状态**（焦点、光标、滚动、弹窗）：存 `ViewStateStore`，靠 `node_id`/`semantic_key` 匹配（见 [004-更新策略与状态保持](004-更新策略与状态保持.md)）；
   - **业务表单状态**（输入值、勾选、下拉选中）：全部存宿主，靠 `BindId` 建立控件与业务字段映射。

## 2. 契约层最小改造（tela-contract，仅纯类型）

- 新增 `BindId` 唯一绑定标识，挂载至 `InteractConcern` 交互槽（见 [003-场景树与节点模型](003-场景树与节点模型.md)）。
- 标准化 `UiAction` 动作枚举，统一携带 `BindId` 承载业务变更：
  - `UiAction::ValueChange(BindId, Value)`：通用值变更（`Value` 为类型化载荷：字符串/数字/布尔/枚举）；
  - 滚动、模态、焦点等**纯视图动作不带 `BindId`**，走原有 `node_id` 链路。
- **无映射、缓存、订阅逻辑**：core 仅透传标识，不读写宿主业务数据。

## 3. 上层组件层（tela-widgets / tela-ui）

- `tela-widgets` 提供 `Button`/`Input`/`InputNumber`/`Checkbox`/`Radio`/`Switch` 等原子控件；它们接收受控值与可选 `BindId`，不持有业务 Store。
- `tela-ui` 组合这些原子控件形成 `Form`、`Table`、`Select`、`Cascader` 和 `Toolbar` 等通用模式；它不持有业务 Store。
- `BindId` 用于受控值变更，`UiIntent` 用于组合组件命令激活：两者都只是宿主路由值，均不是 tela key。动态集合若声明 `auto-stable-identity`，core 可以把稳定的 `BindId` 当作节点内容特征参与内部身份分配；它不会变成 `semantic_key`，组件和业务仍不保存或传递 tela key。
- 宿主与组件协作完成：
  1. 读取 `signal.get()` 提取快照生成节点内容；
  2. 在组件 prop 中声明对应 `BindId`；
  3. 捕获 core 抛出的 `ValueChange`，由宿主 Dispatcher 更新对应 Signal。
- 自动生成 `BindId` 与自动 Signal 同步糖尚未实现；业务可将绑定路由集中在一个 Dispatcher，避免分散匹配逻辑。

## 4. 宿主层实现（游戏/Wasm/离线测试各自适配）

- 宿主可使用 `tela-widgets::Signal`，或自行定义兼容的响应式变量；组件套件提供的是可选的单线程 Signal，不强制统一 Signal 库。
- Signal 变更后，宿主主动组装完整数据快照，调用 `tela.build()` 驱动 UI 刷新。
- 统一全局动作分发逻辑：集中处理 `BindId` 与 `UiIntent`，新增表单控件不应分散修改页面 View。
- 虚拟列表场景可**拼接 `semantic-id` 生成行级唯一 `BindId`**，滚动增删数据不会丢失字段映射关系。

## 5. 完整闭环数据流

1. 宿主 Signal 更新 → 组装业务快照传入基座；
2. core 根据快照生成携带 `BindId` 的 UiNode 树，完成布局渲染；
3. 用户操作控件 → core 输出带 `BindId` 的 `ValueChange` 动作；
4. 宿主/绑定组件捕获 `ValueChange`，通过 `BindId` 匹配对应 Signal 执行更新；`tela-ui` 的
   `UiIntent::Invoke` 则由宿主 Dispatcher 映射为业务命令；
5. Signal 变更触发新一帧渲染，形成双向同步闭环。

## 6. 方案核心收益

1. **架构无损**：不破坏 core 纯函数、无副作用、多环境统一的核心设计，不侵入底层渲染/更新管线；
2. **开发高效**：上层封装绑定组件，业务无需重复编写事件匹配、同步样板代码；
3. **扩展性强**：统一 `BindId` 支撑静态表单、动态列表、虚拟列表、批量表单校验/重置通用能力；
4. **环境兼容**：宿主可自由选用自身响应式实现，不强制统一 Signal 库，离线测试可 Mock 静态数据；
5. **分层解耦**：底层只提供标准契约，响应式、双向同步能力全部封装在上层，可按需选用，简单静态页面无需引入绑定能力。

## 7. 边界约束（防止架构退化）

1. `core`、`adapter` **禁止引入任何订阅、观察者、Effect 响应式运行时**；
2. `BindId` 仅用于业务字段双向同步，**不接管滚动、焦点等纯视图状态**；
3. UI 组件不持有业务数据，仅做数据展示与变更意图抛出，**数据唯一可信源为宿主**。

## 8. 规则

- ✅ `BindId` 挂 `InteractConcern`，`UiAction::ValueChange(BindId, Value)` 为唯一业务变更通道；纯视图动作不带 BindId。
- 🔧 core/adapter 禁响应式运行时；响应式实现（Signal）只允许出现在宿主与 `tela-widgets` 上层。
- 🔧 业务状态与视图状态严格隔离：ViewStateStore 只存视图临时状态，业务表单状态一律宿主持有。
- 🔧 虚拟列表行级 `BindId` 由 `semantic-id` 拼接生成，滚动增删不丢映射。
