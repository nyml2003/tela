# 001-痛点与目标

## 1. 为什么要有这套基座

现实中存在四类形态差异很大的界面，却共享大量底层能力：

| 形态 | 场景 | 渲染环境 | 输入模型 | 更新节奏 |
|---|---|---|---|---|
| 游戏 HUD | 血条、技能栏、对话 | 游戏引擎叠加层 / 3D 贴图 | 主机手柄 + 部分指针 | 整体刷新、动画多 |
| 游戏内编辑器 | 地图/数据编辑面板 | 游戏引擎窗口内 | 指针 + 键盘 | 高频局部改动 |
| B 端 CRUD 后台 | 表格、表单、弹窗 | 浏览器画布 | 键盘 + 指针 + 输入法 | 表单单元格级增量 |
| C 端交互页 | 卡片、列表、导航 | 浏览器画布 | 键盘 + 指针 + 触摸 | 列表滚动、局部更新 |

如果四类界面各自造轮子，会重复实现布局、绘制、命中、滚动、焦点，且行为不一致。tela 的目标是把这些**与业务无关**的底层能力收敛成一套基座，四类界面共享同一份界面描述与行为。

## 2. 基座要解决的核心矛盾

1. **一套描述、多环境一致**：同一棵树在游戏引擎内嵌、浏览器画布、离线渲染下，布局与交互行为保持一致；平台不支持的特效优雅降级，不崩溃。
2. **性能与易用不可兼得的取舍**：游戏类界面要整体重建（简单、动画友好），表单类界面要局部增量更新（高频局部改动成本低）。两种模式必须能同树共存，且组件代码无需感知。
3. **状态归属要清晰**：业务数据在宿主，UI 只持视图状态（焦点、光标、滚动、弹窗）。否则基座必然滑向"业务逻辑写进 UI"。
4. **可嵌入、不夺权**：基座不接管主循环、不独占窗口，嵌入方决定何时 tick、何时重绘、渲染到哪里。

## 3. 定位

- 一套**与业务无关**的底层 UI 基础设施。
- UI 只负责**界面渲染与用户交互采集**，不执行业务逻辑、IO、网络、存储。
- 所有副作用（指令执行、数据读取、资源加载）全部交给外部宿主。
- 基座提供绘图原语，**不内置业务组件**；组件套件由上层构建。

## 4. 成功判据（验收层面）

| 判据 | 说明 |
|---|---|
| 同树同环境必同帧 | 相同输入树 + 相同 viewport 必定得到相同的绘制命令与命中区域，可离线复现 |
| 模式切换零成本 | 同一组件代码不加修改即可运行在整体重建或局部 Dirty 子树下 |
| 环境降级不崩溃 | 不支持的特效被裁剪或降级为最近似效果，不 panic、不黑屏 |
| 业务零 UI 基础设施负担 | 数据驱动列表不强制构造 UI 专用 key：普通列表由 `auto-stable-identity`/`semantic-id` 覆盖，虚拟列表显式复用业务 ID（`semantic-id`）即可，无需为 UI 造 key |
| 宿主零侵入 | 嵌入方只提供 `Host` 实现，不需要改基座核心 |

## 5. 非需求（明确不在基座范围）

1. 不内置任何业务组件（按钮/输入框/表格等由上层组件套件实现）。
2. 不内置业务专属视觉特效。
3. 不提供网络、存储、路由、表单校验能力。
4. 不绑定任何业务项目。

## 6. 与现有系统的关系

本基座的设计参考了 `pokemon-untitled` workspace 中 `punctum-ui` 的思路：渲染器无关的像素 UI 树 → 有序绘制命令与命中区域，树为值语义、`resolve` 为纯操作。tela 在此基础上泛化：

- 布局以 `Row`/`Column`/`Wrap`/`Frame`/`Expanded`/`Spacer`/`BaselineRow`/`Stack`/`Overlay` 等单职责原语组合；每个源节点在一次 resolve 内只测量一次；
- 引入子树级更新策略（整体重建 / 局部 Dirty）与 key 身份策略；
- 引入规约式焦点转移（组件树 + 焦点图，无空间导航）与嵌套模态栈；
- 引入多后端渲染抽象（wgpu / 浏览器 canvas / 软件光栅）与宿主接口。

tela 是全新独立项目，不复制 punctum-ui 代码，仅复用其已验证的架构思路。

## 7. 规则

- 🔧 UI 核心 crate 禁止 `unsafe`，禁止依赖窗口、文件、网络、真实时间或平台 API。
- 🔧 平台相关能力一律通过 `Host` 接口注入，核心不得反向依赖后端。
- 🔧 系统间可共享数据契约与端口，但绝不共享状态与实现。
