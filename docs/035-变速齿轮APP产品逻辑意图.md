# 变速齿轮 APP 产品逻辑意图

> 状态：开发基准稿；主链路已实现，真实 Windows 目标验收待完成
>
> 平台：Windows x64
>
> 形态：独立桌面应用，不是编辑器内的页面
>
> 框架事件、组件状态和帧提交规则以
> [036-事件系统与组件生命周期机制](036-事件系统与组件生命周期机制梳理.md) 为准。

## 1. 产品定义

“变速齿轮”用于对一个已经运行的 Windows x64 进程调整时间流逝速率。用户从当前可访问的进程中选择一个目标，显式建立连接，然后在应用运行期间实时调整速率。

它首先是一个可预期的操作工具，而不是在用户未确认时自动影响目标，或尽可能绕过系统限制的工具。所有会影响外部进程的动作都应当有明确的目标、状态和用户意图。

## 2. 首版边界

首版只面向 Windows x64 进程，并且一次只允许控制一个目标。

应用应列出当前用户权限范围内可识别、可访问的 x64 进程，优先展示拥有可见顶层窗口的普通应用。应用自身、系统关键进程、受保护进程、架构不兼容进程和当前权限无法访问的进程不作为可操作目标。

应用不主动提权，不尝试绕过系统保护、反作弊或目标进程的安全边界。当权限或兼容性不满足时，产品应当明确告知原因，而不把失败表现为无反应或伪成功。

## 3. 核心使用流程

完整操作流程分为五个明确阶段：

1. 应用加载当前可用进程，用户可搜索和刷新。
2. 用户把一个进程移入目标区，此时只是选择，不会改变目标进程。
3. 用户明确执行连接，应用建立对目标的调速能力并验证其可用性。
4. 连接成功后，速率控件可用，用户的调整实时作用于当前目标。
5. 用户停止连接、关闭工具或目标结束后，应用恢复可预期的安全状态。

“选择”和“连接”必须是两个不同的用户动作。用户把进程移到目标区时，不发生隐式连接、注入或调速。这个安全间隔能够避免搜索、误点或列表刷新直接修改外部进程。

## 4. 进程选择

进程选择使用双栏 Transfer 交互。左侧是可用进程，右侧是当前目标。右侧最多保留一项，选择新目标时应当清晰表达对原目标的替换，不出现同时控制多个进程的中间态。

每个进程项至少要让用户能够识别应用名称、进程标识和可用状态。有可见窗口的进程优先排列，其他可访问进程仍可被搜索到。

进程列表定期自动刷新，默认节奏为两秒，并且提供明确的手动刷新动作。刷新时应尽量保留仍然有效的搜索词、勾选和目标选择，不应因为列表数据更新而让整个操作面板跳回初始状态。

进程标识不能只依赖一个可能被系统复用的数字。应用必须能区分“原目标已经退出”和“一个新进程刚好获得了同一数字标识”，避免把旧连接意图误用到新进程。

## 5. 连接语义

未选择目标时，连接动作和速率控件均不可用。已选择但尚未连接时，用户可以更换目标，但任何速率值都不得被表现为已经生效。

用户发起连接后，应用进入明确的处理状态，防止重复连接、目标切换与速率更新互相竞争。这一过程不应阻塞窗口消息循环，用户仍然能够看到进度、移动窗口和获得失败反馈。

连接首先以正常速率建立，并验证目标中的调速能力确实可用。只有这个验证完成后，产品才显示为已连接并启用实时速率调整。

连接失败时，应用回到可重试或可更换目标的状态。失败信息应当区分目标已退出、权限不足、架构不兼容、调速能力无法建立和通信失败，使用户能够知道下一步是重试、更换目标还是停止操作。

## 6. 速率控制

速率范围为正常速率的四分之一到四倍。数值分布采用以正常速率为自然中心的对数感知，让“减半”和“翻倍”在滑块两侧拥有对称的操作距离。

界面提供一个实时滑块，并提供四个高频预设：半速、正常、两倍和四倍。预设和滑块是同一个已生效速率的两种操作方式，它们的高亮、数值显示与目标实际状态必须一致。

拖动滑块时，新速率实时发送给当前目标，不需要额外提交。如果某次速率更新失败，界面不应继续假定新值已经生效，而应展示已确认的最后状态与错误。

改变速率时，目标所观察到的虚拟时间应当连续。无论从慢速切到快速、从快速恢复正常，还是停止连接，都不应让目标时钟突然向前或向后跳变。

## 7. 调速的作用范围

首版只调整目标进程通过高精度性能计数查询所观察到的时间流逝。这一边界必须在产品中清晰、稳定，不宣称对目标的所有时钟、休眠、等待或多媒体计时都有效。

这意味着实际效果取决于目标进程如何计时。对于依赖其他时钟、外部服务器时间、音频时钟或自定义计时机制的应用，变速效果可能不完整、不一致或没有效果。界面应当把这一点作为兼容性边界，而不是在连接成功后暗示完整兼容。

## 8. 停止、关闭与异常恢复

用户执行停止后，目标的时间速率恢复为正常，并且从当前虚拟时间连续向前运行。停止是对调速效果的终止，不要求在目标运行期间卸载已建立的目标内能力。

用户关闭变速齿轮时，行为与显式停止一致：目标恢复正常速率，不产生时间跳变。

如果控制端异常结束、失去响应或长时间无法继续通信，目标端应当自行回到正常速率。不能把安全恢复完全依赖于控制端有机会执行退出清理。

同一目标仍在运行时，后续重新连接应当可以复用目标中已建立的能力，并在正常速率基线上重新确认状态。应用不为追求“完全无留存”而在运行中强行卸载，因为这会引入与目标正在执行的线程和计时调用之间的竞争。

## 9. 目标结束

连接期间如果目标进程结束，应用应立即结束已连接表象，将速率显示重置为正常值，禁用调速操作，并明确告知用户目标已退出。

定期刷新时，已退出目标不应因为数字标识被复用而自动转移到新进程。原目标不再存在后，用户需要重新选择并显式连接。

## 10. 产品状态

界面应当始终能回答两个问题：当前目标是谁，当前调速是否真的生效。

| 产品状态 | 用户看到的意义 | 允许的主要操作 |
|---|---|---|
| 无目标 | 尚未选择进程 | 搜索、刷新、选择 |
| 已选择 | 已确定目标，但未改变它 | 更换目标、发起连接 |
| 正在连接 | 正在建立并验证调速能力 | 等待结果，保持窗口可响应 |
| 已连接 | 显示的速率已被目标确认 | 实时调速、使用预设、停止 |
| 连接失败 | 本次没有建立有效调速 | 重试、更换目标、查看原因 |
| 目标已退出 | 原连接已终止，不再有可控目标 | 刷新并重新选择 |

用户的拖动值、正在发送的值和目标已确认的值不能被混为一个模糊数字。界面可以快速响应操作，但只有确认成功的值才能代表外部事实。

## 11. 界面意图

应用采用安静、紧凑、以扫描和重复操作为导向的 Windows 工具界面。界面不使用营销页式的大标题、装饰性卡片或大面积单一色彩，而是让进程选择、当前连接和速率操作在首个窗口中都清晰可见。

页面的主要区域为：

- 可复用的 Windows 应用标题栏，承担窗口拖动、最小化、最大化与关闭。
- 进程选择区，包含双栏列表、分别搜索、刷新与清晰的不可用原因。
- 连接区，显示当前目标身份、连接状态、主操作和紧邻的错误反馈。
- 速率区，包含当前已生效倍率、实时滑块、高频预设与兼容性状态。

状态反馈应就近出现，不通过一层套一层的卡片或频繁弹窗来表达普通进度。主操作在对应状态下应有明确的可用性，用户不需要靠尝试点击来猜测当前是否能连接或调速。

进程列表、Transfer 双栏、滑块与图标按钮需要稳定尺寸，不因加载、错误、长进程名或鼠标悬停而跳动。所有主要操作应支持键盘焦点与明确焦点外观，长列表在高 DPI 和较小窗口下仍可滚动使用。

## 12. 应用状态与组件状态的边界

应用只管理对外部行为有意义的业务事实：当前目标、连接阶段、已确认速率、正在执行的任务与用户需要看到的错误。

Transfer 的左右搜索词、尚未移动的临时勾选、列表交互中间态等属于组件自身。只有最终目标键集合向应用输出。

同样，滑块拖动的指针中间态属于滑块，而需要发送给外部进程并得到确认的倍率属于应用。这一边界既避免把组件细节泄漏给全局，也避免组件隐藏一个事实上已改变外部进程的业务值。

## 13. 明确不做的事

首版不包含：

- 同时控制多个目标进程。
- 自动选择、自动连接或在 Transfer 移动时立即修改目标。
- 提权、绕过受保护进程、对抗反作弊或隐藏调速行为。
- 兼容 32 位目标或非 Windows 平台。
- 覆盖目标的所有时钟、休眠和等待语义。
- 在目标运行期间强行卸载已建立的调速能力。
- 速率曲线录制、宏、预定时任务、多目标编组或远程控制。

这些能力未来只能在有清晰用户需求、安全边界和可验证的失败语义时单独讨论，不作为首版架构的预留承诺。

## 14. 当前实现基线

后续开发必须从当前主链路继续，不重新引入产品专用的事件或状态通道：

- 应用已是独立的 Windows 窗口，标题栏、Transfer、连接区、倍率预设和滑块已进入统一声明式组合链路。
- 进程枚举、x64/权限/保护状态分类、可见窗口排序与“进程号 + 创建时间”身份已建立。
- 选择、连接、等待握手、已连接、失败、停止和目标退出已是显式产品状态。
- 目标端能力通过共享状态进行初始化确认、倍率更新和心跳安全恢复；未握手成功前不对外宣称已连接。
- Transfer 的搜索词和临时勾选由组件实例持有；应用只接收最终目标集合。滑块的指针中间态也不进入应用业务状态。
- 普通测试、架构门禁、WGPU 回读和 Windows release 交叉构建可以证明可构建性与可移植语义；它们不证明已完成真实目标连接、调速和异常恢复。

## 15. 后续开发顺序

开发以“先证明外部效果，再扩展产品表面”为顺序：

1. 建立可观测的 Windows x64 验收目标，分别记录真实时间和高精度性能计数时间，先证明半速、正常、两倍、四倍及中间倍率。
2. 验证连续性与恢复：连续切换倍率、显式停止、正常关闭、控制端异常终止和目标退出都不得留下错误倍率或虚假连接状态。
3. 验证目标身份和竞态：进程号复用、刷新与连接交错、连接中更换目标、更新倍率失败都必须回到可解释的状态。
4. 完成真实窗口交互验收：标题栏、DPI、键盘焦点、Transfer 搜索与滚动、滑块拖动、长进程名和错误文案必须在真实 Windows 上可见、可操作且不重叠。
5. 只有上述主链路稳定后，才讨论扩大时钟覆盖、更多倍率策略或其他首版外功能。

每个新需求都先确认它属于业务事实、组件私有中间态、Host 能力还是目标端协议。无法用 `ui!`、通用组件或现有 Host 契约表达时，必须把它记为框架缺口并先讨论，不在应用中增加字符串路由、全局临时状态或专用 Host 分支。

## 16. 开发完成条件

后续任务不以“页面能显示”或“产物能构建”作为单一完成条件：

- 产品状态变更必须有领域测试，失败路径必须证明不会提前覆盖已确认事实。
- 组件交互必须证明私有状态跨帧保留，且旧帧输入和失败候选帧不能污染当前状态。
- Windows 代码变更必须通过 release 交叉构建；涉及 renderer 的修改必须在对应的 WGPU 环境验证。
- 涉及连接、调速、时间连续性、心跳或窗口交互的修改，必须补真实 Windows 证据；未执行时明确标记未验收。
- 框架或公共组件变更必须证明它不是变速齿轮的特例，并回写 036 中的通用规则或缺口结论。

## 17. 验收意图

产品需要在真实 Windows x64 环境中证明以下行为：

- 进程列表能正确过滤、排序、搜索、手动刷新和定期刷新。
- 进程刷新不会把旧目标误认为复用数字标识的新进程。
- 把进程移入目标区不会对目标产生任何影响，只有显式连接才开始外部操作。
- 连接以正常速率建立，未验证成功前不启用调速控件。
- 半速、正常、两倍、四倍与范围内的中间值能实时生效，界面显示与目标已确认状态一致。
- 任意速率切换、恢复正常与停止连接都不造成目标虚拟时间跳变。
- 显式停止、正常关闭和控制端异常结束都能使目标回到正常速率。
- 目标主动退出时，应用及时离开已连接状态，不把调速动作发往新进程。
- 权限不足、架构不兼容、目标受保护和通信失败都有可区分、可操作的反馈。
- 只使用高精度性能计数计时的验收目标按预期变速，使用其他时钟的对照目标不被误改。
- 窗口标题栏、高 DPI、键盘焦点、长列表滚动、进程名截断和各种加载与错误状态在真实窗口中无重叠、无布局跳动且可完整操作。

本地逻辑验证、交叉构建成功和产物可生成，都不等价于真实 Windows 目标已经完成连接、调速与异常恢复验收。
