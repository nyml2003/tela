行业组件、业务工作流或 Target 原生验收伪装为已完成。

### 0.2 这次要解决的问题

当前已有的 foundation、desktop-kit 和 mobile-kit 只能证明首批组件可以组合出界面，不能自然扩展到
表单、数据展示、导航、浮层和移动端触摸交互的完整目录。若继续把交互语义、视觉样式、状态保存和业务
命令混在各 kit 内，会出现四个长期问题：

1. 同一个交互行为在 desktop 与 mobile 中重复实现，且行为细节漂移。
2. Signal、局部组件状态和业务 Store 的拥有者不清晰，难以判断一次更新应使谁失效。
3. BindId 同时承担字段绑定和命令编码，会使通用组件依赖某个演示应用的协议。
4. Kernel 的输入能力只覆盖鼠标式点击和滚动，无法为 Swipe、PullRefresh、Picker、Overlay 等组件提供
   可验证的底座。

因此，本次不是继续往现有三个 crate 里堆组件，而是先重排能力边界，再以可计数、可测试的目录扩展组件。

### 0.3 明确不做

| 不做的事 | 原因与边界 |
|---|---|
| 业务、行业或电商组件 | 不引入 SKU、优惠券、地址、联系人、订单、支付、物流等领域模型；它们由外部应用基于通用组件组合。 |
| 无障碍语义 | 本阶段不提供 role、可访问名称树、屏幕阅读器桥接或辅助技术焦点同步；不得用空属性伪装为已支持。 |
| 动效系统 | 本阶段只保证交互状态转换正确，不引入缓动、时间线、过渡或手势惯性动画框架。 |
| 组件展示应用 | 不新建 gallery，也不把业务 demo 改造成组件陈列页；组件质量由库测试、树测试和 Raster 参考快照保证。 |
| shadcn 式源码分发 | 不做 registry、CLI、复制源码或 ejection；Tela 只发布编译后的 crate 与公开主题 token。 |
| 跨平台业务视图复用 | 业务视图由 desktop/mobile 应用分别组合；共享的是 Contract、Headless 语义和适当的视觉原语，而不是以平台判断分叉的页面代码。 |

## 1. 已决策结论

| 主题 | 决策 |
|---|---|
| 组件规模 | 建立 114 个通用根组件族，覆盖 Ant Design 式桌面工作台常见能力与 Vant 式移动交互常见能力。 |
| 新 crate | `tela-ui-headless` 承载 Root/Part 组合和组件事件路由；`tela-ui-dsl` 承载 Application Composition，不依赖 Headless、视觉 kit、Renderer 或 Target。 |
| Signal | Signal<T>、ComponentRuntime、ActionRegistry 与 `ui!` 位于 `tela-ui-dsl`；Application 持有业务 Signal，Headless 不再持有通用状态运行时。 |
| 失效模型 | 由 DSL 的显式 `@watch` 和 `SemanticKey` reconcile 建立订阅；不做隐式依赖收集。 |
| 状态归属 | 应用拥有业务状态和 Signal；组件读取快照、发出类型化事件。组件不得私藏业务状态。 |
| 事件路由 | BindId 只服务表单字段值绑定；新增 EventRegistry，将帧内 UiAction 和稳定 ComponentPartPath 路由为类型化 HeadlessEvent。 |
| 双 Kit | desktop-kit 与 mobile-kit 是不同的视觉和交互形态，实现不同的内置 recipe；二者复用行为语义，不承诺视觉完全一致。 |
| 主题 | 对外公开 DesktopTheme 与 MobileTheme 的语义 token；recipe 留在 kit 内部，不开放外部 recipe trait。 |
| Kernel | 补足 Grid、锚定浮层、原始多指针、指针捕获、手势仲裁、输入类型和文本截断等通用能力。 |
| 迁移 | 干净的破坏性迁移：所有 app 和测试直接切到新 API，删除旧 Signal 导出、ui.invoke: 命令编码和兼容别名。 |
| 验收 | 不以 demo 或 gallery 代替验证；每个根组件族进入契约测试矩阵，关键视觉进入 Raster 参考快照。 |

## 2. 新的逻辑结构

组件体系以五个正交维度组织。一个“Button”不再是一段同时决定业务、状态、输入、视觉和平台的代码，
而是这五个维度的一次受控组合。

| 维度 | 回答的问题 | 唯一拥有者 | 不应混入的内容 |
|---|---|---|---|
| 业务状态 | 当前值、数据源、提交后做什么？ | Application / Controller | kit、Kernel、Renderer |
| 组件行为 | 什么算选中、展开、关闭、取消、拖拽？ | tela-ui-headless 与 Kernel | 颜色、字体、业务命令 |
| 应用组合 | 视图如何声明依赖、订阅状态、组合 Action？ | tela-ui-dsl | 视觉 recipe、Headless 业务语义、Target 生命周期 |
| 输入与帧 | 指针如何命中、谁捕获、谁滚动、焦点如何移动？ | Contract + Kernel | 平台手势预判、业务字段含义 |
| 视觉 recipe | 部件长什么样、间距和触控尺寸是多少？ | desktop-kit / mobile-kit | 平台 API、业务状态 |
| 平台接入 | GUI 循环、Surface、坐标、IME、生命周期如何接入？ | Target Host | 通用组件行为、主题分支 |

这张图的关键不是“所有层都共享同一份代码”，而是依赖方向始终单向：

1. Kernel 只认识通用树、约束、输入、焦点和帧，不认识 Button、Dialog 或 Theme。
2. Headless 只认识组件语义和组件事件契约，不认识圆角、阴影、字体、Metal、UIKit、Android View 或 Application Signal runtime。
3. kit 只把 Headless 的部件映射为视觉节点和本 kit 的 token，不读取业务 Store。
4. Application 通过 `tela-ui-dsl` 组合 kit、持有 Signal、处理类型化事件，因而是唯一可决定业务含义的一层。
5. Target 只标准化宿主能力；不得在共享 UI 或 Host 代码中以 if mac、if ios、if win32 选择产品行为。

## 3. crate 与职责

### 3.1 新旧 crate 的责任重排

| crate | 重构后的职责 | 可以依赖 | 禁止依赖 |
|---|---|---|---|
| tela-contract | 跨层值类型、原始输入、UiAction、BindId、HostPorts、帧与资源协议 | 无 Tela 上层 crate | core、UI、Renderer、Target、Application |
| tela-core | 树解析、布局、命中、焦点、指针捕获、手势仲裁、帧生成 | tela-contract | 所有 UI crate、Renderer、Target、业务 crate |
| tela-ui-headless | 受控组件语义、Root/Part 模型、EventRegistry、HeadlessEvent | contract、core | foundation、desktop-kit、mobile-kit、Renderer、Target、业务 crate |
| tela-ui-dsl | Application Context、Signal、ComponentRuntime、ActionRegistry、候选帧协调与 `ui!` macro re-export | contract、core、tela-ui-dsl-macros | Headless、foundation、kit、Renderer、Target、业务 crate |
| tela-ui-foundation | Box、Text、Icon、Image 等共享视觉原语，以及共享视觉 token 和资源适配 | contract、core | headless、kit、Target、业务 crate |
| tela-ui-desktop-kit | 桌面密度、键鼠优先交互、DesktopTheme 和内置桌面 recipe | headless、foundation、core、contract | mobile-kit、Target、业务 crate |
| tela-ui-mobile-kit | 触控尺寸、页面导航、MobileTheme 和内置移动 recipe | headless、foundation、core、contract | desktop-kit、Target、业务 crate |
| Application | 业务数据、Signal、路由、异步副作用、具体产品视图组合 | tela-ui-dsl 与所需 UI crate | 将业务模型反向放回 UI crate |

任何残留在 foundation 或 Headless 中的 Signal / ComponentRuntime 都必须迁移到 `tela-ui-dsl`。迁移完成后，
foundation 只保留视觉基础能力，Headless 只保留组件契约；不能为了“方便导入”再从任一 UI crate 重导出 Signal，
也不能让 kit 提供第二套状态容器。

### 3.2 Headless 不是“只返回 UiNode 的工具函数”

Headless API 的公开表面以具名语义组件和部件为中心：

| 层次 | 形式 | 例子 | 责任 |
|---|---|---|---|
| Root | Tabs.Root、Dialog.Root、Select.Root | 持有受控快照、声明状态机与整体约束 | 规定组成与交互语义 |
| Part | Trigger、Content、Item、Label、Description、Close | Tabs.Trigger、Dialog.Close | 为一段视觉子树附着稳定角色和行为 |
| Event | Select、OpenChange、ValueChange、Dismiss、Cancel | SelectEvent::Select | 把底层动作转换为组件域事件 |
| Kit recipe | DesktopTabs、MobileTabs | 同一 Tabs.Root 的两种表达 | 决定视觉结构、尺寸和显隐策略 |

UiNode 仍然是 Kernel 与 Renderer 的通用节点接口，但它不是让每个调用者重新手写组件状态机的 Headless
公开模型。调用者应组合 Root 和具名 Part；kit 负责将这些 Part 渲染成当前形态的 UiNode 树。

例如，Tabs 的三个 Trigger 可以在 desktop-kit 中表现为带下划线的水平标签，在 mobile-kit 中表现为
触控尺寸更大的分页导航；两者的 selected、disabled、键盘/手势选择与 Select 事件语义应来自同一个
Headless Tabs 合约。

## 4. 状态、Signal 与局部运行时

### 4.1 Signal 的唯一位置

Signal<T> 是 Application 层持有的显式可观察状态，不是 kit 私有的便利对象。业务状态、当前选项、表单值、
筛选条件、是否打开等可影响产品含义的状态都由应用创建并持有：

~~~rust
// 示意 API，不是当前已存在的签名。
let selected_tab = Signal::new(TabKey::Overview);
let dialog_open = Signal::new(false);

runtime.watch(SemanticKey::from("settings.tabs"), &selected_tab);
runtime.watch(SemanticKey::from("settings.dialog"), &dialog_open);
~~~

组件构建时读取快照；事件处理器在 Application 中更新 Signal。组件本身不得因为收到 Click 就直接修改业务
Store，也不得通过隐藏的静态变量保存选中项。

允许保留的局部瞬时状态只有与视图生命周期绑定、且不携带业务含义的状态，例如：

- 指针捕获、拖动起点、手势竞争结果；
- IME composition、光标、临时选择区；
- 焦点、滚动位置、弹层定位计算缓存；
- 组件实例可恢复所需的短生命周期交互状态。

这些状态分别属于 Kernel 的 ViewStateStore 或明确的 ComponentRuntime 运行时槽位，必须以已解析的稳定
SemanticKey 定位，且不能成为绕开 Application 的第二业务状态源。

### 4.2 显式 watch，而不是隐式依赖收集

不采用“在 render 时读取过 Signal 就自动订阅”的模型。ComponentRuntime::watch 保持显式，原因是：

1. 可从代码直接判断一个 Signal 更新会使哪些稳定身份（`SemanticKey`）失效。
2. 组合组件的复用不会悄悄把外部状态纳入订阅图。
3. 批量更新可以按已登记的 `SemanticKey` 合并，而不是依赖运行期读取轨迹。
4. 未被 watch 的 Signal 改变不应触发无关视图重投影，这也是必须写入测试的契约。

建议的帧内数据流如下：

~~~plantuml
@startuml
~~~

Signal 的具体内部同步实现可以在实现阶段选择，但以下语义是固定的：

- 写入使该 Signal 的 revision 增加。
- 同一批次内，同一 `SemanticKey` 最多产生一次待处理失效。
- 观察关系由 ComponentRuntime::watch 显式建立和释放。
- 组件卸载后，旧 `SemanticKey` 的订阅必须释放；陈旧 key 不能污染新实例。
- 没有 watch 的 Signal 写入不触发重投影。

## 5. 事件模型：BindId 与组件事件彻底分离

### 5.1 BindId 只表示字段绑定

BindId 仍是业务字段绑定标识，且只用于 UiAction::ValueChange 一类值改变。它可以表示
profile.display_name、filter.price_min 或 settings.theme，但不能再编码“打开新建文件夹”“删除记录”之类的
命令。

现有 desktop 演示中以 ui.invoke: 前缀把业务命令塞进 BindId 的 codec 是迁移对象。重构完成时，该前缀、
解析器、兼容分支和依赖它的测试都必须删除，不能保留为“暂时兼容”。

### 5.2 EventRegistry 与稳定组件部件路径

Headless 新增 EventRegistry。它不读取业务状态，也不认识业务命令；它只做两个确定性步骤：

1. 以当前帧的 NodeId 找到 Headless 注册时留下的稳定 ComponentPartPath。
2. 根据该部件角色和 UiAction 转换为该组件声明的 HeadlessEvent。

ComponentPartPath 是组件语义路径，例如：

~~~text
settings.tabs.trigger["appearance"]
settings.profile.dialog.close
orders.filters.status-select.item["paid"]
~~~

它不是 NodeId：NodeId 会随某次树解析而分配。它也不是 BindId：BindId 属于业务字段。它由组件根路径、
部件名和稳定 item key 组成，列表重排后只要 key 不变，语义身份就不变。

业务 view 可以保留自己独立的视觉树，不必为了接入事件而改造成 kit recipe；但它应以
`components::Button::compose(...).part(...)`、`List` 或 `Input` 等实际 Headless Root/Part 调用
`EventRegistry::register_part`。这样 EventRegistry 会校验角色和事件族，Controller 再通过
`ComponentPartPath::item_key` 取得稳定业务 key；不能重新退回到对任意 SemanticKey 直接 register
任意 HeadlessEvent 的模式。

~~~plantuml
left to right direction

rectangle "UiFrame\nNodeId -> ComponentPartPath" as frame
rectangle "UiAction\nClick / Scroll / Focus / ValueChange" as action
~~~

EventRegistry 至少必须保证：

- 重排后的有 key 集合仍路由到原来的语义 item；
- 已被替换或卸载的节点动作按帧版本安全丢弃；
- 组件事件带足够的类型化载荷，例如选项 key、open 值、取消原因，而不是交给应用解析字符串；
- 普通字段 ValueChange 仍经 BindId 回到 Application；
- 点击、关闭、选择等组件控制事件不再借用 BindId。

Headless 不能通过各 kit 私自模拟 Kernel 缺失的行为。以下能力是为完整组件目录建立的 Kernel 增量；

### 7.1 目录使用规则

1. Primitive 不是任意视觉积木的别名。Box、Text、Icon、Image 等只提供稳定语义和视觉基础能力，不能吞进
   Select、Dialog 之类的交互状态机。
2. Atomic 是带有稳定交互契约的单控件，例如 Button、Input、Checkbox、Switch、Slider。它们可被
   Molecular 组合，但不绑定业务字段名称或应用动作。
3. Molecular 是通用工具单元，例如 Form、Search、Menu、Dialog、Table、Picker。它们以 Root/Part
   组合表达复杂行为，并仍然没有行业模型。
4. Business 层不进入这些 crate。CRUD 工作台、游戏 HUD、编辑器、金融图表、订单页等在应用或独立领域
   crate 中组合通用组件。
5. 每个根组件族至少定义：受控输入状态、可选 disabled/loading/error 状态、部件目录、类型化事件、稳定
   item key 要求、键鼠/触摸适用路径和最小测试矩阵。

### 7.2 双 Kit 的角色

| 形态 | 优先目标 | 典型差异 | 不允许发生的事 |
|---|---|---|---|
| desktop-kit | 信息密度、精确焦点、键盘导航、鼠标 hover、表格/树/多面板工作流 | 较紧凑的 control size，强调 hover、context menu、快捷键和多列布局 | 读取 Windows/macOS API，或把移动 TouchAdapter 逻辑复制进 kit |
| mobile-kit | 单手触控、最小触控目标、页面层级、安全区、底部操作和连续手势 | 较大触控目标，NavBar/Tabbar/Cell/Sheet/ActionSheet 等移动表达 | 通过 if iOS / if Android 决定共享 UI 行为，或把 UIKit/Android 业务代码引入 kit |

“行为一致”不等于“视觉一致”。例如 Dialog 在 desktop-kit 可以是居中模态窗，在 mobile-kit 可以是底部
Sheet；它们共同遵守 open、dismiss、outside click、focus 和取消语义。反过来，Sidebar 不需要被伪造为
手机侧栏，NumberKeyboard 也不需要被伪造成桌面主输入方式。

## 8. Theme 与内置 recipe

对外只开放语义 token，不开放一个可由应用随意替换内部结构的 recipe trait。这样能保留可测试、可升级的
组件包边界，同时允许不同产品提供统一主题。

| 主题对象 | 至少覆盖的 token 类别 | 使用者 |
|---|---|---|
| DesktopTheme | surface / text / border / accent / danger 等颜色；字体层级；间距；圆角；elevation；紧凑控件高度；focus/hover/selected/disabled 状态 | desktop-kit |
| MobileTheme | surface / text / border / accent / danger 等颜色；字体层级；间距；圆角；elevation；最小触控目标；安全区相关布局尺度；pressed/disabled 状态 | mobile-kit |

内置 recipe 具有以下约束：

- recipe 可以选择本 kit 的布局、视觉节点和 token，但不能改变 Headless 组件已声明的状态机、事件名称或
  BindId 边界。
- App 可以创建或传入自己的 DesktopTheme / MobileTheme 值，但不能通过主题把业务数据、Host 句柄或
  Renderer 资源塞进组件。
- 同一 Theme 的 token 改变只影响视觉和尺寸相关投影；业务状态仍由 Application 的 Signal 驱动。
- 不提供从 crate 导出源码的 CLI，也不建立由外部文件生成组件实现的注册中心。

任何临时桥接都必须在最终验收前删除。

- tela-ui-foundation 对 Signal 或 SignalSubscription 的重导出；
- BindId 值中的 ui.invoke:、命令字符串解析器或相应兼容断言；
- 仅为了旧调用点存在的 DesktopKit / MobileKit 旧 API 别名；
- 组件用特定 app 的 Store、路由名、资源路径或业务模型决定行为；
- 根据目标平台名称在 shared UI / Host 中选择业务视图。

## 10. 测试与验收

没有 gallery 的前提下，测试目录就是组件目录的证明。每个根组件族都必须进入同一份可枚举矩阵，不能只为
“最常用”的组件写测试。

### 10.1 Kernel 测试

| 范围 | 必测行为 |
|---|---|
| Grid | track 解析、固定/弹性约束、span、溢出与嵌套布局 |
| Anchored overlay | side / align、flip、shift、边界 clamp、滚动后重新放置 |
| Modal / focus | modal 与 non-modal、outside click、焦点限制、关闭后的恢复 |
| Pointer capture | 捕获后移出命中区域仍接收事件、Up/Cancel/卸载均释放 |
| Gesture | 嵌套 scroll 与 swipe 的竞争、long press、pinch、取消和多指顺序 |
| Text input | 输入类型、IME composition、selection、提交/取消与焦点切换 |
| Text constraint | 单行省略、多行 clamp、真实测量边界与布局稳定性 |

### 10.2 Headless 与事件测试

| 范围 | 必测行为 |
|---|---|
| Signal / watch | 批量写入合并；未 watch 的 Signal 不重投影；卸载路径不再订阅 |
| 组件身份 | 稳定 ComponentPartPath；有 key 列表重排后仍指向原 item；重复/缺失 key 失败 |
| 帧安全 | 帧版本不匹配、已卸载部件和陈旧 NodeId 的动作被丢弃 |
| EventRegistry | UiAction 正确转为 Select、OpenChange、Dismiss、Cancel 等 HeadlessEvent |
| BindId 隔离 | ValueChange 保留字段绑定；控制事件不经过 BindId；ui.invoke: 不能再被解析 |
| Root / Part | 不合法部件组合、缺少必需 Part、disabled 和受控状态的语义一致 |

### 10.3 114 根组件族的统一矩阵

每一个根组件族至少验证以下列。某列对组件不适用时，测试必须写明“不适用的语义理由”，而不是静默跳过。

| 矩阵列 | 验证内容 |
|---|---|
| 默认投影 | 由 `ComponentSpec::root` 创建完整 Root；required Part 和 `UiTree` 都必须合法 |
| 受控状态 | 每个声明 state 的变体必须改变同一路径的 recipe 树；Layer 的内容态在相同的 open 上下文比较 |
| disabled / loading / error | 禁用和 loading 完全移除部件交互；loading/error/selected/range 等都必须有可见投影 |
| 键盘路径 | Required 根组件把焦点置到实际 Part 后注入 `KeyboardIntent::Activate`，必须得到对应 `UiAction::Click`；方向、取消等由声明了该专门语义的组件另行增加断言 |
| 触摸路径 | Required 根组件的实际 Touch Down/Up 必须经 Kernel、EventRegistry 到达 Headless；声明 Gesture 的根再执行真实 pan，集合/ScrollArea 验证 Scroll，PullRefresh 验证 Refresh；mobile 还验证每个实际触控节点至少 44pt |
| 事件输出 | 标准 Root 的每一个已声明且非字段事件都必须有路由；`ValueChange` 只保留 BindId 通道；帧版本、重排和 disabled/loading 均有单独测试 |
| 视觉参考 | Kit 对每个支持形态的所有声明状态生成稳定 `UiNode` FNV-1a；Application 测试用同一集合装配 kit 与软件 renderer，再生成 RGBA FNV-1a，任何结构或像素改变都需显式审查 |

当前实现把结构、状态和真实输入矩阵放在 `crates/ui/desktop-kit/src/recipe.rs` 与
`crates/ui/mobile-kit/src/recipe.rs`，而将 RGBA catalog reference 放在
`apps/desktop-demo/src/application/runtime.rs` 与 `apps/mobile-demo/src/application.rs`。后者是有意的
Application 测试边界：它可以在 dev dependency 中同时选择 kit、资源和 renderer；UI Capability 则始终不依赖
Presentation。`ComponentMatrix` 的 `NotApplicable(reason)` 是数据模型的一部分；catalog 测试会拒绝空理由。

### 10.4 工程门禁

1. 所有目标 crate 的 fmt、clippy、unit / integration tests 与依赖方向检查，即项目的 ops check。

3. desktop 与 mobile bundle 的构建和验证，包括 ops build bundle、ops verify bundle、ops build bundle mobile、

   iOS 构建或 iPhone 真机行为标记为已验证。
3. 114 根组件的目录、契约和 recipe 投影，以及第 10.3 规定的键盘、触摸、事件、状态树和 RGBA 矩阵，
   已由本次测试覆盖；后续新增根组件或新状态时仍必须把它纳入同一可执行矩阵。

Root/Part 思路。借鉴的是能力分类和可组合性，不复制其源码分发模式、平台实现或领域扩展。

## 12. 最终边界检查

实施过程中每一次新增组件都应回答下面的问题；任一答案不清楚，就先补契约而不是直接加视觉节点：

1. 它属于哪一个 114 根组件族，还是其实是业务组件？
2. 它的受控状态由哪个 Application Signal 持有？
3. 它的 Root 与 Part 是什么，稳定 item key 在哪里？
4. 它发出的 HeadlessEvent 是什么，是否错误地使用了 BindId 承载命令？
5. 它需要的行为是 Headless 能解决，还是必须先补 Contract / Kernel？
6. desktop-kit 与 mobile-kit 分别怎样表达它，哪些形态本来就不应实现？
7. 它的默认、受控、disabled、键盘/触摸、取消和视觉参考测试放在哪里？

只要这七项都可被源码和测试回答，组件体系才能在扩大目录时保持正交，而不是把更多名字堆进一组难以维护
的视觉函数。
