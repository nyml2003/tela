# 020-字体基线焦点与键盘意图实施目标

> **状态：✅ 基线、键盘与生命周期代码已落地；✅ 2026-08-15 将图标-标签光学对齐收束到 `tela-icon` provider 与 `tela-ui::Text`；👀 浏览器画布人工验收待确认。**
> **前置：** [007-绘制与渲染后端](007-绘制与渲染后端.md) 定义文字与帧协议；[008-交互焦点与宿主接口](008-交互焦点与宿主接口.md) 定义焦点图；[019-文件管理器视觉与图标系统实施目标](019-文件管理器视觉与图标系统实施目标.md) 已建立受控字体与图标组件。  
> **范围：** 本文先记录目标接口与所有权，再在第 11 节回填实际落点、自动化验证和剩余人工验收项。

## 1. 目标

文件管理器当前已经具备全视口客户端结构和图标字体基础，但截图暴露出三个没有闭环的基础问题：

1. 文字行缺少真实基线，且图标字体与文字基线混用会产生光学上浮；
2. 焦点状态存在于 core 的交互路径中，却没有完整的键盘输入桥、可见焦点提示和失效清理；
3. 悬停提示只处理进入，离开后没有恢复，说明宿主没有完整消费状态生命周期。

本阶段将它们收敛为同一条输入和排版链路：

~~~text
真实字体度量 -> 文字基线 / 图标标签视觉居中 -> 后端按基线绘制
平台按键 -> 键位表解析 -> 键盘意图 -> 焦点图/业务动作
core 生命周期动作 -> 应用投影状态 -> 状态栏与可见焦点
~~~

必须保持以下边界：

- tela-core 继续拥有焦点图、基线布局和纯输入规约，不拥有用户键位配置、业务命令或平台事件监听；
- 键位表由宿主/应用层持有，能在运行时整表注入和替换；
- 当前焦点、默认焦点身份和跨帧重映射由 tela-core 的 UiTree/ViewStateStore 维护；tela-widgets、tela-ui 和页面调用方不管理 tela key 或全局焦点；
- 虚拟列表等离屏重建，或其他身份无法由 core 可靠推导的特殊集合，业务复用已有实体 ID 提供 semantic-id；
- 方向导航仍然只依赖组件树和焦点图，禁止退回屏幕坐标最近邻；
- 文本输入、IME 组合态和快捷键解析保持两条不同通道。

## 3. 已确认决策

| 主题 | 决策 |
| --- | --- |
| 键位表所有者 | 宿主/应用层持有当前 KeymapSnapshot；core 不保存、解析或热更新键位表。 |
| 物理键来源 | 使用平台物理键代码归一化，例如浏览器 KeyboardEvent.code；不把受键盘布局影响的字符值当作组合键身份。 |
| 键盘意图 | KeyCombo 只用于查表；解析结果是 FocusNext、MoveFocus、Activate、Cancel 或 Invoke(ShortcutId) 等语义意图。 |
| 键位序列 | 第一阶段只支持单个组合键，不实现多步 chord、超时状态机或录制宏。 |
| 作用域 | UI 树只声明稳定的 KeymapScopeId；活动焦点的最近作用域优先，逐层向外回退，最后查应用默认层。 |
| 更新语义 | 运行时只替换校验通过的完整不可变快照；不允许半更新和原地修改，后续按键立即读取新快照。 |
| 焦点身份 | 约八成常规 UI 使用 core 默认策略；组件不传 focus_key，UiTree/ViewStateStore 生成、保持并重映射当前焦点。动态集合分子组件可仅声明 AutoStableIdentity，让 core 用稳定结构语义分配身份；虚拟列表及其他 core 无法可靠推导实体身份的例外才由业务提供 semantic-id。 |
| 焦点可见性 | core 在 resolve 期间按当前稳定焦点 key 生成不参与布局和命中的 FocusRing 绘制装饰。 |
| 文字与图标 | 文本度量、布局盒与绘制命令都传递真实首行基线；文字与文字使用 `BaselineRow`，图标字体与单行标签使用 `tela-ui::Text` 的视觉居中。 |
| 悬停清理 | entered=false 是一等生命周期事件；树重建后还要做一次投影状态校验，防止条件卸载时留下陈旧提示。 |

这些决策对应决策日志中的 D54 和 D55。此前 D27 的组件内静态快捷键映射只保留为历史记录，不得再作为新增接口的依据。

## 4. 键盘：原始输入、键位表和意图三层分离

### 4.1 三层模型

~~~text
平台 adapter
  RawKeyboardEvent { physical_key, modifiers, state, repeat }
        |
        v
应用 KeymapSnapshot + 当前 KeymapScopeId 路径
  resolve(raw) -> KeyboardIntentEvent
        |
        v
tela-core
  焦点图规约 / UiAction::ShortcutActivated
        |
        v
应用 Controller 或宿主业务
~~~

原始事件描述“按下了什么”，键位表描述“这个组合键在当前上下文代表什么”，键盘意图描述“UI 应该做什么”。三个概念不能混为一个 enum。

建议的契约类型如下；名称可在实现期校准，但职责不能改变。

~~~rust
pub enum PhysicalKey {
    KeyA,
    KeyB,
    // ...
    Digit0,
    // ...
    Tab,
    Enter,
    Escape,
    ArrowUp,
    ArrowDown,
    ArrowLeft,
    ArrowRight,
    // ...
}

pub struct KeyCombo {
    pub modifiers: Modifiers,
    pub key: PhysicalKey,
}

pub enum KeyboardIntent {
    FocusNext,
    FocusPrevious,
    MoveFocus(FocusDirection),
    Activate,
    Cancel,
    Invoke(ShortcutId),
}

pub struct KeyboardIntentEvent {
    pub intent: KeyboardIntent,
    pub repeat: bool,
}
~~~

现有 Key::Char 不能继续作为物理组合键的正式语义。可打印文本由文本输入通道提供；例如 Ctrl 加物理位置 KeyS 是一个 KeyCombo，而不是字符 s。

### 4.2 应用层键位表

键位表是应用配置，而不是 UiNode 属性。tela-contract 只放无状态的协议类型；可替换快照、校验和解析器首先落在 tela-demo 的 application/keymap 模块。未来多个应用确实复用同一实现后，才考虑提取无依赖 tela-keymap crate。

~~~rust
pub struct KeymapSnapshot {
    pub revision: u64,
    pub default_layer: KeymapLayer,
    pub scoped_layers: BTreeMap<KeymapScopeId, KeymapLayer>,
}

pub struct KeymapLayer {
    pub bindings: Vec<KeyBinding>,
}

pub struct KeyBinding {
    pub combo: KeyCombo,
    pub intent: KeyboardIntent,
}
~~~

应用必须提供等价于以下两个操作的接口：

~~~rust
fn handle_raw_key(&mut self, event: RawKeyboardEvent) -> Vec<UiAction>;
fn replace_keymap(&mut self, snapshot: KeymapSnapshot) -> Result<(), KeymapError>;
~~~

WebView、原生宿主和测试夹具可以有不同传输格式，但最终都调用同一个应用层解析器；不能为不同 renderer 维护两份键位逻辑。浏览器运行时注入可使用版本化 JSON，解析完成后再调用 replace_keymap，而不是把未校验 JSON 留在渲染层。

替换快照时必须一次性校验：

1. 同一个层内，同一 KeyCombo 只能出现一次；
2. PhysicalKey、修饰键和 KeyboardIntent 必须属于当前协议版本；
3. Invoke 的 ShortcutId 必须是应用允许的语义动作；
4. 快照 revision 不得回退；拒绝后保留旧快照；
5. 某个尚未显示的 KeymapScopeId 可以有配置，以支持之后打开的模态或条件分支。

解析优先级是当前焦点最近作用域、祖先作用域、default_layer。第一个匹配的组合键获胜。多个组合键可以映射到同一意图。纯宿主级命令，例如浏览器全屏，可在此流程前由宿主处理；它们不进入 core。

### 4.3 焦点树与键位表的连接

现有 ShortcutScope 将映射表直接塞进 UI 树，这一结构在本阶段改为只声明 KeymapScopeId 的逻辑容器。KeymapScopeId 是键位作用域，不是焦点身份；core 仍负责默认焦点 key、当前焦点和从当前稳定焦点返回的作用域祖先路径，应用只把路径交给自己的 KeymapSnapshot 解析器。

~~~text
当前焦点节点
  -> 最近 KeymapScopeId
  -> 父 KeymapScopeId
  -> ...
  -> 应用 default_layer
~~~

这让 Teleport、ModalHost 和 FocusScope 仍按 core 已有的逻辑焦点链工作，同时不会把用户偏好、快捷键 JSON 或业务命令绑定进组件定义。组件只声明结构，应用只持有配置。

core 的输入入口改为消费 KeyboardIntentEvent：

- FocusNext 和 FocusPrevious 使用既有 Tab 树序规则；
- MoveFocus 使用既有方向化焦点图，绝不读取像素位置；
- Activate 和 Cancel 使用现有确认、取消规约；
- Invoke 只输出 UiAction::ShortcutActivated，业务副作用仍在上层。

长按重复策略也是意图的一部分：焦点移动允许 repeat；Activate、Cancel 与 Invoke 默认忽略 repeat，防止重复提交、重复关闭或高频业务命令。需要连续触发的业务必须显式定义不同意图，不能靠放开默认防线。

### 4.4 浏览器与 IME

浏览器画布需要成为可聚焦宿主表面，并在该表面激活时接收 keydown：

- canvas 具有 tabindex；点击非文本交互区域时恢复其 DOM 焦点；
- adapter 使用 KeyboardEvent.code、修饰键、repeat 和 isComposing 归一化原始事件；
- 键位表命中的非文本 UI 意图会阻止浏览器默认行为，尤其是 Tab；未命中的按键不伪造 UI 事件；
- 隐藏 textarea 仍只承担文本、beforeinput 和 IME 组合态；组合期间不把可打印键转为快捷键或焦点意图；
- 文本编辑结束、取消或失焦后，焦点返回由现有显式 SaveFocus/RestoreFocus 规则决定，而不是由 DOM 偶然决定。

通用键盘桥覆盖唯一的 WebView WGPU 入口，并最终调用同一个 `App::handle_raw_key`。页面或 JavaScript 不能各自维护一份焦点顺序、键位表或业务分支。

## 5. 可见焦点与生命周期

### 5.1 不改变布局的 FocusRing

焦点提示不是每个 Button、Table 行或导航项各自维护的 hovered 变体。它由 core 在 resolve 时根据 ViewStateStore 的当前稳定焦点 key 投影；该 key 对常规 UI 由 UiTree 默认策略生成，不要求组件或页面提供：

1. resolve 接收只读的焦点状态和宿主提供的 FocusAppearance；
2. 遍历到焦点节点时记录其最终布局盒、裁剪区域和视觉圆角；
3. 在该节点子树的正确绘制顺序追加 FocusRing；
4. FocusRing 使用独立 DrawPayload 边框，默认在盒内缩进 2px；
5. 它不写入 LayoutConcern、不扩大 HitRegion、不参与布局尺寸计算。

FocusAppearance 是主题输入而不是 core 内置配色。最小字段为颜色、线宽和内缩；没有宿主样式时可显式关闭。这样 core 仍是纯函数：相同树、视图状态、样式和 viewport 必然生成相同帧。

当树重建后当前焦点 key 不再存在或不可聚焦，ViewStateStore 必须清空该焦点；下一次 FocusNext 从当前作用域的首个可聚焦节点开始。这个清理和 FocusRing 的消失必须在同一帧完成。

### 5.2 悬停和状态栏的完整投影

状态栏的命令说明是应用投影状态，不能把一次 Hover 进入当作永久赋值：

1. entered=true 时，只有命中的可说明目标才写入 hovered_toolbar_target；
2. entered=false 时，只在离开的 node 仍是当前记录目标时清空，避免旧节点离开事件覆盖新节点进入事件；
3. 每次树重建或命令集合变化后，应用以 core 当前 hover key 回查本帧真实交互节点；若 key 已卸载则清空，不能让 AutoPath 的同槽位新节点继承旧提示；
4. 状态栏按 hovered 提示、当前选择摘要、当前目录摘要的优先级派生文本，不能缓存渲染后的字符串。

这套规则适用于条件卸载、模态关闭、筛选后节点消失和指针直接离开 canvas 的场景。组件只派发 UI 生命周期动作，业务容器决定最终提示文本。

## 6. 字体度量、基线布局与绘制

### 6.1 文本契约

TextMetrics 新增 first_baseline，表示从文本布局盒上边缘到第一条渲染文本基线的逻辑距离。它由实际 FontRef 对应字体数据和字号得出，不允许使用单纯 font_size 或图标尺寸猜测。

~~~rust
pub struct TextMetrics {
    pub width: f32,
    pub height: f32,
    pub line_count: u32,
    pub first_baseline: f32,
}
~~~

换行文本的行间距继续由 line_height 控制；用于横向基线对齐的是首行基线。无字形、空文本和 no_std 降级路径也必须给出确定的回退基线，保证布局不会产生 NaN 或后端间漂移。

### 6.2 布局与帧协议

布局盒新增可选 first_baseline。文本节点写入该值；其他节点没有时以交叉轴末端作为基线回退。`BaselineRow` 是专门的水平布局节点：

1. 行收集每个子项的基线；
2. 找到该行最大基线位置；
3. 将每个子项沿交叉轴移动到同一基线；
4. 没有文字基线的子项按其盒底参与，保持现有非文本组件的可预期行为。

Icon 是使用 tela-icons 的文本节点，因此它也有真实字体度量；但真实基线并不保证跨字体的可见墨迹对齐。`tela-text::GlyphInkMetrics` 从与实际 baseline 一致的受控字体轮廓计算逻辑墨迹中心，`tela-icon` provider 将目标中心差写入 `VisualConcern::visual_offset`。所以 `BaselineRow` 保留给文字与文字；IconButton、带图标的 ToolbarItem、导航行、文件行和品牌行使用 `tela-ui::Text` 的 `Icon` prefix/suffix 与普通 `Row` 的 `CrossAlign::Center` 组合。该偏移仅改变 draw 命令和文本 baseline，不影响布局、命中、clip 或页面的 key。

解析后的 DrawPayload::Text 还必须携带绝对 baseline_y。renderer 只按这个坐标放置字形原点；它不再以 geometry.y 加 font_size 或后端局部 ascent 猜测基线。raster、Canvas 和 WGPU 对同一 UiFrame 必须解释同一个 baseline_y。

受控字体字节继续由 tela-fonts 提供。TextMeasurer 与实际 renderer 必须使用同一 FontRef 对应数据；未知 FontRef 和无字形路径按既有回退策略工作，但必须返回一致的度量。

## 7. crate 与文件归属

| 位置 | 本阶段职责 | 明确不负责 |
| --- | --- | --- |
| tela-contract | PhysicalKey、KeyCombo、KeyboardIntent、KeymapScopeId、KeyboardIntentEvent、TextMetrics 基线字段和帧协议字段。 | 可变键位表、浏览器事件、业务命令实现。 |
| tela-core | 默认焦点身份分配、焦点意图规约、作用域路径查询、BaselineRow、FocusRing 帧投影和焦点失效清理。 | JSON、键盘布局转换、用户偏好、DOM。 |
| tela-icon | 语义 `IconKey`、provider、Material iconfont 映射与基于 `GlyphInkMetrics` 的光学校正；降级为已有 core 原语。 | renderer 协议、Button 状态、全局焦点、tela key。 |
| tela-widgets | Button 等原子组件接受任意内部内容，继续只管理局部视觉手感。 | 图标来源、全局焦点、键位表、tela key。 |
| tela-ui | `Text`/`InlineSlot`/`IconButton`、Toolbar 等分子组件消费统一的焦点/图标结果；动态项目集合只声明 core 的 AutoStableIdentity，不生成或保存 tela key。 | 文件业务、键位配置、renderer。 |
| tela-demo/application | KeymapSnapshot、校验、热替换、RawKeyboardEvent 到意图的解析、状态栏悬停投影。 | 平台 DOM 监听和绘制后端。 |
| WebView SDK JavaScript 半边 | DOM 焦点、KeyboardEvent.code 归一化、IME/text bridge 和调用统一 ABI/guest 入口。 | 焦点图、键位解析策略、业务命令。 |
| `tela-text` | 受控字体选择、em 缩放、文本度量、绝对基线定位和字形覆盖事件；不持有 renderer 或宿主状态。 | 纹理、Canvas、GPU、布局树、焦点。 |
| renderers | 按 UiFrame 的 baseline_y 绘制；Raster/WGPU 消费 `tela-text` 覆盖事件，Canvas 直接消费同一帧协议；验证字体数据与像素结果。 | 自行重算布局、字体度量或维护焦点状态。 |

新增代码应按这个物理结构拆分，例如 application/keymap、application/input、core/interact/focus、core/layout/baseline 和 renderer/text；不得把 DOM 事件、键位 JSON、焦点图和页面状态栏逻辑堆入 runtime.rs。

## 8. 实施顺序

1. 在 tela-contract 增加键盘意图、作用域标识和基线协议，并为旧 RawKeyboardEvent/ShortcutScope 写清迁移弃用期；
2. 在 tela-core 先完成基线布局、文本帧坐标、FocusRing 和焦点失效清理，再将键盘入口切换为 KeyboardIntentEvent；
3. 在 tela-demo/application 新建 keymap 与 input 模块，实现默认键位表、完整快照校验、热替换和悬停投影修复；
4. 为 WebView WGPU 入口接入通用键盘桥和 DOM 焦点管理，保留 IME 专用路径；
5. 迁移 IconButton、Toolbar、导航和详情摘要到 `tela-ui::Text` 的图标行内组合；文字-文字关系保留 Baseline，并补全焦点视觉主题；
6. 源码和自动化测试完成后更新本文和 D54/D55；浏览器画布人工验收单独保留为可见的待确认项。

每一步都必须保持现有鼠标、文本输入、IME、文件选择、弹窗和渲染后端可用；不能以暂时删除某条输入路径换取通过。

## 9. 验收标准

### 9.1 文字与图标

- 对同一行中文、英文、数字标签，布局测试验证计算后的文字基线相同；图标+标签以 `tela-ui::Text` 和 `tela-icon` provider 验证实际字形墨迹中心误差不超过 1px；
- raster、Canvas mock 与 WGPU 对相同 UiFrame 使用相同 baseline_y；至少一组图标和标签像素测试覆盖非透明字形；
- 改变 FontRef 或字号后，基线由度量重新计算，不依赖 IconButton 的固定偏移；
- FocusRing 的加入不会改变焦点节点、邻居节点或 HitRegion 的布局数据。

### 9.2 焦点与键盘

- Tab、Shift+Tab、上、下、左、右、确认和取消都能从浏览器 host 进入同一 App 输入链；
- 浏览器键位表热替换后，不重建 UI 树即可使用新绑定；无效或过期快照不会破坏旧绑定；
- 内层 KeymapScopeId 覆盖外层，离开作用域后外层重新生效；Teleport 和模态只使用当前焦点链上的作用域；
- 普通页面测试不传 focus_key，仍由 AutoPath/AutoStableIdentity 保持焦点；虚拟列表及其他 core 无法可靠推导实体身份的特殊集合，以业务实体 semantic-id 保持焦点；
- 方向意图的测试只读取焦点图和树序，不读取布局坐标；
- 键盘可见焦点在请求、移动、模态切换和节点卸载后均正确出现、移动或消失；
- IME 组合期间的文本按键不触发快捷键，文本提交、取消和失焦语义不回归。

### 9.3 生命周期

- 指针进入“新建”后显示对应状态栏说明；离开后恢复到选择/目录摘要；
- 从 A 移到 B 时，A 的离开事件不能清除 B 的说明；
- 目标在悬停期间被过滤、条件卸载或关闭模态后，状态栏不保留已不存在命令的说明；
- 焦点节点在树重建中消失后，ViewStateStore 和 Frame 中不保留悬空引用。

## 10. 非目标与完成定义

本阶段不实现多键 chord、宏录制、浏览器保留快捷键接管、基于屏幕坐标的空间导航、每个组件自行维护焦点 key，或为对齐图标加入页面私有魔法偏移。

完成的定义是：协议、core、应用、浏览器桥和三条 renderer 路径均按本文职责落地；自动化测试覆盖基线、键位热替换、焦点图、IME 和离开生命周期；画布人工验收确认图标/文字基线、焦点环和键盘导航可见且正确。仅有文档、单后端构建或局部单元测试均不构成完成。

### 11.3 待用户进行的画布验收

遵从“不自行启动 Chromium”的约束，本次没有拉起浏览器。请在现有页面上人工确认：

1. 顶栏品牌、工具栏、导航行和文件摘要中的图标与中英文标签视觉居中；文字与文字仍共享文字基线。不要在页面层加入私有 y 偏移；
2. Raster 与 WGPU 后端都填满 canvas 全视口；在高 DPI 下没有被 CSS 放大的左上角裁剪区；
3. 点击 canvas 后 Tab、Shift+Tab、上下左右、Enter 与 Escape 均能移动、激活或取消，并显示蓝色 FocusRing；WGPU 下它必须是透明内部的 2px 描边，而非填满整行的蓝色矩形；
4. Tab 从搜索/弹窗输入离开后，方向键移动 canvas 焦点而不是被隐藏 textarea 吞掉；
5. 鼠标进入“新建”时底部说明更新，离开后恢复；
6. 控制台调用 `window.telaReplaceKeymap(json)` 后新按键立即生效，非法或回退 revision 保留旧表。

浏览器宿主使用 `node web/build.mjs` 打包，绕开 pnpm 的运行前安全检查，但仍只使用项目已安装的依赖；浏览器视觉验收仍由用户在现有页面完成。

### 11.4 本次 renderer 校正的完成边界

截图已经证明 Raster 与 WGPU 消费同一个 `UiFrame` 并不自动保证相同像素：WGPU 曾在 CPU 批处理阶段把
core 发出的 `RoundedRect { fill: None, border: Some(...) }` 改写成同色实心填充且丢掉 border width，导致
FocusRing 变成蓝色矩形。修复只在 `tela-render-wgpu::RoundedBatch`，没有改页面 DSL、core 焦点策略或
FocusAppearance。单元测试覆盖该顶点编码；由于本机原生 draw 回读环境不可靠，最终 WGPU 着色器画面仍需由
浏览器人工确认，不能以这项测试替代。
